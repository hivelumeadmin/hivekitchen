## Story

As **a parent starting onboarding for the first time**,
I want **Moment 1 ("Who's at the table") to capture my household name and each child's name + age band via the chaptered conversation**, so that **Lumi writes `households.display_name` and one `children` row per child into the DB, the UI header shows "Moment 1 of 5 · Who's at the table", the Kitchen Profile panel reflects what has been captured so far, and mid-Moment-1 resume correctly picks up where I left off**.

### AC1 — `household.set_name` tool wires a real DB write

Replace the stub in `createHouseholdSetNameToolSpec` with a call to a new `HouseholdsService.setDisplayName` method.

**AC1.1 — `HouseholdsRepository.setDisplayName`** (new method)

```typescript
async setDisplayName(householdId: string, displayName: string): Promise<void> {
  const { error } = await this.client
    .from('households')
    .update({ display_name: displayName })
    .eq('id', householdId);
  if (error) throw error;
  await this.bumpKitchenMapVersion(householdId);
}
```

`display_name` is NOT encrypted (low PII risk — self-chosen household label like "The Menons"). No DEK needed. The `bumpKitchenMapVersion` call bumps `kitchen_map_version` so the kitchen map composer picks up the new value on next read.

No vocabulary validation needed — `display_name` is a free-text label constrained only at the contract boundary (`HouseholdSetNameInputSchema.display_name: z.string().trim().min(1).max(120)`).

## Dev Agent Record

### Implementation Plan

Worked the slice as nine sequential tasks (T1-T9). The repository-up-then-tool-down ordering matched the actual call graph and let each layer's test compile before moving on. The frontend refactor was a single pass: extract `submitTurn(chips, text)` from the existing `handleSubmit`, then call it from both the form submit and the SkipChip onClick — no duplicated optimistic-render/rollback logic.

Two non-obvious decisions while implementing:

1. **`pre_start` chip_config test** — the existing 2.5-s4 passthrough test iterated all moments including `pre_start` and asserted `null`. After this slice fills `m1_table`, the bootstrap logic in `submitTextTurn` advances `pre_start → m1_table` on the first turn, which means a `pre_start` preTurnMomentState now produces an `m1_table` chip_config. Dropped `pre_start` from the null-loop and added a dedicated test that exercises the bootstrap → M1 hint chips path.

2. **SkipChip `getByRole('button')` mismatch** — the SkipChip renders via `ChoiceChip` with `mode='single'`, which sets ARIA `role='radio'`. `getByRole('button', { name: /Skip/ })` therefore can't find it. Used `findByText` instead — the visible "Skip this moment" label is the user-affordance and the click handler is what matters for the assertion.

### Completion Notes

- **AC1 (real DB write):** `households.set_name` tool now writes `display_name` directly via `HouseholdsRepository.setDisplayName`. Single column update, no encryption (per slice guardrail and 2.5-s1 design decision), version bump via `bumpKitchenMapVersion` so the kitchen-map composer picks up the new value on next read. `maxLatencyMs` bumped from 80 (stub) → 300 (real write + version bump RPC).
- **AC2 (M1 hint chips):** `momentToChipConfig('m1_table')` returns the canonical 3 hints verbatim from `Moment1Page.tsx`. Function exported so it's covered by a focused unit test alongside the service-level assertions.
- **AC3 (`moment_key` on the wire):** Added to `TextOnboardingTurnResponseSchema` as `z.string().nullable().optional()` — backwards-compatible (old clients ignore it). `SubmitTextTurnResult` gains the field; the route handler returns `result` directly so no route change was needed. ## Dev Notes

### `household.set_name` → `setDisplayName` routing

The tool stub currently has `_deps: OnboardingToolDeps` with a leading underscore to signal it's intentionally unused. Remove the underscore (`deps`) and add the real DB write. The full `OnboardingToolDeps` already includes `householdsService` — no interface change needed.

The `HouseholdsRepository.setDisplayName` is a simple single-column update — no DEK, no encryption. Pattern reference: look at `bumpKitchenMapVersion` in `households.repository.ts` for the simplest supabase update pattern in this file.

### Chip mode for M1 (hint) vs later moments

M1 uses `mode: 'hint'` (non-selectable examples). The taxonomy from the chip memory:
- **hint** = illustrative; renders with "Something like" label; no tap interaction
- **action** = single-select; tap one
- **choice** = multi-select; tap any

M1's broad "tell me about your family" is the canonical hint-chip case. The 3 hint strings match exactly what `Moment1Page.tsx` shows in the `broad-hint` scenario — use those verbatim.

### `moment_key` in the response

The `nextCurrentMoment` variable is already computed in `submitTextTurn` (from 2.5-s4). Adding it to the return is a one-liner. The type is `CurrentMoment` (a string union), which satisfies `z.string()` in the Zod schema. The optional + nullable on the schema means old clients ignore it — zero breaking change.

**First-turn behavior:** On the very first turn, if the agent emits no `[NEXT_MOMENT:]` directive, `nextCurrentMoment` defaults to `'m1_table'` (the bootstrap logic from 2.5-s4's completion notes). So `moment_key` will be `'m1_table'` on the first turn — which is correct for the header.

### `MOMENT_CONFIG` on the frontend

The map only needs to cover the moments the agent can emit in the text path (`m1_table` through `summary`). `pre_start` and `finalized` should return `{ number: 0, name: '' }` so the header falls back gracefully. `summary` maps to `{ number: 5, name: 'Summary' }` — this will be used by 2.5-s10.

### SkipChip wiring without duplication

The current `handleSubmit` in `OnboardingText.tsx` is a `useCallback` that handles both text-turn and chip-turn shapes. Extract the POST logic into a `submitChipTurn(chips, text)` helper and call it from both the form submit and the SkipChip handler. This avoids any duplication and ensures the same optimistic rendering / rollback logic applies.

Pattern:
```typescript
const submitChipTurn = useCallback(async (chips: string[], text: string) => {
  // ... the chip-selection branch of the current handleSubmit body
}, [pending, setChipSelections, setTurns, /* etc */]);

const handleSubmit = useCallback(async (e: React.FormEvent) => {
  e.preventDefault();
  if (hasChipSelections) {
    void submitChipTurn(chipSelections, draft.trim());
    return;
  }
  // ... text-only path
}, [draft, pending, chipSelections, submitChipTurn]);
```

### Resume mid-M1

The "resume mid-Moment-1 works" AC in the sprint change proposal is satisfied by the existing infrastructure:
- `GET /v1/onboarding/state` (2-s26) returns `status: 'in_progress'` with thread turns

No new resume logic is needed for this slice. The story scope "resume mid-Moment-1 works" is confirmed by the existing plumbing.

Copy the `IcoHome` SVG function verbatim from `apps/web/src/features/onboarding-mockups/Moment1Page.tsx` into `OnboardingText.tsx`. It's defined identically to the other icon helpers already in that file. Do not import from the mockup directory — the mockup feature folder is a dev-only surface.
