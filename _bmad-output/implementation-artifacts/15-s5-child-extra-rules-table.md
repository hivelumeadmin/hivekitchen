## Story

As the platform's data model owner,
I want `children.extra_rules` retired in favor of a `child_extra_rules` table (one row per pin/ban),
so that per-child Extra-slot rules are queryable rows instead of a JSONB blob — closing the dual-representation gap the spec calls out (§4.2, §5 row 6) and the JSONB-removal step of the Epic 15 strangler sequence (§8 step 3), continuing directly from 15-s4's `school_policy_notes` retirement.

## Scope (small independent JSONB removal — create table → backfill → drop → coordinated cleanup, per §8 step 3)

**This slice:** a new `child_extra_rules` table (with its own kitchen_map_version bump trigger), a one-shot backfill script copying every child's `extra_rules.pins`/`.bans` array entries into rows, a verification gate, a migration that drops `children.extra_rules` and retires the `append_extra_ban` function (both gated on the backfill's success, USER-SIDE), and rewriting `ExtraRulesRepository`'s internals (and `KitchenMapRepository.loadRaw()`'s extra-rules fetch) to read/write the new table while preserving the exact same `{pins, bans}` shape every consumer already expects.

**NOT this slice:**
- Linking `child_extra_rules` rows to `extra_library` via FK — see Dev Notes point (2). `extra_library` and its UI picker (`useExtraRules.ts`, `child-extra-rules.tsx`) are untouched.
- Any change to the wire contract (`packages/contracts/src/extra-rules.ts`) or the REST route shapes (`PATCH`/`GET /v1/children/:id/extra-rules`) — both keep returning `{pins, bans}` arrays.
- Any change to planner prompt content, snack-rotation logic, or coverage-gating logic (`coverage.ts`, `render.ts`, `snack-rotation.service.ts`, `assemble.ts`) — they consume `ExtraRulesRepository.findExtraRules()`'s return value, which is byte-identical before and after this slice.
- Any change to the passive-bias THRESHOLD/WINDOW semantics in `ExtraRemovalSignalService` (Story 3.22, FR116) — only its call into `ExtraRulesRepository` changes from an RPC to a row insert; the bias behavior (3 removals / 30 days → silent ban) is unchanged.
- Resolving the pre-existing "no RLS on `children`" deferred item (`deferred-work.md`, from 3.21's review) — stays open; `child_extra_rules` gets its own explicit RLS (deny-all for anon/authed, service-role bypass), same pattern as `school_policies`, independent of that gap.

## Acceptance Criteria

1. **Create-table migration** `supabase/migrations/20261035000400_add_child_extra_rules.sql`:
   - `CREATE TYPE extra_rule_kind AS ENUM ('pin', 'ban')` (guarded with the `DO $$ ... EXCEPTION WHEN duplicate_object` idiom used by `slot_scope_enum` in `20260700000000_create_school_policies.sql:14-17`).
   - `child_extra_rules(id uuid PK default gen_random_uuid(), child_id uuid NOT NULL REFERENCES children(id) ON DELETE CASCADE, rule extra_rule_kind NOT NULL, component_type text NOT NULL CHECK (char_length(component_type) BETWEEN 1 AND 50), created_at timestamptz NOT NULL DEFAULT now())`. No `updated_at` — rows are insert/delete only, never updated in place (mirrors the enum-value-plus-label shape; nothing about an existing row changes except its existence).
   - `CREATE UNIQUE INDEX ... ON child_extra_rules (child_id, rule, lower(component_type))` — the case-insensitive dedup key that replaces `append_extra_ban`'s `lower()` containment check (Dev Notes point 6), and is also the backfill's idempotency/upsert conflict target.
   - `CREATE INDEX ... ON child_extra_rules (child_id)` — planner-context read path (mirrors `school_policies_child_id_idx`).
   - RLS enabled, no policy defined (service-role bypass only) — exact precedent: `school_policies` (`20260700000000_create_school_policies.sql:38-41`), not `extra_library`'s member-select policy (that one has a direct `household_id` column; `child_extra_rules` only has `child_id`, same shape as `school_policies`).
   - **Kitchen Map trigger, same migration**: `CREATE TRIGGER child_extra_rules_bump_kitchen_map AFTER INSERT OR UPDATE OR DELETE ON child_extra_rules FOR EACH ROW EXECUTE FUNCTION bump_kitchen_map_from_child();` — exact precedent `school_policies_bump_kitchen_map` (`20260820000000_add_kitchen_map_version.sql:246-249`). This closes the gap described in Dev Notes point (5); without it, PATCH /extra-rules stops invalidating the Kitchen Map cache the moment the column drops.
   - **Replace-full-set function**: `replace_child_extra_rules(p_child_id uuid, p_household_id uuid, p_pins text[], p_bans text[]) RETURNS boolean` — `SECURITY DEFINER`, same lockdown as `append_extra_ban` (`REVOKE ... FROM PUBLIC; GRANT ... TO service_role;`). Verifies `(id, household_id)` match on `children` first (returns `false`/no-op if not found — mirrors the current `updateExtraRules`'s `.maybeSingle()` → `null` cross-household guard), then in one transaction: `DELETE FROM child_extra_rules WHERE child_id = p_child_id`, then bulk-`INSERT` one row per pin (`rule='pin'`) and per ban (`rule='ban'`) from the input arrays. Preserves the current UPDATE's atomicity for the full-replace PATCH path (Dev Notes point 7) — a naive two-call DELETE-then-INSERT from the API layer is not equivalent and must not be used for this path.

2. **Backfill script** `apps/api/scripts/backfill-child-extra-rules.ts` (same shape as `backfill-school-policy-notes.ts` — `#!/usr/bin/env tsx`, numbered-steps header docblock, exported pure `runBackfill({client})` + `verifyParity({client})`, `main()` guard on `import.meta.url`, non-zero exit on failure, idempotent, `ScriptDeps.logger` threaded into every skip/warn path):
   - Pages `children` selecting `id, extra_rules`, `ORDER BY id ASC` (15-s3's review lesson — every paginated `.range()` scan must carry an explicit stable-key `ORDER BY`; do not repeat the unordered-pagination bug two review layers caught there).
   - For each child, parse `extra_rules` (reuse `parseExtraRules`'s tolerant-parse logic, or an equivalent inline version — treat a malformed/missing value as `{pins: [], bans: []}`, count and warn, don't throw).
   - For each `pins[i]`, upsert `(child_id, 'pin', pins[i])`; for each `bans[i]`, upsert `(child_id, 'ban', bans[i])`, all via a single batched `.upsert(rows, { onConflict: 'child_id,rule,component_type', ignoreDuplicates: true })` per page (mirrors 15-s4's `ON CONFLICT DO NOTHING` idempotency pattern — note the DB unique index is on `lower(component_type)`, so an exact-duplicate re-run still no-ops even though the upsert's literal conflict target list doesn't include `lower()`; a functional unique index still catches it, verify this in the script's tests against the real conflict target Supabase reports).
   - Skip (count, don't insert) any label exceeding 50 chars (`child_extra_rules.component_type` CHECK) — mirrors 15-s4's `skipped_too_long` pattern; the *contract* layer already caps pins/bans entries at 50 chars (`ExtraRulesSchema`, `z.string().min(1).max(50)`), so this should be a true no-op path in practice, but the backfill must not trust that a historical row was always written through the validated PATCH route.
   - **Verification gate:** for every child with a non-empty `pins`/`bans` array, the corresponding `(child_id, rule, component_type)` triples must all exist as `child_extra_rules` rows, and vice versa (set-equality both directions, `missing_rule_row` / `orphan_rule_row` — mirrors 15-s4's `missing_note_row`/`orphan_note_row` deviation, which is stronger than one-directional count parity and is now the established doctrine for this story family). Mismatch → print diff (child IDs + rule kind only, no component_type text — component_type is not PII but keep the no-PII discipline consistent) and `process.exit(1)`. No skip-on-error escape hatch.
   - Unit tests on the exported pure functions (same fake-Supabase-client pattern as `backfill-school-policy-notes.test.ts`): empty pins/bans skip, idempotent re-run (including a re-run after a human has since edited rows via PATCH — must not clobber), too-long label skip, malformed/missing JSONB tolerance, multi-page continuation (`pageSize: 1`), parity pass/fail both directions, no-PII diff output.

3. **Drop migration** `supabase/migrations/20261035000500_drop_extra_rules_and_ban_fn.sql`:

   DROP FUNCTION IF EXISTS append_extra_ban(uuid, uuid, text);
   ALTER TABLE children DROP COLUMN IF EXISTS extra_rules;

   Header comment mirrors `20261035000300_drop_school_policy_notes.sql`'s convention: states this runs AFTER `apps/api/scripts/backfill-child-extra-rules.ts` has executed against the target database and its verification gate has passed; re-applying before the gate passes is a data-loss event by design. **USER-SIDE GATE**, same doctrine as 15-s1 through 15-s4: authored and reviewed in this slice, but the `supabase db push` that applies it happens outside this dev session. This migration must apply AFTER `20261035000400` (this story's own create-table migration, obviously) and after the still-unpushed `20261035000000`/`…000100`/`…000200`/`…000300` migrations from 15-s1 through 15-s4 — migrations apply in filename order, so `…000400`/`…000500` naturally land last; no action needed, just don't reorder.

4. **`ExtraRulesRepository` rewrite** (`apps/api/src/modules/children/extra-rules.repository.ts`) — same public method signatures and return shapes, internals only:
   - `updateExtraRules(opts)`: calls `.rpc('replace_child_extra_rules', { p_child_id, p_household_id, p_pins: opts.pins, p_bans: opts.bans })`. On `false`/no-op result, return `null` (preserves the current cross-household-guard `null` contract). On success, re-read the child's rows (or accept them back from an `RETURNS TABLE` variant of the function — implementer's choice, whichever keeps one round trip) and build `{ child_id, extra_rules: {pins, bans}, updated_at }` — `updated_at` can be `new Date().toISOString()` (row-level, no single `updated_at` column exists anymore on the aggregate) rather than reading a DB timestamp, since the table has no `updated_at` column (AC #1) and the API response's `updated_at` field only needs to reflect "when this replace happened," not track row-level mutation history.
   - `findExtraRulesForChild(childId, householdId)`: first confirm the child belongs to the household (mirrors the current cross-household guard — a `children` existence+ownership check, since the query no longer implicitly does this via `.eq('household_id', ...)` on the `children` table read), then `SELECT rule, component_type FROM child_extra_rules WHERE child_id = $1`, group into `{pins, bans}`. Returns `null` when the child doesn't exist or isn't in the household (same as today).
   - `appendBanAtomic(opts)` → **replace with a plain `INSERT ... ON CONFLICT (child_id, rule, lower(component_type)) DO NOTHING`** (Dev Notes point 6) against `child_extra_rules` with `rule='ban'`, `component_type=opts.componentType.trim().toLowerCase()` (preserve the existing lowercase-normalization the RPC did). Determine `'appended'` vs `'already_banned'` from whether the insert actually returned a row (Postgres `RETURNING` on a no-op `ON CONFLICT DO NOTHING` returns zero rows). Still needs the cross-household guard (child exists under `p_household_id`) before inserting — do this check first and return `null` if it fails, same contract as today. Consider renaming to `appendBan` (the "atomic" qualifier described *how* the old JSONB approach worked; a plain unique-indexed insert is atomic by construction and doesn't need the RPC route anymore — implementer's call whether the rename is worth the diff noise; if kept as `appendBanAtomic`, note in a comment why it's still just as atomic without the RPC).
   - `findExtraRules(childId)`: `SELECT rule, component_type FROM child_extra_rules WHERE child_id = $1`, group into `{pins, bans}`; return `{pins: [], bans: []}` for a child with zero rows (preserves today's "missing row → default" behavior, now naturally "zero rows → empty arrays" with no special-casing needed).
   - `parseExtraRules` (the tolerant-parse helper) is retired — it existed to defend against a raw/malformed JSONB value; row-based reads have no equivalent decode step. Its logic is reused (not literally, but its "coerce to string[]" instinct) inside the backfill script's row parsing (AC #2).
   - `append_extra_ban` RPC call sites: only `appendBanAtomic` (now `appendBan`) calls it — confirm via grep that `ExtraRemovalSignalService` is the only consumer (matches the current codebase state).

**DEVIATION 1 — the unique index is case-SENSITIVE, not `lower(component_type)` (AC #1).** The story specified `UNIQUE (child_id, rule, lower(component_type))`. That is not implementable here for two independent reasons:
1. `ExtraRulesSchema`'s uniqueness refine is `new Set(arr).size === arr.length` — case-sensitive. `pins: ['Fruit', 'fruit']` is a **currently-valid** PATCH payload. A case-insensitive DB constraint would turn it into a 23505 → 500. That is a regression, not a tightening.
2. PostgREST's `onConflict` names columns; it cannot target a functional index. AC #2's `.upsert(rows, { onConflict: 'child_id,rule,component_type' })` would fail with `42P10` against a `lower()` index. (The story flagged this as "verify against the real conflict target Supabase reports" — it does not hold.)

The index is therefore `(child_id, rule, component_type)`. The case-insensitive dedup the retired `append_extra_ban` RPC provided **for bans only** is preserved in `ExtraRulesRepository.appendBanAtomic`: it lowercases on write (as the RPC did) and compares case-blind against the child's existing bans before inserting. The INSERT + unique index remains the race authority — the pre-check is an optimisation, and a `23505` from a concurrent writer is caught and reported as `already_banned`, not thrown.

**DEVIATION 2 — `replace_child_extra_rules` RETURNS boolean, and `updateExtraRules` does not read back (AC #1/#4).** AC #4 offered "re-read, or a `RETURNS TABLE` variant — whichever keeps one round trip". Neither is needed: a full replace writes exactly the input, so the repository echoes `{pins: opts.pins, bans: opts.bans}` — the same value the old `UPDATE ... RETURNING extra_rules` produced. One round trip, no read-back.

**DEVIATION 3 — the backfill does not report `skipped_existing` as an idempotency proxy alone.** It also counts `skipped_duplicate` (exact duplicates collapsed within one child's array). The contract forbids duplicates, but the script must not trust historical rows.
