### OpenAI strict tool calling — schema requirements

**`strict: true` on a function definition requires:**
1. `additionalProperties: false` on every `object`-type node in the parameters schema (including deeply nested objects)
2. Every `property` of every object node must appear in `required`
3. For fields that are truly optional, they should be typed as nullable: `{ anyOf: [{ type: '...' }, { type: 'null' }] }` — this is what makes them "required-but-nullable"

**`toStrictJsonSchemaParameters()` must implement this.** The existing `toJsonSchemaParameters()` (uses `z.toJSONSchema()`) does NOT add `additionalProperties: false`. The strict wrapper adds it recursively.

**`additionalProperties: false` is the blocker.** If it's missing at ANY level, OpenAI rejects the schema when `strict: true`. Implement the recursion correctly:
```ts
function addStrictConstraints(schema: Record<string, unknown>): Record<string, unknown> {
  if (schema.type === 'object') {
    const props = schema.properties as Record<string, unknown> ?? {};
    return {
      ...schema,
      additionalProperties: false,
      required: Object.keys(props),  // move ALL properties to required
      properties: Object.fromEntries(
        Object.entries(props).map(([k, v]) => [k, addStrictConstraints(v as Record<string, unknown>)])
      ),
    };
  }
  if (schema.type === 'array' && schema.items) {
    return { ...schema, items: addStrictConstraints(schema.items as Record<string, unknown>) };
  }
  if (schema.anyOf) {
    return { ...schema, anyOf: (schema.anyOf as Record<string, unknown>[]).map(addStrictConstraints) };
  }
  return schema;
}
```

Apply this ONLY for strict tool definitions. Non-strict tools continue using `toJsonSchemaParameters()` unchanged.

### `reasoning` field — why it's in `PlanComposeTreeInputSchema` after s2

**Before s2:** `plan.tools.ts:71` recovered `reasoning` from the raw unvalidated `input` (before schema parsing), because `PlanComposeTreeInputSchema` didn't include the field. This was a deliberate workaround: the model emits `reasoning` as planner metadata outside the structural schema.

**After s2:** With strict OpenAI mode, fields NOT in the schema are STRIPPED from the tool arguments before the SDK returns them. So the raw-args recovery silently loses `reasoning`. Fix: add `reasoning: z.string().max(600).optional()` to `PlanComposeTreeInputSchema`. The schema's `.superRefine()` validates structural cross-references (`main_assignments` ↔ `days[].slots`) — adding `reasoning` as an independent string field does NOT conflict with it.

After adding `reasoning` to `PlanComposeTreeInputSchema`:
- `PlanComposeTreeInputSchema.parse(input)` produces `parsed.reasoning` directly
- `plan.tools.ts` reads `parsed.reasoning` (no more `(input as { reasoning?: unknown })` cast)
- The 600-char truncation is now enforced by the schema itself (`.max(600)`) — the `rawReasoning.slice(0, 600)` line in `plan.tools.ts:74` becomes redundant; remove it
- `PlanComposeTreeOutputSchema.reasoning` remains as-is (still optional `z.string().max(600).optional()`)

### `toExternalName` encoding — critical for forced tool_choice

`plan.compose` → `plan__compose` (dots encoded as double underscores). This is done by `toExternalName()` at `openai.adapter.ts:79`. The forced `tool_choice` object must use the external name:

`toExternalName` throws if the internal name already contains `__` — ensure `forcedToolName` uses the canonical dotted form.
