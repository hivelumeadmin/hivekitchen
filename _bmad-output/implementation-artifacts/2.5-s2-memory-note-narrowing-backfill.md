## Story

As **the architect of HiveKitchen's onboarding data model**,
I want **the four deprecated `memory_nodes.node_type` values (`preference`, `cultural_rhythm`, `allergy`, `school_policy`) to be migrated into the structured signal tables from 2.5-s1, soft-forgotten in `memory_nodes`, and the enum narrowed in both the DB and contracts** — and **for `children.declared_allergens`, `children.dietary_preferences`, and `children.cultural_identifiers` JSONB columns to be backfilled into their corresponding structured tables** —
so that **every downstream Epic 2.5 slice (agent prompt v2, the five moment slices, the Kitchen Profile live read) operates against clean, non-ambiguous data shapes** — existing households' data is accessible via the structured arrays in the Kitchen Map rather than buried in unstructured prose — and the `memory.note` tool surface is unambiguously scoped to qualitative narrative only, eliminating agent confusion about when to reach for `memory.note` versus the structured tools.

This slice is **pure data migration + contract tightening: no user-facing change.** A fresh signup goes through the existing OnboardingText flow unchanged. The agent's tool surface after this slice is unchanged from 2.5-s1 (the new structured tools are still not exposed to OpenAI — that's 2.5-s4). The only observable outputs: migrations applied, backfill script run, contracts narrowed, `pnpm typecheck` + tests green.

## Acceptance Criteria

### AC1 — memory_nodes backfill: `cultural_rhythm` → `cultural_priors`

For every existing `memory_nodes` row with `node_type = 'cultural_rhythm'`:

1. Attempt to write a corresponding row to `cultural_priors`:
   - `key`: derive from `facet` — kebab-case the facet text, truncate to 64 chars (e.g., `facet='indian_cooking'` → key=`'indian_cooking'`).
   - `label`: first 128 chars of `prose_text`.
   - `state`: `'suggested'` — backfill rows are unratified; the household has not explicitly confirmed them.
   - `tier`: `'L3'` — cultural rhythms are culinary/cooking-pattern signals, not identity-level (L1) or religious (L2).
   - `confidence`: `50` — conservative default; narrative-derived signals are less precise than explicit declarations.
   - `presence`: `50` — same rationale.
   - `enforcement`: `'just_for_context'` — matches the shipped default for `cultural_priors.enforcement`.
   - `household_id`: from the source `memory_nodes.household_id`.
   - `source_provenance`: `'backfill_migration'` (if the cultural_priors table has a provenance column; otherwise carry in `source_ref` of the memory_provenance row).
   - Idempotency: skip if a row with the same `household_id` + `key` already exists (ON CONFLICT DO NOTHING).

2. After successfully writing (or skipping due to conflict), soft-forget the source `memory_nodes` row: set `soft_forget_at = now()` where `soft_forget_at IS NULL`. Do NOT overwrite an already-set `soft_forget_at`.

3. Write a `memory_provenance` row for the source memory node: `source_type = 'import'`, `source_ref = '{"migration":"2.5-s2","target_table":"cultural_priors","target_key":"<key>"}'::jsonb`, `captured_at = now()`, `confidence = 0.50`.

4. This backfill is **pure SQL** — `cultural_priors` is not encrypted. Run in the migration file `20260904000100_backfill_cultural_rhythm_to_cultural_priors.sql`.

### AC2 — memory_nodes backfill: `preference`, `allergy`, `school_policy` — soft-forget only

For rows with `node_type IN ('preference', 'allergy', 'school_policy')`:

- **No backfill write to a structured table.** These node_types contain free-text prose that cannot be reliably parsed into the structured schemas without LLM interpretation. Attempting automated extraction risks corrupt data in tables that downstream agents treat as authoritative.
  - `preference` prose (e.g., "Layla really dislikes mushrooms but will eat them in soup") cannot be reliably parsed into `food_preferences.item` + `.valence` without NLP.
  - `allergy` prose (e.g., "Aarav has a serious peanut allergy — always eats before school") contains narrative context; raw allergen tags live in `children.declared_allergens` (handled in AC5).
  - `school_policy` prose contains unstructured policy descriptions that require a human-interpreted schema mapping to `school_policies.policy_type` enum.

- **Action**: Set `soft_forget_at = now()` on these rows (idempotent — skip if already set). Write a `memory_provenance` row with `source_type = 'import'`, `source_ref = '{"migration":"2.5-s2","action":"soft_forget_no_backfill_target","reason":"<type>_prose_unstructured"}'::jsonb`.

- Run in `20260904000100` alongside the AC1 backfill, or in a separate `20260904000200` if simpler.

### AC3 — DB enum narrowing: `node_type` → `('rhythm', 'child_obsession', 'other')`

A SQL migration narrows the `node_type` Postgres enum (created in `20260601000000`) from 7 values to 3.

**Prerequisite:** AC1 and AC2 must have run before this migration. This migration includes a guard:

```sql
DO $$
DECLARE remaining_count integer;
BEGIN
  SELECT COUNT(*) INTO remaining_count
  FROM memory_nodes
  WHERE node_type IN ('preference','cultural_rhythm','allergy','school_policy')
    AND soft_forget_at IS NULL;
  IF remaining_count > 0 THEN
    RAISE EXCEPTION
      '2.5-s2 guard: % non-forgotten rows with deprecated node_types remain — run the backfill before this migration',
      remaining_count;
  END IF;
END $$;
```

After the guard passes, narrow the enum using the Postgres pattern:

```sql
-- Step 1: create the narrowed enum
CREATE TYPE node_type_v2 AS ENUM ('rhythm', 'child_obsession', 'other');

-- Step 2: convert column — deprecated values are already soft-forgotten; remap
-- any stragglers to 'other' as the safety fallback.
ALTER TABLE memory_nodes
  ALTER COLUMN node_type TYPE node_type_v2
  USING (
    CASE node_type::text
      WHEN 'rhythm' THEN 'rhythm'::node_type_v2
      WHEN 'child_obsession' THEN 'child_obsession'::node_type_v2
      WHEN 'other' THEN 'other'::node_type_v2
      ELSE 'other'::node_type_v2
    END
  );

-- Step 3: drop old enum, rename new to canonical name
DROP TYPE node_type;
ALTER TYPE node_type_v2 RENAME TO node_type;
```

Migration file: `supabase/migrations/20260904000300_narrow_node_type_enum.sql`.

**Index update**: The existing `memory_nodes_household_type_forgotten_idx` on `(household_id, node_type, hard_forgotten)` remains valid — Postgres rebuilds it automatically after the column type change. Verify with `\d memory_nodes` after applying.

### AC6 — JSONB backfill: `children.declared_allergens` → `child_allergens` table

For every `children` row with a non-null, non-empty `declared_allergens` JSONB column:

1. Decrypt the JSONB (AES-256-GCM via household DEK, same pattern as `kitchen-map.repository.ts` → `decryptAllergens`).
2. Parse the decrypted value as a JSON array of strings (allergen tag strings, e.g., `["peanut","tree_nut"]`).
3. For each allergen tag:
   a. Compute `normalizedHash(allergen_tag)` (SHA-256 of `lower(trim(tag))`).
   b. Check `child_allergens` for an existing row with `(child_id, allergen_hash)` — skip if exists.
   c. Encrypt the allergen tag via `encryptField(dek, allergen_tag)`.
   d. Insert into `child_allergens`: `(household_id, child_id, allergen=<ciphertext>, allergen_hash, source='backfill_migration')`.
4. This requires the household DEK — app-layer only; **cannot be done in pure SQL**.

**Implementation**: A TypeScript migration script at `scripts/migrations/2-5-s2-backfill.ts`. It runs against the Supabase database using the service-role key (same access pattern as the 2-s27 backfill script). Must be **idempotent** — safe to re-run; the `allergen_hash` unique index guarantees no duplicates.

**Scope**: `children.declared_allergens` only. `households.declared_allergens` is household-scoped (no child_id FK in `child_allergens`); it stays in the household JSONB column and is surfaced via `KitchenMapHouseholdSchema.declared_allergens` until a future Epic defines a household-allergen structured table.

### AC7 — JSONB backfill: `children.dietary_preferences` → `dietary_preferences` table

For every `children` row with a non-null, non-empty `dietary_preferences` JSONB column:

1. Decrypt (same AES-256-GCM pattern).
2. Parse as JSON array of dietary tag strings (e.g., `["vegetarian","dairy_free"]`).
3. For each tag:
   a. Check `dietary_preferences` table for existing `(household_id, child_id, tag)` — skip if exists (ON CONFLICT DO NOTHING via unique index on those three).
   b. Insert: `(household_id, child_id, tag, enforcement='default', source='backfill_migration')`. `enforcement='default'` is the correct default for children's dietary preferences declared during onboarding without an explicit strength signal.
4. `dietary_preferences.tag` is NOT encrypted — the table uses closed vocabulary (validated tags). Insert plaintext.

**Same script** as AC6 (`scripts/migrations/2-5-s2-backfill.ts`) — add a second pass after the allergen loop.

### AC8 — JSONB backfill: `children.cultural_identifiers` → `cultural_priors` table

For every `children` row with a non-null, non-empty `cultural_identifiers` JSONB column:

1. Decrypt (same pattern).
2. Parse as JSON array of cultural tag strings (e.g., `["south_indian","tamil"]`).
3. For each tag:
   a. Derive: `key = tag`, `label = tag` (humanize if a label mapping is available in vocabulary tables; otherwise use the tag as-is), `state = 'suggested'`, `tier = 'L2'`, `confidence = 80`, `presence = 70`, `enforcement = 'just_for_context'`.
   b. Check `cultural_priors` for existing `(household_id, key)` — skip if exists.
   c. Insert with `household_id` from the child's row.
4. Also backfill `households.cultural_identifiers` JSONB (same decrypt + loop; `state='active'` for household-level declarations, `confidence=90`, `tier='L1'` — household-level is more explicit than child-level).
5. NOT encrypted in `cultural_priors`.

**Same script**, third pass.

## Critical Guardrails — Read First

**DO NOT** narrow the enum (AC3) before the backfill (AC1, AC2) has soft-forgotten all deprecated rows. The AC3 migration includes a guard that enforces this — if the guard fires, stop and investigate.

**DO NOT** delete `memory_nodes` rows. The soft-forget pattern (`soft_forget_at = now()`) is the correct disposal — the nightly job promotes to hard-delete after 30 days, and the audit trail is preserved in `memory_provenance`.

**DO NOT** attempt to extract structured food preference data (`item` + `valence`) from `preference`-type memory node prose. The prose is qualitative narrative ("likes mushrooms in soup sometimes") — parsing it without an LLM introduces silent data corruption. Soft-forget only.

**DO NOT** attempt to extract structured allergen data from `allergy`-type memory node prose. The authoritative allergen source is `children.declared_allergens` (handled in AC6). Allergy memory nodes are narrative colour, not structured data.

**DO NOT** overwrite `soft_forget_at` on rows where it's already set (a prior run may have set it). Use `WHERE soft_forget_at IS NULL` in all UPDATE statements.

**DO NOT** change the `cultural_priors` state machine. Backfilled priors enter at `state='suggested'` — they require explicit ratification (slice 2.5-s7, or a future user action in Kitchen Profile) before becoming `active`. Never backfill with `state='active'`.

**DO NOT** modify or remove `children.declared_allergens`, `children.dietary_preferences`, `children.cultural_identifiers` columns. They are the LIVE READ source through Epic 2.5 — both columns and the new structured tables coexist. The columns are deprecated but not removed; removal happens in a post-Epic-2.5 cleanup slice.

**DO NOT** change the tool exposure in `createOnboardingToolSpecs` — the 4-tool set (`child.upsert`, `cultural.note`, `memory.note`, `household.upsert`) is unchanged. AC12.

**DO NOT** remove or modify the `createCulturalNoteToolSpec`, `createAllergenDeclareToolSpec`, or any of the 7 new stub factories added in s1. This slice touches `createMemoryNoteToolSpec` only (to remove the deprecation warn + update the description).

**DO NOT** bump `KitchenMapMetaSchema.schema_version` — the schema shape is unchanged in this slice. Only the enum narrows; the Kitchen Map's top-level field set, child projection, and meta fields are identical to 1.1.0.

## Open Questions for PM / Architect

### Q1 — `cultural_rhythm` → `cultural_priors`: key derivation from `facet`

The AC1 key derivation (`key = kebab-case(facet)`) is a best-effort approach. If `facet` values contain spaces, unicode characters, or punctuation, the derived key may be lossy.

**Option (a)**: Use `facet` directly as the key (raw, not kebab-cased), capped to 64 chars. Simpler, no transformation loss.
**Option (b)**: Kebab-case normalize: `lower(trim(facet)).replace(/[^a-z0-9_]+/g, '-').slice(0, 64)`. More slug-friendly for future vocabulary integration.

**Suggested resolution**: (b) — matches the cultural_templates vocabulary key convention. The dev agent confirms this against existing keys in the vocabulary tables before running.

### Q2 — households.cultural_identifiers: tier and state for backfill

AC8 proposes `state='active'` for household-level cultural identifiers. However, the current `KitchenMapCulturalSchema` only surfaces `active` and `suggested` priors (dormant/forgotten are excluded). If a household declared "south_indian" during onboarding (stored in `households.cultural_identifiers`), it should arguably be `active` since the household explicitly declared it.

**Concern**: Setting `state='active'` means the Kitchen Map will render these priors as "ratified" in the active bucket — before the household has explicitly gone through Moment 3 (s2.5-s7). This may cause the UI to show "south_indian: active" as if the household confirmed it in the new chaptered flow, when in fact it was a legacy onboarding declaration.

**Option (a)**: `state='suggested'` for both child and household cultural identifiers. Kitchen Profile renders them as "pending ratification." More conservative — avoids false impression of a ratified Moment 3.
**Option (b)**: `state='active'` for households, `'suggested'` for children. Household-level declaration is authoritative; child-level via `children.cultural_identifiers` is less explicit.

**Suggested resolution**: (a) — use `suggested` for all backfilled cultural_priors regardless of source. Ratification to `active` is the job of Moment 3 (s2.5-s7). Avoids UI confusion. **Architect should confirm before the dev agent writes the backfill.**

### Q3 — DB enum narrowing and any read-replicas / cached queries

Postgres enum narrowing via CREATE/RENAME involves a brief lock on `memory_nodes`. If the API is under load during the migration, queries touching `memory_nodes.node_type` may experience brief lock contention.

**Impact**: Low for current scale (the `node_type` index exists and queries are scoped to household_id). The migration should run during a low-traffic window.

**Mitigation**: The backfill (000100) can run any time without downtime concerns. Only the enum narrowing (000300) requires a maintenance window or low-traffic deploy. Document in the PR.

**No decision needed** — this is an operational note for whoever manages the deploy. The dev agent documents it in the PR description.

### Q4 — scripts/migrations/ directory and CI

The backfill script at `scripts/migrations/2-5-s2-backfill.ts` runs manually, not as part of the automated Supabase migration pipeline. Should it be run in CI against a test database?

**Option (a)**: Manual only — documented in the deploy runbook. CI doesn't run it.
**Option (b)**: Add a CI step that runs the script against the ephemeral test DB after `db:reset`, validates exit code 0, checks that the summary shows non-zero inserts.

**Suggested resolution**: (a) for this slice — CI integration of backfill scripts has no precedent in the project yet. (b) can be added as a follow-up if the team adopts a policy. The dev agent uses (a); documents it clearly in the PR.
