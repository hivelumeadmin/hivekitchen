## Summary

2.5-s6 introduced `ChildAllergensRepository.declare()` as the canonical per-child allergen write path, with an explicit comment that the cutover of the **read** path was "deferred to a later slice." 2.6-s7 closed the FALCPA-baseline half by switching the guardrail to read FALCPA from `allergen_tags`. This slice closes the symmetric per-child half:

1. **Backfill** any legacy `children.declared_allergens` JSONB entries into `child_allergens` rows with `source='backfill_migration'`.
2. **Redirect every live writer** of per-child allergens to `ChildAllergensRepository.declare()`. After this slice, the legacy column is written by nothing.
3. **Cut over the guardrail read** to `child_allergens` only. After this slice, the legacy column is read by nothing safety-critical.
4. **Cut over the kitchen-map read** to `child_allergens` only for allergens (cultural_identifiers and dietary_preferences stay on legacy column — different cutover scope).

The legacy `children.declared_allergens` column becomes a zombie after this slice. A separate follow-up story can drop it once the kitchen-map's other JSONB columns have similar cutovers.

---

## Context and Motivation

After 2.5-s6 shipped, allergens declared during Epic 2.5 onboarding via `allergen.declare` land in `child_allergens`. The allergy guardrail still reads `children.declared_allergens` JSONB. FALCPA top-9 are unaffected because they're handled by the engine baseline regardless of declaration. But any **non-FALCPA** per-child allergen (kiwi, mustard, sulfite, sesame extensions — all from `20260902000400_expand_allergen_vocabulary.sql`) declared via 2.5 onboarding is invisible to the guardrail. Plans clear as safe when they should be blocked.

Blast radius: beta-only households that finished 2.5 onboarding and declared a non-FALCPA allergen for a specific child. Small absolute volume, but the safety contract is "no allergic exposure in cleared plans" — even one missed declaration is a contract violation.

Pre-2.5 households with legacy `children.declared_allergens` entries also need to keep working. The backfill ensures their data is present in `child_allergens` before the read cutover, so they remain protected.

## Acceptance Criteria

### AC1 — Backfill: legacy `children.declared_allergens` → `child_allergens`

A one-shot script `apps/api/scripts/backfill-child-allergens.ts` scans every household, decrypts each child's legacy `children.declared_allergens` JSONB array under the household DEK, and calls `ChildAllergensRepository.declare(householdId, childId, allergen, 'backfill_migration')` for each entry.

- Idempotent: re-running the script is a no-op (UNIQUE on `(child_id, allergen_hash)`).
- Pagination: 100 households per page to keep memory bounded. Pattern matches `apps/api/scripts/backfill-household-food-identity.ts`.
- Per-household decrypt failure logs and continues (operator re-runs after fixing) — same accept-and-continue posture as `backfill-household-food-identity.ts`.
- Final summary log includes `{ households_scanned, children_scanned, allergens_migrated, skipped_existing, decrypt_failures }` via `console.log` (consistent with the existing backfill-script precedent; Pino requires Fastify context the script doesn't have).

The script does NOT delete or null the legacy `children.declared_allergens` column. The column is left in place; subsequent slices (out of scope) deprecate it.

### AC2 — `child.upsert` tool routes `declared_allergens` to `ChildAllergensRepository`

In `apps/api/src/agents/tools/onboarding.tools.ts`, the `child.upsert` tool currently routes its `declared_allergens` field through `ChildrenService.upsertByName({ ..., declared_allergens })`, which writes to the legacy encrypted JSONB column.

After this slice:
- `ChildrenService.upsertByName()` no longer accepts a `declared_allergens` field, OR accepts it and routes it to `ChildAllergensRepository.declare()` instead of the legacy column.
- The unknown-allergen partition logic at `onboarding.tools.ts:111-128` is preserved — only known vocabulary keys are accepted; unknowns produce a memory-note via the existing `memory.note` tool surface.
- A child created via `child.upsert` with a `declared_allergens` array results in one row per allergen in `child_allergens` with `source='onboarding_declared'`.

Decision: do not remove the `declared_allergens` field from the `child.upsert` tool input schema. Some agent prompts (older 2.5-s5 path) may still send it. Keep the input, redirect the storage.

### AC3 — REST `POST/PATCH /v1/children` routes `declared_allergens` to `ChildAllergensRepository`

In `apps/api/src/modules/children/children.repository.ts`, `create()` and `update()` currently encrypt `declared_allergens` and write to the legacy column. After this slice:
- The repository methods continue to accept `declared_allergens: string[]` in their input contract (no breaking change for callers).
- Instead of `update.declared_allergens = encryptField(...)`, the methods invoke `ChildAllergensRepository.declare(householdId, childId, allergen, source)` per allergen.
- `source` is `'parent_edited'` for any update path that comes through REST (the closest enum value from `child_allergens.source` CHECK constraint — see `20260903000100`). For initial child creation via REST, `source` is `'onboarding_declared'` (parent created a child outside the agent flow but during initial onboarding).
- The legacy column is set to encrypted `[]` on insert (so the column shape remains valid for any code path that still reads it during the transition).

### AC4 — `AllergyGuardrailRepository.getRulesForHousehold()` reads `child_allergens` only

In `apps/api/src/modules/allergy-guardrail/allergy-guardrail.repository.ts`:
- Remove the legacy per-child decrypt block (the `for (const row of childStoredRows) { ... decryptArray(row.declared_allergens, ...) }` loop).
- Add a parallel query for `child_allergens` rows scoped to the household.
- Decrypt each `child_allergens.allergen` ciphertext under the household DEK using `decryptField<string>`.
- Convert each row into a `parent_declared` `AllergyRule` with `child_id = row.child_id`.
- An undecryptable cell throws `AllergyGuardrailDecryptError` (fail-closed, same semantics as the existing legacy path — NOT the skip-and-log pattern used by `kitchen-map.repository.ts`).
- The household-wide read of `households.declared_allergens` is **unchanged** — household-level allergens are out of scope for this slice (no equivalent structured table exists; `households.declared_allergens` JSONB + advisory-lock writes remain the canonical path).

### AC5 — Kitchen-map allergen read cuts over

`apps/api/src/modules/kitchen-map/kitchen-map.repository.ts` already queries `child_allergens` in parallel (line ~314, slice 2.5-s11). It also decrypts `declared_allergens` from the legacy `children` column inside `decryptChildren()`. After this slice:
- `decryptChildren()` stops decrypting `declared_allergens` from the legacy column (it remains in the SELECT for the field to stay non-null-shaped, but the value is ignored; or the field is removed from `CHILD_COLUMNS` entirely if the row reader is updated accordingly).
- The composer's `RawChildRow.declared_allergens` is populated from the `child_allergens` query rows (already-fetched), grouped by `child_id`.
- `cultural_identifiers` and `dietary_preferences` continue to be decrypted from the legacy column — this slice does NOT touch those.

The simplest implementation: build a `Map<child_id, string[]>` from the `child_allergens` query results and replace the legacy decryption call inside the child-row build loop. Less invasive than restructuring `decryptChildren()`.

### AC7 — Deploy ordering note

The cutover is sequenced:
1. Apply migration `20260903000100_create_child_allergens_table.sql` (already shipped in 2.5-s1; no-op here, just confirm).
2. Deploy code that writes to both legacy AND `child_allergens` — **not done in this slice** (this slice goes straight to single-target writes). Operator runs the backfill before code deploy.
3. Run the backfill script (`apps/api/scripts/backfill-child-allergens.ts`).
4. Deploy code that reads from `child_allergens` only and writes to `child_allergens` only.

Pre-deploy verification step in the operator runbook: after backfill completes, run `SELECT COUNT(*) FROM child_allergens WHERE source='backfill_migration'` and compare against the script's `allergens_migrated` counter. They must match.

A row in `_bmad-output/implementation-artifacts/deferred-work.md` documents the dual-write-skip decision and the resulting deploy order requirement. If a future story revisits this and wants a zero-coordination deploy, dual-write is the next step.

### T1 — Backfill script

New file: `apps/api/scripts/backfill-child-allergens.ts`. Pattern after `apps/api/scripts/backfill-household-food-identity.ts`.

```typescript
// Pseudocode shape
async function main() {
  const supabase = createServiceRoleClient(env);
  const kek = await loadKek(env);
  const summary = { households_scanned: 0, children_scanned: 0, allergens_migrated: 0, skipped_existing: 0, decrypt_failures: 0 };
  for await (const householdPage of paginateHouseholds(supabase, 100)) {
    for (const household of householdPage) {
      summary.households_scanned++;
      const dek = await getHouseholdDek(supabase, kek, household.id);
      const { data: children } = await supabase.from('children').select('id, declared_allergens').eq('household_id', household.id);
      const repo = new ChildAllergensRepository(supabase, kek);
      for (const child of children ?? []) {
        summary.children_scanned++;
        if (child.declared_allergens === null) continue;
        let allergens: string[];
        try {
          allergens = decryptField<string[]>(child.declared_allergens, dek);
        } catch (err) {
          summary.decrypt_failures++;
          console.error(`[backfill] decrypt failed: household=${household.id} child=${child.id}`, err);
          continue;
        }
        for (const allergen of allergens) {
          const { was_existing } = await repo.declare(household.id, child.id, allergen, 'backfill_migration');
          if (was_existing) summary.skipped_existing++; else summary.allergens_migrated++;
        }
      }
    }
  }
  console.log('[backfill] summary:', summary);
}
```

async findByHousehold(householdId: string): Promise<Array<{ child_id: string; allergen: string }>> {
  const { data, error } = await this.client
    .from('child_allergens')
    .select('child_id, allergen')

## Dev Notes

### Why no dual-write transition

A safer cutover pattern is: deploy dual-write (write to both legacy AND new), then backfill, then read cutover. This slice skips the dual-write phase because:
- Beta-only data volume; backfill is small and fast.
- Pre-2.5 households are a small set; pre-deploy backfill closes the gap.
- The deploy is sequenced (backfill before code deploy) so the read-cutover never lands before its data does.

If the user count grows before this slice ships, revisit and add a dual-write phase.

### Why `households.declared_allergens` is NOT migrated here

Household-wide allergens are written through `HouseholdsService.addAllergens()` under a Postgres advisory lock that serialises concurrent agent turns. There is no `household_allergens` structured table; the column IS the canonical store. The guardrail reads it directly. No symmetric cutover work needed.

Future work (out of scope): a `household_allergens` structured table to mirror the per-child model. Not required by any current epic. Tracked in deferred-work.

### Why backfill writes `source='backfill_migration'`

The `child_allergens.source` CHECK constraint includes `'backfill_migration'` precisely for this case (see `20260903000100`). Auditability — operator can run `SELECT child_id, count(*) FROM child_allergens WHERE source='backfill_migration' GROUP BY child_id` to see exactly which children have backfilled vs. natively-onboarded allergens.

### Why fail-closed on guardrail decrypt vs. fail-open on backfill decrypt

Different failure modes:
- **Backfill**: operator-driven. A decrypt failure means investigate and re-run. Skip-and-log doesn't compromise safety — the legacy column still has the data, the operator fixes the DEK or the row, and re-runs the script.
- **Guardrail read**: serves an active plan-clearance decision. A silent decrypt failure could clear a plan containing an undisclosed allergen. Must fail-closed → `AllergyGuardrailDecryptError` → `verdict='uncertain'` → no clearance.

### What this story does NOT do

- Does NOT drop the legacy `children.declared_allergens` column. The column persists, written with `[]` on new rows. A separate slice handles drop.
- Does NOT touch `households.declared_allergens` or its read/write paths.
- Does NOT migrate `cultural_identifiers` or `dietary_preferences` columns on `children`. Different cutovers; out of scope.
- Does NOT change the on-wire contract of `POST/PATCH /v1/children` or the `child.upsert` tool input schema. `declared_allergens` field stays; storage location moves.

### Design choices and deviations from spec

- **Repository-level cutover (T4 style) over service-level orchestration (T3 style)** — `ChildrenRepository.insert` / `updateProfile` own the dual operation: write `encryptField([], dek)` to the legacy column AND fan `declared_allergens` into `child_allergens` via the new `ChildAllergensRepository.declareIfNew()`. The tool layer (`onboarding.tools.ts child.upsert`) doesn't iterate — it still passes `declared_allergens` through `ChildrenService.upsertByName`. AC2 + AC3 are satisfied because `source` is contextual: insert → `'onboarding_declared'` (matches AC2's "created via child.upsert"), updateProfile → `'parent_edited'` (matches AC3).
- **New helper `ChildAllergensRepository.declareIfNew()`** — added alongside the existing `declare()`. Uses `ignoreDuplicates: true` so re-mentions across multiple `child.upsert` turns don't overwrite an already-existing row's `source` (would have downgraded `'onboarding_declared'` to `'parent_edited'` on a duplicate declare). `declare()` is kept intact for the per-call `allergen.declare` tool which needs `was_existing` semantics.
- **Legacy column read fully discarded** — `ChildrenRepository.decryptRow` no longer decrypts `row.declared_allergens`; it always emits `[]`. Callers (insert/updateProfile/findById/findByHouseholdId) overlay the canonical value from `child_allergens`. This eliminates a spurious decrypt failure mode if a pre-2.6-s8 row hasn't been touched by the backfill yet.
- **Backfill script tests required a vitest config tweak** — `scripts/` was excluded from `include`. Added `'scripts/**/*.test.ts'` so the new tests run with the rest of the suite. Existing precedent (`backfill-household-food-identity.ts`) had no tests; 2.6-s8 sets a higher bar per AC6.
