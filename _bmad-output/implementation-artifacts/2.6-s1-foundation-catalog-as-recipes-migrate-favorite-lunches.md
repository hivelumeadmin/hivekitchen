## Story

As a **HiveKitchen developer**,
I want to **migrate the standalone `favorite_lunches` table into the existing `recipes` + `household_recipe_usage` infrastructure (shipped by story 3-31) with a new `catalog_provenance` column, swap the Kitchen Profile starting-line read in-slice, and drop `favorite_lunches`**,
so that **the M5 lunch catalog stops being a parallel-store anti-pattern and becomes a single source of truth that the planner (Epic 3), the swap surface (story 3-32), and the M5 chip card (slice 2.6-s4) all consume from one shape**.

## Acceptance Criteria

**AC1 — Schema extensions land cleanly.**
- New column `household_recipe_usage.catalog_provenance` (NOT NULL, CHECK enum) with values: `'declared'` / `'inferred'` / `'parent_added'` / `'plan_promoted'`. Default `'plan_promoted'` for backfill of existing rows.
- Extended CHECK on `recipes.source` accepts: `'agent_generated'` / `'curated'` / `'imported'` / `'catalog_seeded'` / `'parent_declared'`.
- Migration runs idempotently in dev + staging via `pnpm --filter @hivekitchen/api db:migrate`.

**AC2 — Migration of live `favorite_lunches` rows is atomic per source row.**
For each row in `favorite_lunches`:
1. Decrypt `item` ciphertext using the household's DEK (envelope-encryption pattern; same key the existing `FavoriteLunchesRepository` uses for read).
2. In a single transaction:
   - INSERT into `recipes` with `source='parent_declared'`, `visibility='private'`, `created_by_household_id=<household_id>`, `canonical_name=<plaintext>`, `ingredients='[]'::jsonb`, `ingredient_keys='{}'::text[]`, `allergen_flags='{}'::text[]`, `applicable_slots=ARRAY['main']::text[]`. If `(household_id, normalized canonical_name)` UNIQUE conflict (item already created by Stage 0/1 in a parallel-running deploy), **reuse the existing `recipes.id`** instead of inserting; do not error.
   - INSERT into `household_recipe_usage` with `household_id`, `recipe_id`, `catalog_provenance='declared'`, `is_household_favorite=true`, `confidence_score=80`, `first_used_at=<favorite_lunches.created_at>`, `last_used_at=<favorite_lunches.created_at>`.
3. On any row failure outside `42P10`/`23505`-with-recovery: transaction rolls back BOTH writes; row is left in `favorite_lunches` and logged.

**AC3 — Decryption-failure handling.**
Per-row try/catch around DEK decryption. On failure: log structured event `migration.favorite_lunches.decrypt_failed` with `{ household_id, row_id, error_class }` (NEVER the plaintext attempt or ciphertext). Quarantine the row (do not migrate). Continue with next row. **Abort the entire migration only if `>5%` of rows fail decryption.** Quarantined rows remain in `favorite_lunches` until explicitly triaged; the table drop in AC8 is gated on zero quarantined rows OR explicit ops sign-off (manual flag).

**AC4 — Encryption-drop security checkpoint.**
Slice spec carries an explicit note: *"plaintext `recipes.canonical_name` + RLS + `visibility='private'` threat model reviewed and accepted (or deferred per brief Section 3)."* If deferred, link to a follow-up issue. Do not ship without this checkpoint visibly captured in the PR description or commit body.

**AC5 — Agent tool refactor.**
`favorite_lunch.add` tool (currently at `apps/api/src/agents/tools/onboarding.tools.ts`) is refactored to `recipe.declare(label, provenance='declared')` (or equivalent — keep the existing name if migration cost is high, but its body MUST now write to `recipes` + `household_recipe_usage` instead of `favorite_lunches`). M5 hot path stays functional: tapping a chip / typing a lunch in the M5 turn writes through the tool and the new state is read by the Kitchen Profile.

**AC6 — Kitchen Map composer projection swap.**
`apps/api/src/modules/kitchen-map/kitchen-map.composer.ts`:
- Delete `projectFavoriteLunches` and its `favorite_lunches` source query in the repository.

## Dev Notes

### Why this slice exists

`2.5-s9` shipped `favorite_lunches` as an encrypted-text standalone table for M5 cold-start seeding. Two weeks earlier `3-31` had shipped `recipes` + `household_recipe_usage` — a more capable, GIN-indexed, planner-aware infrastructure with confidence scoring, favorite/banned flags, and per-household engagement counters. The two were authored independently; the catalog UX spec finalized 2026-05-23 made the redundancy explicit. This slice folds `favorite_lunches` into the older, more capable infrastructure.

**See:** Epic 2.6 brief §1 (Issue Summary) for the full architectural-collision narrative.

### Two-layer model (architectural commitment)

Epic 2.6 commits to a two-layer model where lunch items have a lightweight "suggestable idea" representation (Layer 1: name + tags; emitted by Stage 1 LLM seeding in slice `2.6-s3`) and a heavyweight "structured recipe" representation (Layer 2: full ingredients + instructions; materialized lazily via `RecipeAgent.discover()` at plan-commit time, reusing 3-31's existing flow).

**This slice (`2.6-s1`) is the data-shape foundation only.** It does NOT introduce Stage 1 LLM seeding (that's `2.6-s3`) or the Layer 2 trigger integration in `PlansService.commit()` (also `2.6-s3`). It just makes the table shapes ready.

### Encryption decision (resolved)

The 2.5-s9 choice to encrypt `favorite_lunches.item` is **reversed in this slice** in favor of plaintext `recipes.canonical_name` + RLS + `visibility='private'`. Rationale documented in Epic 2.6 brief §3 "Encryption decision."

**Threat model:** A DB-read-without-DEK attacker would see `"biryani"` or `"Mama's special pasta"` in plaintext. Acceptable because (a) RLS + `visibility='private'` + `created_by_household_id` prevent cross-household reads, (b) the same attacker can already see `children.declared_allergens` (encrypted but cross-table-joinable), (c) the existing `recipes` table has been in production for ~3 weeks via story 3-31 with this pattern — Epic 2.6 just brings the M5 catalog into pattern consistency.

**Reversibility:** If a future security review flags this, add an encrypted-variant column `canonical_name_encrypted` for `visibility='private'` rows; switch reads to that variant when present. No schema-shape change required.

### Established patterns to follow (from previous slices)

**From `2.5-s1` (Foundation slice that birthed `favorite_lunches`):**
- Idempotency on hash-based unique indices: PostgreSQL `42P10` (functional-index conflict) recovery path. The current `favorite_lunches` repository uses `insert → 23505 → SELECT` fallback (see `apps/api/src/modules/favorite-lunches/favorite-lunches.repository.ts`). The new `recipes` INSERT in this slice uses the SAME pattern via the new normalization unique index (Task 2).
- All migrations land via `supabase/migrations/`; rollback comments at the top of each.

**From `2.5-s11` (Kitchen Profile read live data — the read path this slice swaps):**
- The Kitchen Profile starting-line card reads from `kitchen_map.favorite_lunches` projection. This slice changes the WRITE source (recipes+household_recipe_usage) but keeps the projection shape intact — the UI doesn't change.
- See `_bmad-output/implementation-artifacts/2.5-s11-kitchen-profile-read-live-data.md` for the reference implementation.

**From `3-31` (Recipe Agent — Tavily structured fetch):**
- `recipes` + `household_recipe_usage` schema is in `supabase/migrations/20260820000200_create_recipes_and_usage.sql`. Read this file before writing migrations — the patterns (GIN indexes, RLS policies, the version-bump trigger on `household_recipe_usage` for stable-flag flips only) are non-obvious and must be preserved.
- The `recipes.canonical_name` is plaintext (RLS-gated); the existing pattern this slice extends.

### Anti-patterns to avoid

- **Do not** keep `favorite_lunches` around as a "for now we'll dual-write" — the brief explicitly commits to dropping it. Dual-write creates synchronization risk and is the parallel-store anti-pattern the slice exists to eliminate.
- **Do not** introduce a new `lunch_catalog` table. The earlier Epic 2.6 brief rev 1 proposed this; rev 2 explicitly rejected it after schema review. The catalog IS `recipes` + `household_recipe_usage`.
- **Do not** encrypt the new `recipes.canonical_name` rows. Plaintext + RLS is the established pattern in production from story 3-31.
- **Do not** add the `catalog_provenance` column to `recipes`. It belongs on `household_recipe_usage` (a recipe can be `declared` in one household and `inferred` in another).
- **Do not** Layer-2-materialize (call `RecipeAgent.discover()`) in this slice. That's the integration point added in `2.6-s3`. This slice's `recipes` rows have `ingredients=[]` and that's correct.

### Edge cases captured during readiness check (must be handled)

From the `bmad-review-edge-case-hunter` pass and folded into the brief rev 3 ACs:

| Edge case | AC reference | Handling |
|---|---|---|
| Migration atomicity per source row | AC2 | Single transaction per source row; failure rolls back both writes |
| `recipes` UNIQUE conflict (parallel create from Stage 1) | AC2 | Reuse existing `recipes.id`; INSERT only `household_recipe_usage` |
| Corrupt ciphertext on a single `favorite_lunches` row | AC3 | Per-row try/catch; quarantine; abort whole migration only if >5% failure rate |
| Rollback script semantics in forward-deployed Supabase | AC8 | Separate rollback SQL re-creates table + re-encrypts; tested in dev |
| Encryption-drop security review | AC4 | Explicit PR-description / code-comment checkpoint |

## Review Findings

_Code review 2026-05-24 (pass 2 — independent 3-layer adversarial review). 6 decisions needed, 10 patches, 3 deferred, 9 dismissed._

### Decision-Needed

- [ ] [Review][Decision] **AC2 atomicity: supabase-js compensation vs true transaction** — The spec says "single transaction per source row" but the implementation acknowledges supabase-js exposes no multi-statement transactions and uses write-ordering + compensation (DELETE the fresh recipe row if usage INSERT fails). The compensation path is documented but not a true rollback guarantee — a process crash between INSERT and compensating DELETE leaves an orphan `recipes` row. Decision: accept the compensation approach as written (document orphan-recovery path in ops runbook), or wrap both writes in a Postgres RPC? [confirmed by all 3 review layers]

- [ ] [Review][Decision] **Position wrong for idempotent re-declarations in `favorite_lunch.add`** — After `declareForHousehold` returns with `usageWasExisting=true`, `countDeclaredFavorites` still returns the same count (unchanged), so `Math.max(0, declaredCount - 1)` emits the last item's position rather than the re-declared item's actual position. Also two concurrent calls can receive the same position value. Decision: is a wrong position on re-declaration acceptable (spec says "idempotent = no-op"), or should the tool return the item's current position in the sorted projection? [`apps/api/src/agents/tools/onboarding.tools.ts:795-798`]

- [ ] [Review][Decision] **Quarantined rows in `migrate-favorite-lunches.ts` are permanently unretriable** — Quarantined rows (DEK decryption failed) get `migration_status='quarantined'` and the query filters only `'pending'` rows. There is no mechanism to reset them to `'pending'` for retry without manual SQL. If a transient KMS/DEK failure quarantined rows that would decrypt on re-run, they are permanently stuck. Decision: add a `--reset-quarantined` CLI flag to the migration script, or document it as ops-manual-SQL only? [`apps/api/scripts/migrate-favorite-lunches.ts:358`]

- [ ] [Review][Decision] **AC3 abort threshold: undocumented ≥20 row minimum window** — The spec says "Abort the entire migration only if >5% of rows fail decryption." The implementation adds `DECRYPT_FAIL_MIN_PROCESSED = 20` — the abort never fires until at least 20 rows are processed. A batch where the first 19 rows all fail decryption would not abort. The minimum is reasonable defensive engineering but deviates from the spec as written. Decision: accept the warm-up window as an implementation detail, or align spec/code? [`apps/api/scripts/migrate-favorite-lunches.ts:374`]

- [ ] [Review][Decision] **AC8 rollback script is a DDL stub — data re-encryption deferred to an operator note** — The spec says the rollback script "copies records back (re-encrypting canonical_name via household DEK)." The actual rollback SQL only re-creates the table schema and leaves re-encryption to an operator note comment. A DDL-only rollback provides false confidence in an incident; no executable recovery path exists to test against a representative dataset (AC8 gate). Decision: accept the DDL stub + operator runbook as sufficient for prod safety, or implement the application-layer re-encryption script now? [`supabase/migrations/20260908000300_2_6_s1_drop_favorite_lunches.rollback.sql`] [confirmed by Acceptance Auditor]

- [ ] [Review][Decision] **`parsed.position` accepted from agent input but not persisted** — `FavoriteLunchAddInputSchema` accepts an optional `position` field, but the new tool body never passes it to `declareForHousehold` (there is no position column on `household_recipe_usage`). Position is instead derived post-hoc from `countDeclaredFavorites`. An agent-supplied position is silently discarded even though the output returns a position value. Decision: remove `position` from the input schema (breaking change to agent contract) OR document that caller-supplied position is advisory only and used as a fallback when count-derived position is unavailable? [`apps/api/src/agents/tools/onboarding.tools.ts:800`, `packages/contracts/src/onboarding-tools.ts` — FavoriteLunchAddInputSchema]

### Patches

- [ ] [Review][Patch] **Normalization mismatch: UNIQUE index strips hyphens/apostrophes; ilike fallback does not** — SQL index uses `regexp_replace(lower(name), '[\s\-'']+', '', 'g')` (strips ALL whitespace, hyphens, apostrophes). App normalization uses only `trim().normalize('NFC')`. A first call with `"dal-chawal"` stores that canonical_name; a second call with `"dal chawal"` triggers a 23505 conflict, but `.ilike('canonical_name', 'dal chawal')` won't find `"dal-chawal"` → throws "UNIQUE conflict but no row found" error and permanently breaks that household-label pair. Fix: apply the same stripping in TypeScript before the ilike fallback lookup (or query via the SQL function). Same bug in both `declareForHousehold` and `findOrInsertRecipe`. [`apps/api/src/modules/recipe/recipes.repository.ts:231-242`, `apps/api/scripts/migrate-favorite-lunches.ts:133-152`] [confirmed by all 3 review layers]

- [ ] [Review][Patch] **`insertUsage.error` (root cause) is lost when rollback DELETE also fails** — In `declareForHousehold`, when `usageCode !== '23505'` and the cleanup `DELETE` also errors, `throw del.error` discards the original `insertUsage.error`. Caller receives a misleading delete-failure error and the recipe row is orphaned. Fix: always `throw insertUsage.error`; log `del.error` separately when non-null. [`apps/api/src/modules/recipe/recipes.repository.ts:265-269`] [confirmed by Blind Hunter + Edge Hunter]

- [ ] [Review][Patch] **Infinite loop: `processOne` returning `'failed'` leaves row as `'pending'`, re-fetched every batch** — Steps 2/3/4 in `processOne` return `'failed'` without setting `migration_status='quarantined'`. The main loop re-queries `migration_status='pending'`, so a permanently-failing row (e.g. normalization mismatch) is re-fetched on every iteration, looping forever. Fix: quarantine rows after N consecutive failures, or promote `'failed'` to `'quarantined'` after first failure. [`apps/api/scripts/migrate-favorite-lunches.ts:258-323`] [confirmed by all 3 layers]

- [ ] [Review][Patch] **`failed` row count excluded from quarantine-rate abort threshold** — The abort gate divides `summary.quarantined / summary.total`. Rows that fail at `findOrInsertRecipe` or `upsertUsageDeclared` land in `summary.failed`, not `summary.quarantined`. A DB outage can accumulate many `failed` rows without triggering the 5% gate; the migration completes "successfully" with most rows unmigrated. Fix: include `failed` in the rate denominator, or add a separate `failed`-rate abort gate. [`apps/api/scripts/migrate-favorite-lunches.ts:368-393`] [confirmed by Blind Hunter + Acceptance Auditor]

- [ ] [Review][Patch] **`declareForHousehold` UPDATE on re-declare omits `confidence_score: 80`** — On 23505 conflict recovery, the UPDATE only sets `catalog_provenance='declared'` and `is_household_favorite=true`. If the planner previously promoted this recipe with `confidence_score=30`, a parent's explicit M5 declaration will not raise it to 80. The lower confidence score may prevent the item from appearing in `recipes.favourites` context sent to the planner. Fix: add `confidence_score: 80` to the UPDATE. [`apps/api/src/modules/recipe/recipes.repository.ts:273-281`] [confirmed by Blind Hunter + Edge Hunter]

- [ ] [Review][Patch] **Drop migration not gated: `DROP TABLE IF EXISTS favorite_lunches` runs unconditionally** — AC8 requires the drop to be gated on zero quarantined rows or explicit ops sign-off. The migration applies the drop regardless, permanently destroying any rows still in `pending` or `quarantined` state. Fix: add a `DO $$ BEGIN IF (SELECT COUNT(*) FROM favorite_lunches WHERE migration_status IN ('pending','quarantined')) > 0 THEN RAISE EXCEPTION '...'; END IF; END $$` guard before the DROP. [`supabase/migrations/20260908000200_2_6_s1_drop_favorite_lunches.sql`] [confirmed by all 3 layers]

- [ ] [Review][Patch] **`household_recipe_usage` INSERT in `declareForHousehold` and `upsertUsageDeclared` omits `use_count`** — The sibling method `upsertUsageIncrement` always passes `use_count: 1`. If `use_count` has `NOT NULL` without a DB default, this INSERT will fail with a 23502 (null violation), hitting the non-23505 error path and triggering the recipe-row rollback. Fix: add `use_count: 0` to both INSERTs (a declared item has not yet been used in a plan). Verify the column default in the live schema. [`apps/api/src/modules/recipe/recipes.repository.ts:249-258`, `apps/api/scripts/migrate-favorite-lunches.ts:162-171`]

- [ ] [Review][Patch] **NULLS LAST sort inverted in `projectFavoriteLunchesFromUsage`** — The sort coerces `null last_used_at` to `''` and compares via `localeCompare`. Empty string sorts lexicographically before any ISO timestamp, so in descending order (`bTs.localeCompare(aTs)`) a null row sorts FIRST — meaning freshly-declared items with no `last_used_at` float to the top instead of the bottom. AC7 specifies `last_used_at DESC NULLS LAST`. Fix: treat null as a min-value sentinel (`null → '0000-01-01T00:00:00Z'`) so it always sorts last. [`apps/api/src/modules/kitchen-map/kitchen-map.composer.ts:352-356`] [confirmed by all 3 review layers — new finding]

- [ ] [Review][Patch] **Kitchen map cache not invalidated when `catalog_provenance` changes but `is_household_favorite` was already true** — The `bump_kitchen_map_from_recipe_usage` trigger only fires when `is_household_favorite` or `is_household_banned` change. If the planner previously set `is_household_favorite=true` on a `plan_promoted` row, a subsequent `declareForHousehold` call flips only `catalog_provenance` to `'declared'`; the trigger does not fire. The `favorite_lunches` projection changes (the item now qualifies even without the favourite flag), but the kitchen map cache version is NOT bumped. Fix: either include `catalog_provenance` in the trigger's NEW vs OLD comparison, or add a manual version bump in `declareForHousehold` after the UPDATE. [`apps/api/src/modules/recipe/recipes.repository.ts:270-282`] [new finding — Edge Hunter]

- [ ] [Review][Patch] **Migration UPDATE-conflict path does not preserve `first_used_at` from `favorite_lunches.created_at`** — AC2 specifies `first_used_at=<favorite_lunches.created_at>` for the INSERT path. On a 23505 conflict in `upsertUsageDeclared`, the UPDATE sets only `catalog_provenance` and `is_household_favorite`; the existing row's `first_used_at` (set by the planner) is left unchanged. The historical signal ("parent first declared this in onboarding at time T") is lost. Fix: add `first_used_at` to the UPDATE with a `LEAST(existing, row.created_at)` via a separate SELECT, or document that the planner timestamp takes precedence. [`apps/api/scripts/migrate-favorite-lunches.ts:180-188`] [new finding — Blind Hunter + Edge Hunter]
