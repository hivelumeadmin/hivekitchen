## Story

As a **HiveKitchen developer**,
I want to **migrate the standalone `favorite_lunches` table into the existing `recipes` + `household_recipe_usage` infrastructure (shipped by story 3-31) with a new `catalog_provenance` column, swap the Kitchen Profile starting-line read in-slice, and drop `favorite_lunches`**,
so that **the M5 lunch catalog stops being a parallel-store anti-pattern and becomes a single source of truth that the planner (Epic 3), the swap surface (story 3-32), and the M5 chip card (slice 2.6-s4) all consume from one shape**.

## Acceptance Criteria

**AC1 — Schema extensions land cleanly.**
- New column `household_recipe_usage.catalog_provenance` (NOT NULL, CHECK enum) with values: `'declared'` / `'inferred'` / `'parent_added'` / `'plan_promoted'`. Default `'plan_promoted'` for backfill of existing rows.
- Extended CHECK on `recipes.source` accepts: `'agent_generated'` / `'curated'` / `'imported'` / `'catalog_seeded'` / `'parent_declared'`.
- Migration runs idempotently in dev + staging via `pnpm --filter @hivekitchen/api db:migrate`.

**AC2 — Migration of live `favorite_lunches` rows is atomic per source row.**
For each row in `favorite_lunches`:
1. Decrypt `item` ciphertext using the household's DEK (envelope-encryption pattern; same key the existing `FavoriteLunchesRepository` uses for read).
2. In a single transaction:
   - INSERT into `recipes` with `source='parent_declared'`, `visibility='private'`, `created_by_household_id=<household_id>`, `canonical_name=<plaintext>`, `ingredients='[]'::jsonb`, `ingredient_keys='{}'::text[]`, `allergen_flags='{}'::text[]`, `applicable_slots=ARRAY['main']::text[]`. If `(household_id, normalized canonical_name)` UNIQUE conflict (item already created by Stage 0/1 in a parallel-running deploy), **reuse the existing `recipes.id`** instead of inserting; do not error.
   - INSERT into `household_recipe_usage` with `household_id`, `recipe_id`, `catalog_provenance='declared'`, `is_household_favorite=true`, `confidence_score=80`, `first_used_at=<favorite_lunches.created_at>`, `last_used_at=<favorite_lunches.created_at>`.
3. On any row failure outside `42P10`/`23505`-with-recovery: transaction rolls back BOTH writes; row is left in `favorite_lunches` and logged.

**AC3 — Decryption-failure handling.**
Per-row try/catch around DEK decryption. On failure: log structured event `migration.favorite_lunches.decrypt_failed` with `{ household_id, row_id, error_class }` (NEVER the plaintext attempt or ciphertext). Quarantine the row (do not migrate). Continue with next row. **Abort the entire migration only if `>5%` of rows fail decryption.** Quarantined rows remain in `favorite_lunches` until explicitly triaged; the table drop in AC8 is gated on zero quarantined rows OR explicit ops sign-off (manual flag).

**AC4 — Encryption-drop security checkpoint.**
Slice spec carries an explicit note: *"plaintext `recipes.canonical_name` + RLS + `visibility='private'` threat model reviewed and accepted (or deferred per brief Section 3)."* If deferred, link to a follow-up issue. Do not ship without this checkpoint visibly captured in the PR description or commit body.

**AC5 — Agent tool refactor.**
`favorite_lunch.add` tool (currently at `apps/api/src/agents/tools/onboarding.tools.ts`) is refactored to `recipe.declare(label, provenance='declared')` (or equivalent — keep the existing name if migration cost is high, but its body MUST now write to `recipes` + `household_recipe_usage` instead of `favorite_lunches`). M5 hot path stays functional: tapping a chip / typing a lunch in the M5 turn writes through the tool and the new state is read by the Kitchen Profile.

**AC6 — Kitchen Map composer projection swap.**
`apps/api/src/modules/kitchen-map/kitchen-map.composer.ts`:
- Delete `projectFavoriteLunches` and its `favorite_lunches` source query in the repository.
- Extend `projectRecipes` (or rename to `projectCatalog` for clarity) to surface `catalog_provenance` on each row of the recipes projection.
- `KitchenMapSchema.favorite_lunches` array shape preserved at the projection boundary (no breaking change to consumers) — populated from `household_recipe_usage WHERE catalog_provenance IN ('declared','parent_added') OR is_household_favorite=true`, joined to `recipes` for `canonical_name`.

**AC7 — Kitchen Profile starting-line read swap (in-slice).**
`apps/web/src/routes/(app)/kitchen-profile.tsx` (and any helpers under `apps/web/src/features/kitchen-profile/...`):
- Starting-line card data source swapped to the new joined query via the existing Kitchen Map API.
- Read order: `is_household_favorite DESC, last_used_at DESC NULLS LAST` with `LIMIT 20`.
- Card behavior preserved: count display, edit-button presence (still deferred per 2.5-s11), copy "Lumi's starting line" unchanged.
- All Epic 2.5 Kitchen Profile E2E tests in `apps/web/test/e2e/2.5-s11-kitchen-profile-read-live-data.spec.ts` still pass without modification (or only minimal id/selector adjustments).

**AC8 — `favorite_lunches` table dropped at slice end.**
After AC2 verification (zero unmigrated rows OR ops sign-off on quarantined rows) and AC6/AC7 verification (no remaining code references), a follow-up migration drops the `favorite_lunches` table. Rollback script ships in the same migration directory:
- The rollback script re-creates `favorite_lunches` with the original schema, copies `recipes`+`household_recipe_usage` rows back (re-encrypting `canonical_name` via household DEK), and drops the `catalog_provenance` column.
- Rollback script is tested in dev against a representative dataset before any prod apply.

**AC9 — No regressions.**
- All existing Epic 2.5 E2E tests on M5 (`apps/web/test/e2e/2-7-text-onboarding.spec.ts` and related) still pass.

## Dev Notes

### Why this slice exists

`2.5-s9` shipped `favorite_lunches` as an encrypted-text standalone table for M5 cold-start seeding. Two weeks earlier `3-31` had shipped `recipes` + `household_recipe_usage` — a more capable, GIN-indexed, planner-aware infrastructure with confidence scoring, favorite/banned flags, and per-household engagement counters. The two were authored independently; the catalog UX spec finalized 2026-05-23 made the redundancy explicit. This slice folds `favorite_lunches` into the older, more capable infrastructure.

**See:** Epic 2.6 brief §1 (Issue Summary) for the full architectural-collision narrative.

### Two-layer model (architectural commitment)

Epic 2.6 commits to a two-layer model where lunch items have a lightweight "suggestable idea" representation (Layer 1: name + tags; emitted by Stage 1 LLM seeding in slice `2.6-s3`) and a heavyweight "structured recipe" representation (Layer 2: full ingredients + instructions; materialized lazily via `RecipeAgent.discover()` at plan-commit time, reusing 3-31's existing flow).

**This slice (`2.6-s1`) is the data-shape foundation only.** It does NOT introduce Stage 1 LLM seeding (that's `2.6-s3`) or the Layer 2 trigger integration in `PlansService.commit()` (also `2.6-s3`). It just makes the table shapes ready.

### Encryption decision (resolved)

The 2.5-s9 choice to encrypt `favorite_lunches.item` is **reversed in this slice** in favor of plaintext `recipes.canonical_name` + RLS + `visibility='private'`. Rationale documented in Epic 2.6 brief §3 "Encryption decision."

**Threat model:** A DB-read-without-DEK attacker would see `"biryani"` or `"Mama's special pasta"` in plaintext. Acceptable because (a) RLS + `visibility='private'` + `created_by_household_id` prevent cross-household reads, (b) the same attacker can already see `children.declared_allergens` (encrypted but cross-table-joinable), (c) the existing `recipes` table has been in production for ~3 weeks via story 3-31 with this pattern — Epic 2.6 just brings the M5 catalog into pattern consistency.

**Reversibility:** If a future security review flags this, add an encrypted-variant column `canonical_name_encrypted` for `visibility='private'` rows; switch reads to that variant when present. No schema-shape change required.

### Established patterns to follow (from previous slices)

**From `2.5-s1` (Foundation slice that birthed `favorite_lunches`):**
- Idempotency on hash-based unique indices: PostgreSQL `42P10` (functional-index conflict) recovery path. The current `favorite_lunches` repository uses `insert → 23505 → SELECT` fallback (see `apps/api/src/modules/favorite-lunches/favorite-lunches.repository.ts`). The new `recipes` INSERT in this slice uses the SAME pattern via the new normalization unique index (Task 2).
- All migrations land via `supabase/migrations/`; rollback comments at the top of each.

**From `2.5-s11` (Kitchen Profile read live data — the read path this slice swaps):**
- The Kitchen Profile starting-line card reads from `kitchen_map.favorite_lunches` projection. This slice changes the WRITE source (recipes+household_recipe_usage) but keeps the projection shape intact — the UI doesn't change.
- See `_bmad-output/implementation-artifacts/2.5-s11-kitchen-profile-read-live-data.md` for the reference implementation.

**From `3-31` (Recipe Agent — Tavily structured fetch):**
- `recipes` + `household_recipe_usage` schema is in `supabase/migrations/20260820000200_create_recipes_and_usage.sql`. Read this file before writing migrations — the patterns (GIN indexes, RLS policies, the version-bump trigger on `household_recipe_usage` for stable-flag flips only) are non-obvious and must be preserved.
- The `recipes.canonical_name` is plaintext (RLS-gated); the existing pattern this slice extends.

### Anti-patterns to avoid

- **Do not** keep `favorite_lunches` around as a "for now we'll dual-write" — the brief explicitly commits to dropping it. Dual-write creates synchronization risk and is the parallel-store anti-pattern the slice exists to eliminate.
- **Do not** introduce a new `lunch_catalog` table. The earlier Epic 2.6 brief rev 1 proposed this; rev 2 explicitly rejected it after schema review. The catalog IS `recipes` + `household_recipe_usage`.
- **Do not** encrypt the new `recipes.canonical_name` rows. Plaintext + RLS is the established pattern in production from story 3-31.
- **Do not** add the `catalog_provenance` column to `recipes`. It belongs on `household_recipe_usage` (a recipe can be `declared` in one household and `inferred` in another).
- **Do not** Layer-2-materialize (call `RecipeAgent.discover()`) in this slice. That's the integration point added in `2.6-s3`. This slice's `recipes` rows have `ingredients=[]` and that's correct.

### Edge cases captured during readiness check (must be handled)

From the `bmad-review-edge-case-hunter` pass and folded into the brief rev 3 ACs:

| Edge case | AC reference | Handling |
|---|---|---|
| Migration atomicity per source row | AC2 | Single transaction per source row; failure rolls back both writes |
| `recipes` UNIQUE conflict (parallel create from Stage 1) | AC2 | Reuse existing `recipes.id`; INSERT only `household_recipe_usage` |
| Corrupt ciphertext on a single `favorite_lunches` row | AC3 | Per-row try/catch; quarantine; abort whole migration only if >5% failure rate |
| Rollback script semantics in forward-deployed Supabase | AC8 | Separate rollback SQL re-creates table + re-encrypts; tested in dev |
| Encryption-drop security review | AC4 | Explicit PR-description / code-comment checkpoint |
