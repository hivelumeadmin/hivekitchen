## Story

As a **HiveKitchen developer**,
I want to **generate the M2/M3/M4 chip lists from the vocabulary/schema source of truth, apply pure-chip turns deterministically with zero LLM calls, and replace the `[CHIP_PROMPT:elevation:…]` prose sentinel with a structured `allergen.declare` tool field**,
so that **chips collapse from three channels (deterministic map + catalog projection + fragile prose sentinels) with hand-maintained drift risk into one deterministic, tested source — cutting cost on chip-only turns and removing a whole class of sentinel-parsing fragility**.

**AC2 — Zero-call chip turns (4b).**
- A **pure-chip** selection (no free text) is applied deterministically: chip keys map directly to tool calls (e.g. `peanut` at M2 → `allergen.declare`) and the moment advances **with zero conversational LLM calls**.
- A **chip + free-text** turn still routes through the model as normal.
- **Acknowledgment prose for the pure-chip path is a code-filled template (Option A — decided 2026-06-26)**, e.g. `"Got it — I've noted {allergens} to keep out of every plan."`, filled deterministically by the service from the selected chips. A small set of per-moment templates is authored in this slice.

**AC3 — Elevation via tool, not sentinel (4c).**
- The `[CHIP_PROMPT:elevation:<tag_key>:<tag_label>]` regex channel (`onboarding.service.ts:240` `extractElevationPrompt`) is removed.
- `allergen.declare` gains structured optional fields `enforcement` (e.g. `'strict'`) and `request_ratification` (boolean) in `packages/contracts/src/onboarding-tools.ts`. When the model judges strong enforcement language, it sets these on the tool call; the ratification chip renders as a deterministic consequence of the structured result (traced, validated, cannot half-leak into the visible message).

**AC4 — M5 catalog chips untouched.**
- M5 catalog-projected chips (`CatalogProjectionService`, Epic 2.6) are out of scope for derivation — treated as a black-box input. Cold-start + Stage-0/1/2 behavior is asserted unchanged.

**AC5 — `household_name` swap deferred (not faked).**
- The `[CHIP_PROMPT:household_name]` hint swap (`onboarding.service.ts:835`) is a sub-state of M1 and is **deferred to `s6`** (needs slot state to know "kids asked, name not yet"). Do not fake it here. It remains working via its current path until `s6`.

**AC6 — Client behavior preserved.**
- Client-side `'none'` mutual-exclusion for M2 keeps working with generated chips.
- Chip render position (below Lumi's message, above the input) unchanged.

**AC7 — No behavior regression.**
- `2.7-s1` eval green (chip-driven scenarios produce identical structured outcomes; pure-chip turns now show zero LLM calls where applicable).
- Existing onboarding service + tool + contract tests green; root typecheck clean.

## Dev Notes

### Why this slice exists

Chips come from three sources today: deterministic moment-keyed (`momentToChipConfig`, fine), per-household catalog projection (M5, fine), and two **prose sentinels** — `[CHIP_PROMPT:household_name]` (`:835`) and `[CHIP_PROMPT:elevation:…]` (`:240`). The sentinels fail the same way `[NEXT_MOMENT:]` fails. Separately, the deterministic chip lists are kept in sync with their tool/vocab keys by hand-copied comments ("copied verbatim from Moment2Page.tsx" `:304`; "mirror `BagCompositionPatternSchema` exactly" `:355`) — three silent drift points with no test. This slice makes chips one deterministic, tested source; moves the elevation sentinel onto the structured tool channel; and makes pure-chip turns free. It strengthens the control-inversion thesis: it proves the deterministic sources already hold what the controller needs.

### The zero-call decision (Option A)

When the parent answers entirely by tapping chips, there is nothing to interpret — Lumi is confirming a known selection and advancing. So the acknowledgment is a code-filled template (zero LLM calls). The moment free text is mixed in, the turn routes through the model normally. Decided by Menon 2026-06-26; see brief §4 → `2.7-s5` 4b and the risk register.

### Patterns to follow

- **`momentToChipConfig` (`onboarding.service.ts:296`)** + `ChipConfig`/`ChipOption` (`@hivekitchen/contracts`) — the structure to keep; only the *source* of the option lists changes.
- **`chip-taxonomy-three-types` memory** — hint (non-selectable) / action (single-select) / choice (multi-select); chips render below Lumi's message, above the input.
- **`s2` strict-null-safe schema** — the new `allergen.declare` fields must follow the nullable rule.

### Anti-patterns to avoid

- **Do not** touch the M5 catalog projection (`CatalogProjectionService`) — black-box input (AC4).
- **Do not** implement the `household_name` swap here — it needs slot state; it lands in `s6` (AC5).
- **Do not** keep `extractElevationPrompt` "just in case" — the structured tool field replaces it entirely (AC3).
- **Do not** call the LLM on pure-chip turns — that round-trip exists today only to route known keys to known tools (AC2).
- **Do not** hardcode chip labels divorced from vocab — derive from the source so the drift test stays meaningful (AC1).

### Edge cases captured in the brief

| Edge case | AC | Handling |
|---|---|---|
| Chip-key ↔ tool/vocab drift | AC1 | Generate from source + drift test |
| Pure-chip ack prose without an LLM call | AC2 | Per-moment code-filled templates (Option A) |
| Elevation sentinel half-leaking into message | AC3 | Structured tool field; chip from result; no regex on prose |
| M5 cold-start / Stage-0/1/2 | AC4 | Untouched; asserted unchanged |
| `household_name` sub-state | AC5 | Deferred to `s6` (slot-derived), not faked |
| M2 `'none'` mutual exclusion | AC6 | Preserved with generated chips |

- M2 (FALCPA filter) and M4 (enum) genuinely auto-light-up new vocab/enum entries at runtime. M3 is necessarily a **curated subset** (the full active dietary+cuisine vocab is ~90 rows vs. the 17 onboarding chips), so its drift guard is a subset-validity + tool-acceptance check rather than set-equality.
- The drift test's vocab fixture mirrors the seed migration; full SQL-drift detection (failing when a FALCPA row is added to the SQL but not the chip layer) would want an integration test against a seeded DB — a possible follow-up. The unit drift test still converts the three silent comment-drift points into one explicit, failing-loud assertion.
