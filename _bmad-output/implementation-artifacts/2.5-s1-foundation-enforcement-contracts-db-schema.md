## Story

As **the architect of HiveKitchen's onboarding data model**,
I want **the enforcement-strength contract, the five new structured signal tables, the new `KitchenMap*Schema` fragments, the new `OnboardingTool*Schema` fragments, and the tool-manifest stubs to all exist before any user-facing slice runs**,
so that **every downstream Epic 2.5 slice (chip UX, agent prompt v2, the five moment slices, the finalize gate, the Kitchen Profile live read) can land against a stable contract surface instead of having to redesign data shapes mid-sprint** — and so paused Epic 3 stories (3-23, 3-24, 3-25, 3-26, 3-27, 3-29) have a single, authoritative `enforcement_level` enum to rebase against when they resume.

This slice is **pure foundation: DB, contracts, tool registry**. **No user-facing change.** A fresh signup still goes through the existing v1 onboarding agent unchanged. The new tools exist as `ToolSpec` registrations with maxLatencyMs values; their factory functions return success but are not yet wired into `OnboardingService` and the agent prompt does not know about them yet — that happens in 2.5-s4.

## Acceptance Criteria

### AC1 — `enforcement_level` Postgres enum

A new Postgres enum type `enforcement_level` exists with **five values** in increasing-strictness order (snake_case strings, matches project convention per architecture.md:561):

```
non_negotiable    -- hard rule: planner MUST NOT violate. Allergen-equivalent strength.
strong            -- elevated cultural / religious / dietary; planner avoids and confirms before exceptions.
default           -- standard family preference; planner respects, may surface alternatives.
soft              -- gentle bias; planner weighs but does not gate.
just_for_context  -- informational only; planner reads but never enforces.
```

Created via a dedicated enum-first migration (`<prefix>_create_enforcement_level_enum.sql`) so subsequent migrations can reference it in column definitions (mirrors the pattern in `20260501115000_create_node_type_enum.sql`, architecture.md:1001).

A paired contract value lives at `packages/contracts/src/enforcement.ts` as a const tuple + Zod enum:

```ts
export const ENFORCEMENT_LEVEL_VALUES = [
  'non_negotiable',
  'strong',
  'default',
  'soft',
  'just_for_context',
] as const;
export const EnforcementLevelSchema = z.enum(ENFORCEMENT_LEVEL_VALUES);
export type EnforcementLevel = z.infer<typeof EnforcementLevelSchema>;
```

A parity test (`packages/contracts/src/enforcement.test.ts`) asserts the tuple has exactly five values in this order; a paired API-side test (`apps/api/test/integration/enforcement-enum-parity.test.ts`) queries `pg_enum` and asserts the DB values match the TS tuple element-for-element. If the two ever diverge it must fail loudly — this is the same parity discipline as `audit_event_type` (see 2-s27 T1.3).

### AC6 — Tool manifest registration

`apps/api/src/agents/tools.manifest.ts` (architecture.md §3.5) gains entries for the seven new tools. Each entry follows the existing `ToolSpec` shape (see `child.upsert` for reference). `maxLatencyMs` values, conservative budget per tool:

| Tool | maxLatencyMs | Rationale |
|---|---|---|
| `household.set_name` | 80 | single UPDATE |
| `allergen.declare` | 120 | INSERT + envelope encrypt + idempotency lookup |
| `dietary.declare` | 100 | INSERT + vocabulary lookup |
| `cuisine.declare` | 100 | shares `cultural_priors` write path |
| `food_preference.declare` | 120 | INSERT + envelope encrypt + dedupe lookup |
| `favorite_lunch.add` | 120 | INSERT + envelope encrypt |
| `rule.set` | 100 | INSERT + idempotency lookup |

**Tool factory wiring.** Each new tool gets a `createXxxToolSpec` factory in `apps/api/src/agents/tools/onboarding.tools.ts`, parallel to `createChildUpsertToolSpec` / `createCulturalNoteToolSpec` / `createMemoryNoteToolSpec`. **For this slice the factories may be minimal:** they validate input via the Zod schema, return a deterministic-stub success response (e.g. emit a `*_id` derived from a deterministic hash so tests pass), and emit a Pino `info` log line with the structured payload. **Full DB-writing implementations land in the moment slices (s5–s9) that actually need them.** The `createOnboardingToolSpecs` factory function returns all ten tools (3 existing + 7 new), but the new seven are **not yet added to the OnboardingService's tool list** that gets passed to OpenAI — that exposure happens in 2.5-s4 when the agent prompt v2 ships. This way, downstream slices can `import` the factory and the contracts without runtime risk.

> **Alternative considered:** ship the seven new tools fully wired (DB writes and all) in this slice. Rejected because (a) the agent prompt doesn't know to call them yet so no value is realised, (b) full DB writes would require RLS policies + service-layer code that's better authored alongside the moment slice that needs them, (c) review surface area for this foundation slice stays compact. The contract surface IS stable; the handlers are stubs until summoned.

### Previous Story Intelligence (from 2-s27)

Key lessons that apply directly:

1. **DEK + envelope encryption pattern**: works as-is. Use `getOrCreateHouseholdDek` + `encryptField` / `decryptField` (`apps/api/src/lib/envelope-encryption.ts`). Reads decrypt at the repository boundary; services see plaintext.
2. **Idempotency on encrypted columns is tricky.** AES-GCM uses a random nonce per encrypt call, so the ciphertext bytes differ each time even for the same plaintext. For idempotency lookups on `child_allergens.(child_id, allergen)`, the encrypted column cannot serve as the dedupe key directly — either (a) add an unencrypted **hash column** (`lower_normalized_hash text`) populated at write time and used as the dedupe key, or (b) read all rows for the child, decrypt, then check membership in app code. Option (a) is faster + cleaner for the per-row pattern; option (b) avoids the schema field. **DECISION POINT:** see Open Questions.
3. **Backfill scripts vs migrations.** The 2-s27 backfill used a Node script because envelope encryption is application-layer. This slice has NO backfill of data — only structure. So no script needed. (s2 will need one.)
4. **Audit event parity pattern**: TS enum + paired `ALTER TYPE` migration + parity test. Reused as the template for `enforcement_level` enum parity.
5. **Vocabulary validation pattern**: `VocabularyService.validate*` at the handler boundary. The new tool factories call these where applicable (`dietary.declare`, `cuisine.declare`); allergens fall through (open-vocab per the locked policy).
6. **CHECK constraints + Zod enums in sync**: prefer enum-backed columns over CHECK constraints where the enum is shared with TS (per `enforcement_level`). For closed sets that won't ever be enums in TS (e.g., `source`), CHECK constraints are fine.

## Open Questions for PM / Architect

These should be resolved BEFORE the dev agent begins (or — for low-risk items — flagged and decided in-PR with a written note).

### Q1 — PRD FR121–FR130 numbering collision (PM)

The sprint change proposal Section 4.B lists ten new FRs `FR121–FR130` (enforcement gradient, allergens uniform-hardness, required-set gate, etc.). **The PRD at `_bmad-output/planning-artifacts/prd.md` already has FR121–FR127 defined** — they cover Lunch Link rating window, session URI semantics, etc. (lines 959–965). The sprint proposal's PRD amendments (Pass B.1) have not yet been authored.

**Decision needed:** Should the new enforcement FRs renumber to FR128+? Or do the Lunch Link FRs renumber? Either is fine; the dev agent doesn't depend on the numbers being final for THIS slice, but the architecture amendments (T1) reference FR121–FR130 by number and will need to be revised once PM picks a numbering.

**Suggested resolution:** Defer to John (PM) in Phase 1 per the sprint change proposal's handoff plan. This slice can ship referencing the *names* of the FRs (enforcement gradient, required-set gate, etc.) rather than numbers. T1 architecture amendments should use FR names too.

### Q2 — `dietary_preferences` table name vs. existing column (Architect)

The new structured table per AC2.3 is named `dietary_preferences`. The existing encrypted JSONB column on `households` is also `dietary_preferences`. Once both exist, references in code that say `dietary_preferences` will be ambiguous (column on households, OR table).

**Options:**
- (a) Live with the name collision; rely on context (`households.dietary_preferences` = column; `dietary_preferences` table = table). Existing pattern with `child_allergens` ≠ `children.declared_allergens` already does this.
- (b) Rename the new table to `dietary_signals` or `household_dietary_signals` internally; keep `dietary` as the contract name. (Sprint proposal uses `dietary_preferences` as the table name in 4.A.)
- (c) Rename the old column.

**Suggested resolution:** (a) — accept the collision; it mirrors `child_allergens` ↔ `children.declared_allergens`. SQL queries always qualify with table name; TypeScript uses distinct schemas. Document the convention in T1 architecture amendments.

### Q3 — Encrypted-column idempotency strategy (Architect)

Per Dev Note "Previous Story Intelligence #2": idempotency on `(child_id, allergen)` where `allergen` is encrypted needs either an unencrypted hash column or app-side dedupe via full read+decrypt.

**Options:**
- (a) Add `allergen_hash text not null` (BLAKE2 / SHA-256 of `lower(normalized_allergen)`) + a unique index on `(child_id, allergen_hash)`. Same for `food_preferences.item_hash`, `favorite_lunches.item_hash`, `household_rules.custom_label_hash` (where applicable). Pure DB-level idempotency; one SELECT + INSERT in the tool handler.
- (b) Repository-level dedupe: every write loads all rows for the household, decrypts, checks membership, then inserts if absent. Cleaner schema; slower at scale.

**Suggested resolution:** (a) — add hash columns. Trades schema noise for performance and atomic idempotency. The hash function lives next to `encryptField` in `envelope-encryption.ts` as `normalizedHash(value: string): string`. **If the architect prefers (b), the AC2.* schemas drop the hash column and the tool factory handlers explicitly do the read-then-decide-then-write dance.**

### Q4 — `enforcement_levels` as a vocabulary table (Architect)

The vocabulary tables pattern (`20260820000100_create_vocabulary_tables.sql`) might or might not want `enforcement_levels` as a row-per-value table for consistency.

**Options:**
- (a) Enum only — `enforcement_level` Postgres enum + TS tuple. No vocabulary row. Vocabulary service does not know about it.
- (b) Both — enum AND a vocabulary table mapping each value to a human label, color hint, planner-weighting hint, etc.

**Suggested resolution:** (a) for this slice. (b) can come later if/when a UI needs to render enforcement labels with localized strings or design-system colors. The chip UX wall slice (2.5-s3) may surface the need.

### Q5 — `bag_composition_pattern` deprecation timing

The new `bag_composition_pattern` (string enum: `main_only | main_plus_snack | …`) and the existing `bag_composition` (`{ main, snack, extra }` booleans) are equivalent representations. The string is a parent-stated mental model; the booleans are derived.

**Decision:** Do we deprecate `bag_composition` (booleans) after Epic 2.5?

**Suggested resolution:** Yes — but not in this slice. The booleans stay live and writable; this slice just adds the pattern as a parallel field. Cleanup belongs in a post-Epic-2.5 slice or the Epic 2 retrospective.
