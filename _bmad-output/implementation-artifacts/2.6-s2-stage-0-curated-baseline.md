## Story

As a **HiveKitchen developer**,
I want to **create a global `curated_baseline_items` reference table seeded with ~50 hand-tagged items spanning major cuisine × dietary × allergen intersections, and wire a Stage 0 worker that materializes per-household `recipes` + `household_recipe_usage` rows at household creation and again on M3 completion**,
so that **every new household has a safety-net catalog from day one — ensuring Lumi has at least some relevant suggestions before Stage 1 LLM seeding runs, and protecting cohorts where LLM seeding is sparse (Somali, Yemeni, Tibetan, sub-regional cuisines)**.

## Acceptance Criteria

**AC1 — `curated_baseline_items` table created.**
New global table in `supabase/migrations/`:
```
id                uuid        NOT NULL DEFAULT gen_random_uuid() PRIMARY KEY
canonical_name    text        NOT NULL
allergen_flags    text[]      NOT NULL DEFAULT '{}'
dietary_flags     text[]      NOT NULL DEFAULT '{}'
cultural_tags     text[]      NOT NULL DEFAULT '{}'
cuisine_tags      text[]      NOT NULL DEFAULT '{}'
applicable_slots  text[]      NOT NULL DEFAULT ARRAY['main']::text[]
notes             text        -- authoring hint, NEVER exposed to frontend
is_active         boolean     NOT NULL DEFAULT true
created_at        timestamptz NOT NULL DEFAULT now()
```
- Global reference — NOT per-household. No `created_by_household_id`. No FK to `households`.
- No RLS needed: read only via service-role at materialization time. Add a comment explaining this.
- Seed INSERT of ~50 items using `ON CONFLICT (canonical_name) DO NOTHING` (idempotent).

**AC2 — `households.stage0_materialized_at` column added.**
`ALTER TABLE households ADD COLUMN stage0_materialized_at timestamptz;` (nullable).
- `NULL` = Stage 0 initial materialization has not yet run.
- Set to `now()` after the initial materialization completes.
- Re-materialization at M3 completion does NOT check this column — it always runs. Both paths rely on row-level idempotency (see AC5).

**AC3 — Seed data file authored (~50 items).**
`apps/api/src/seeds/curated-baseline.ts` — exports `CURATED_BASELINE` const array (TypeScript source of truth for git history; the migration seed INSERT is generated from / matches this array).

Required cuisine coverage (minimum counts):
| Cuisine bucket | Min items |
|---|---|
| `anglo` | 8 |
| `south_asian` | 8 |
| `east_asian` | 6 |
| `middle_eastern` | 6 |
| `latin_american` | 5 |
| `african` | 5 |
| `mediterranean` | 5 |
| `global` (mixed / cross-cultural) | 3 |

**"Broad safe seed" invariant for the global subset:** items seeded into this table MUST NOT contain any of the `FALCPA_TOP_9` allergen keys (`peanut`, `tree_nut`, `dairy`, `egg`, `wheat`, `soy`, `fish`, `shellfish`, `sesame`) OR pork-derived dietary flags. Rationale: Stage 0 fires at household creation before allergens are declared; these items must be safe for an unknown household. Items with FALCPA allergens or pork are omitted from the curated baseline entirely (content authoring decision, not a runtime filter).

**AC4 — Stage 0 worker materializes rows into `recipes` + `household_recipe_usage`.**

New `CuratedBaselineMaterializationService` (see Dev Notes for placement):

`materialize(householdId: string): Promise<void>` — initial materialization (triggered at household creation).
`rematerialize(householdId: string, cuisineTags: string[]): Promise<void>` — M3 re-seed (triggered on M3 completion).

For **initial materialization**:
- Load all `curated_baseline_items WHERE is_active = true`.
- No cuisine filter (M1/M2 not complete yet) — use all items.
- Because all seed items already honor the "broad safe seed" invariant (AC3), the guardrail check here is belt-and-suspenders for any future baseline additions that might violate the invariant.

For **M3 re-materialization**:
- Load `curated_baseline_items WHERE is_active = true AND cuisine_tags && :cuisineTags` — cuisine-bucket match only.
- Include any items not yet in `household_recipe_usage` for this household (additive only; `ON CONFLICT DO NOTHING`).

**Both paths:**
1. For each candidate item, call `AllergyGuardrailService.evaluate([planItem], householdId)`. Skip items where verdict `!== 'cleared'`. Skip `uncertain` verdict too (fail-closed). See Dev Notes for how to map a baseline item to `PlanItemForGuardrail` efficiently.
2. For each surviving item:
   - INSERT into `recipes`: `source='catalog_seeded'`, `visibility='private'`, `created_by_household_id=householdId`, `canonical_name`, `ingredients='[]'::jsonb`, `ingredient_keys='{}'`, all tag arrays from `curated_baseline_items`. If `recipes_household_normalized_name_uniq` UNIQUE conflict (23505), reuse the existing `recipe_id`.
   - INSERT into `household_recipe_usage`: `catalog_provenance='inferred'`, `confidence_score=60`, `is_household_favorite=false`, `use_count=0`. Use `ON CONFLICT (household_id, recipe_id) DO NOTHING` — never downgrade an existing `'declared'` row or lower `confidence_score=80` to 60.
3. Log structured event (no PII) `catalog.stage0.below_floor` if post-guardrail persisted count < 30.
4. Log `catalog.stage0.terminal_zero` if persisted count = 0 (ops visibility; NOT an error — downstream stages compensate).
5. **Never throw.** Catch all errors, log them, return void. Stage 0 must not block household creation or M3 completion.

**AC5 — Idempotency two-layer guard.**
- **Household-level (initial only):** Before running initial materialization, check `households.stage0_materialized_at IS NULL`. If already set, skip immediately. Set to `now()` inside `materialize()` on success.
- **Row-level (both paths):** `ON CONFLICT (household_id, recipe_id) DO NOTHING` on `household_recipe_usage` INSERT — the `PRIMARY KEY (household_id, recipe_id)` constraint is the guard. The `recipes_household_normalized_name_uniq` index (from 2.6-s1) handles duplicate recipe inserts.

**AC6 — Two trigger points wired.**

**Trigger 1 — Household creation:**
- After the `households` row is committed (signup completion), call `materialize(householdId)` fire-and-forget.
- Pattern: `.then(() => householdsRepo.setStage0MaterializedAt(householdId)).catch(err => logger.error(...))` — do NOT await in the request path.
- Update `households.stage0_materialized_at = now()` INSIDE the `materialize()` success path (NOT in the fire-and-forget caller — let the service own its own timestamp write).

**Trigger 2 — M3 completion:**
- In `apps/api/src/modules/onboarding/onboarding.service.ts`, find where M3 cultural priors are committed to the DB.
- After the write: `curatedBaseline.rematerialize(householdId, m3CuisineTags).catch(err => logger.error(...))` — same fire-and-forget pattern.
- `m3CuisineTags` derives from the `cultural_priors` rows just written (cuisine_tag values from the M3 priors).

**AC7 — Edge cases from brief rev 3 handled.**
- Stage 0 fires before M1/M2: all items are "broad safe" by construction (AC3); no allergen filter needed beyond the guardrail call.
- Guardrail blocks items: skip; continue; log if count < 30. Never fail.
- Idempotent double-fire: `ON CONFLICT DO NOTHING` handles cleanly.
- M3 re-materialize races with initial: both use `ON CONFLICT DO NOTHING`; union of surviving items is the result.
- Guardrail uncertain verdict (DEK decrypt failure): skip item; log `catalog.stage0.guardrail_uncertain` with `{household_id, item_index: N}` (no name/hash logged — PII risk).

**AC8 — No regressions.**
- All 2.6-s1 tests pass without modification.
- All existing onboarding E2E tests pass.
- `pnpm tsc --noEmit` clean.
- `pnpm --filter @hivekitchen/api test` passes (new tests included).

## Dev Notes

### Why this slice exists

Stage 0 is the safety net for the two-layer catalog model. Stage 1 LLM seeding (2.6-s3) may produce sparse or poor results for under-represented cultural cohorts. Without Stage 0, those households get zero catalog items at M5, forcing the cold-start fallback path for everyone. With Stage 0, the fallback only triggers when even the curated baseline doesn't provide enough coverage.

**No UI changes in this slice.** The Kitchen Profile and M5 chip card already read from `household_recipe_usage` via the query wired in 2.6-s1. Stage 0 items (`catalog_provenance='inferred'`) surface automatically once they're in the DB.

### Schema prerequisites from 2.6-s1 (already live — do NOT re-add)

- `recipes.source` CHECK accepts `'catalog_seeded'` ✓
- `household_recipe_usage.catalog_provenance` column exists (`'inferred'` is Stage 0's value) ✓
- `recipes_household_normalized_name_uniq` UNIQUE partial index exists ✓

### AllergyGuardrailService — efficient pattern for batch catalog evaluation

`AllergyGuardrailService.evaluate()` calls `getRulesForHousehold()` on every invocation (one DB round-trip per call). For a batch of ~50 items, calling it per-item naively = 50 DB round-trips. Instead:

```typescript
// Load rules once
const rules = await this.guardrailRepo.getRulesForHousehold(householdId);

// Then use the pure engine function per item (no audit write, no DB round-trip)
import { evaluate } from '../allergy-guardrail/allergy-rules.engine.js';

for (const item of candidates) {
  const planItem: PlanItemForGuardrail = buildPlanItemFromBaselineItem(item);
  const result = evaluate([planItem], rules);  // pure function, no async
  if (result.verdict !== 'cleared') continue;
  // persist...
}
```

**`PlanItemForGuardrail` shape** — check `packages/contracts/src/plan.ts` for the exact type. The key field the engine uses is `allergen_flags`. A baseline item maps as:
```typescript
{
  // populate all required fields; use item.allergen_flags for the allergy check
  allergen_flags: item.allergen_flags,
  // other required fields: fill with safe defaults (empty arrays, 'main' slot, etc.)
}
```

**On `uncertain` verdict:** skip the item (fail-closed). Log `catalog.stage0.guardrail_uncertain` with `{household_id, item_index}`. Do NOT log `canonical_name` — even curated names could be culturally identifying.

### `RecipesRepository.seedFromCatalogBaseline()` — pattern and gotchas

Model on `declareForHousehold()` from 2.6-s1 but with key differences:

| | `declareForHousehold()` (M5 tool) | `seedFromCatalogBaseline()` (Stage 0) |
|---|---|---|
| `catalog_provenance` | `'declared'` | `'inferred'` |
| `confidence_score` | 80 | 60 |
| `source` | `'parent_declared'` | `'catalog_seeded'` |
| On usage conflict | error if non-23505 | `DO NOTHING` always |
| Tag arrays | `allergen_flags=[]` only | full tag arrays from baseline |
| `use_count` on INSERT | must include explicitly (2.6-s1 review patch #8) | `use_count=0` |

**Normalization must match the UNIQUE index** (lesson from 2.6-s1 review finding #1):
The index uses: `lower(name)` → NFC normalize → `regexp_replace` stripping `[\s\-']+`.
Your TypeScript normalization MUST apply the same stripping before the ilike fallback. Curated baseline names are curator-authored (not user-typed), but if any contain hyphens or apostrophes (e.g., `"dal-chawal"`, `"mom's rice"`), the mismatch will cause the conflict-recovery path to throw "UNIQUE conflict but no row found."

**Error pattern** — from 2.6-s1 review finding #2: when a compensation DELETE also fails, `throw insertUsage.error` (root cause), NOT `throw deleteError`. Log both.

In `apps/api/src/modules/onboarding/onboarding.service.ts`, search for where M3 cultural priors are persisted (the moment `cultural_priors` rows are written after the M3 agent turn completes). M3 = "How your kitchen tastes" (cuisine + dietary + food preferences).

Extract the committed `cuisine_tags` from the cultural priors just written (the `key` fields from `cultural_tags` vocabulary). Pass them to:
```typescript
this.curatedBaseline.rematerialize(householdId, cuisineTags)

```

### Anti-patterns to avoid

- **Do NOT** call `declareForHousehold()` for Stage 0 items — it sets `provenance='declared'` and `confidence_score=80` (wrong).
- **Do NOT** await Stage 0 in the signup or M3 request path — it is always fire-and-forget.
- **Do NOT** create a separate `curated_lunches`, `baseline_recipes`, or `catalog_seeds` table. `curated_baseline_items` is the source; `recipes` + `household_recipe_usage` is the per-household projection.
- **Do NOT** put `stage0_materialized_at` on `recipes` or `household_recipe_usage`. It belongs on `households`.
- **Do NOT** delete `household_recipe_usage` rows at re-materialization. Additive only.
- **Do NOT** downgrade `catalog_provenance` from `'declared'` → `'inferred'` or lower `confidence_score` from 80 → 60 via `ON CONFLICT DO NOTHING`.
- **Do NOT** call `RecipeAgent.discover()` or trigger Layer 2 materialization in this slice. `ingredients=[]` is correct for Stage 0 items. Layer 2 fires lazily at plan-commit time (2.6-s3 integration point).
- **Do NOT** import `curated-baseline.ts` seeds at runtime. The seed file is for authoring + git history; the DB is the authoritative source at runtime.

### Edge cases table (from brief rev 3)

| Edge case | Handling |
|---|---|
| Stage 0 fires before M1/M2 complete | All baseline items are broad-safe by construction (AC3); guardrail still runs as belt-and-suspenders |
| Guardrail blocks some items | Skip; continue; log `catalog.stage0.below_floor` if post-guardrail count < 30 |
| Post-guardrail count = 0 | Valid degraded state; log `catalog.stage0.terminal_zero`; Stage 1/2/cold-start compensate downstream |
| Idempotent double-fire on same household | `stage0_materialized_at` check (initial path) + `ON CONFLICT DO NOTHING` (both paths) |
| M3 re-seed races with initial materialization | Both use `ON CONFLICT DO NOTHING`; final state = union of surviving items |
| Guardrail returns `uncertain` (DEK failure) | Skip item; log with item index (no name); continue batch |

### Key Decisions

- **Guardrail engine quirk**: the engine's token reverse-check (`target.includes(tok)`) makes the literal word "and" match the dairy synonym `half-and-half`. All 50 seed canonical names use commas / "with" / compound nouns to avoid this. Also avoided: `bean` singular (matches `soybean`), `pollo` (matches `pollock`), and any FALCPA synonym substring. Decisions documented in `curated-baseline.ts` AUTHORING RULES comment so future curators don't trip the same wires.
- **PlanItemForGuardrail.child_id**: Stage 0 fires before any children exist; FALCPA rules carry `child_id=null` and apply to any child UUID. Pass `householdId` as the synthetic `child_id` (already a valid UUID) — the engine never dereferences it as a real child.
- **PlanItemForGuardrail.ingredients**: pass `[canonical_name.slice(0, 200)]`. The engine's substring+synonym match against FALCPA categories runs on the recipe name, catching curator slip-ups even when `allergen_flags` is empty.
- **terminal-zero still sets stage0_materialized_at**: a degraded materialization (zero survivors) is logged but the timestamp is still set. Stage 1/fallback compensate; we don't want a retry loop on subsequent logins for the same household.
- **Decrypt error fail-closed**: `AllergyGuardrailDecryptError` aborts the batch (persisted=0) but `materialize()` still sets the timestamp. The next M3 trigger will run a cuisine-filtered re-seed once the DEK becomes readable; the alternative (leaving timestamp NULL forever) would race-loop on every login.
- **rematerialize tag filtering**: pass ALL `cultural_priors` keys, not pre-filtered cuisine keys. The SQL overlap operator on the GIN-indexed `curated_baseline_items.cuisine_tags` naturally drops non-cuisine values, keeping the OnboardingService trigger free of vocabulary-classification logic.
