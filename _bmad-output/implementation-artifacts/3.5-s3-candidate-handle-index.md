> **Source brief:** `_bmad-output/planning-artifacts/epic-3.5-brief.md` § Slice 3.5-s3. **[PRE-LAUNCH] · Gated by s1 (done) and s2 (done).**
> This is the third slice of Epic 3.5. It **removes** the `findIdByName` fuzzy-lookup path for slate-sourced recipes and **replaces** it with a deterministic handle-index (`m1`, `m2`, ..., `e1`, `e2`, ...). Net effect: "Recipe not found → feed error back → retry" is eliminated for all slate-sourced compositions. The `findIdByName` cold-acquisition path is retained as a clearly-flagged fallback for recipes surfaced by `recipe.search`/`discover` at runtime (not in the pre-loaded slate). No migration, no contract wire-shape change visible to clients.

## Story

As a **HiveKitchen engineer eliminating the remaining recipe-name fuzzy-resolution retry loop from the plan-compose path**,
I want **the `<recipe_candidates>` block to emit stable short handles (`m1`, `m2`, …, `e1`, `e2`, …) and `plan.compose` to resolve a model-emitted handle to a catalog UUID deterministically from the in-memory slate index — never from a DB fuzzy match for slate hits**,
so that **the "Recipe not found → feed error back → self-correction turn" path is unreachable for any recipe the planner was shown at planning time, a handle that doesn't exist in the index fails immediately with a non-retried error, and the golden-set eval (s1) continues to pass with handle-emitting fixtures**.

## Dev Notes

### What this story adds and what it removes

| Before s3 | After s3 |
|---|---|
| `renderPlannerRecipeCandidatesBlock` returns `string` | Returns `{ block: string; handleMap: Map<string, string> }` |
| `PlannerRecipeCandidate` has no `id` | Gains `id: string` (catalog UUID) |
| `toCandidate()` excludes `id` | Includes `id: row.id` |
| Model emits recipe names in `recipe_id` (fuzzy) | Model emits handles (`m1`, `e1`, ...) from the slate |
| `resolveRecipeId` calls `findIdByName` for all non-UUIDs | `findIdByName` only for non-UUID, non-handle strings (cold path) |
| "Recipe not found" feeds back into the loop as a self-correction turn | Hard throw for handle misses — no retry, no loop re-entry |
| `createPlanComposeSpec` takes 3 params | Takes 4 params (handleIndex optional) |
| `planWeek` does NOT build a per-run plan.compose spec | Builds per-run spec when `recipeCandidates` is provided |

### Handle naming convention

- **Main candidates:** `m1`, `m2`, `m3`, ... (ordered by position in `slate.main[]`)
- **Extra candidates:** `e1`, `e2`, `e3`, ... (ordered by position in `slate.extra[]`)
- **Snack:** server-assigned by `SnackRotationService`; never appears in the slate or handle map.
- `m*` and `e*` namespaces cannot collide by construction.

### Handle resolution priority in `resolveRecipeId`

```
UUID → [UNCHANGED]
  ↓ (not UUID)
handleIndex.has(value) → return UUID from index [NEW — no DB call]
  ↓ (not in index)
/^[me]\d+$/.test(value) → throw hard error [NEW — not a retry]
  ↓ (not a handle pattern)
nameCache → findIdByName → throw "Recipe not found..." [UNCHANGED cold-acquisition path]
```

The regex `/^[me]\d+$/` is a soft heuristic for "looks like a handle". If a real recipe name happened to match this pattern (e.g., a recipe literally called "m1"), it would be incorrectly thrown. This is a deliberate tradeoff: recipe names of length 2 starting with `m` or `e` followed by digits do not exist in practice, and the hard error is preferable to an accidental retry. The cold-acquisition path handles all legitimate non-handle names.
