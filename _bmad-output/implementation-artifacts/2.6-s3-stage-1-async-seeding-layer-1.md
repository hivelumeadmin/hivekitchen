## Story

As a **HiveKitchen developer**,
I want to **build a BullMQ job (`catalog.seed.stage1`) that fires at M2 allergen-declaration completion, calls an LLM once to generate ~50 household-personalized lunch ideas (Layer 1: name+tags only, no ingredients), deduplicates against the curated baseline, filters through the allergy guardrail, and persists survivors into `recipes`+`household_recipe_usage` — then wire a Layer 2 trigger into `PlansService.commit()` so the first time a `catalog_seeded` item enters a plan, `RecipeAgent.discover(canonical_name)` populates full structured ingredients before the commit lands**,
so that **2.6-s4 M5 chip personalization has a household-specific catalog ready within ~5 seconds of M2 completion, and the planner can safely commit plans that include catalog-seeded items without `ingredients=[]` reaching the plan store**.

**AC2 — `catalog-seed.prompt.ts` authored.**

  - `applicable_slots` is one or more of `['main', 'snack', 'extra']`; most items are `['main']`.
  - Output MUST be valid JSON with the `items` key at root — no preamble, no markdown.
- User prompt: concise structured block with household snapshot values, templated by `buildCatalogSeedPrompt`.

**AC4 — `CatalogSeedService` authored.**
New `apps/api/src/modules/catalog/catalog-seed.service.ts`:

```
seedForHousehold(householdId: string, requestId: string): Promise<void>
```

Full pipeline (NEVER throws — catch everything, log, return void):

1. **Idempotency check.** Read `households.stage1_completed_at`. If already set, log `catalog.stage1.skip_idempotent` and return.

2. **Household snapshot.** Load:
   - Children + age bands → `ChildrenRepository.findByHousehold(householdId)`.
   - Kitchen map (for cultural priors, dietary flags, food preferences, cuisines, bag composition) → `KitchenMapService.getKitchenMap(householdId)` or compose directly from repositories already wired in 2.6-s2 (`CulturalPriorRepository`, dietary + food pref repos). The goal: have enough data to build the prompt snapshot.
   - Allergen rules → `AllergyGuardrailRepository.getRulesForHousehold(householdId)` — load ONCE; reuse for per-item filtering below.

3. **LLM call.** Call `openai.chat.completions.create`:
   - `model: 'gpt-4o'` (not mini — needs cultural breadth and allergen discipline).
   - `temperature: 0.7` (diversity over determinism for catalog generation).
   - `max_tokens: 4000`.
   - `response_format: { type: 'json_object' }`.
   - Timeout: apply a 5 000ms AbortSignal so the job's p95 ≤ 5s SLA holds. On timeout: log `catalog.stage1.llm_timeout`, treat as Stage 1 failure.

4. **Validate response.** `CatalogSeedResponseSchema.safeParse(JSON.parse(raw))`. On failure: log `catalog.stage1.response_schema_invalid`, treat as Stage 1 failure.

5. **Per-item Zod validation.** Parse each item with `CatalogSeedItemSchema`. Invalid items → log, discard.

6. **If post-validation count < 10:** log `catalog.stage1.floor_breach` with `{ household_id, validated_count }`. Still proceed with guardrail + persistence for whatever items survived. After persist, log `catalog.stage1.below_floor`. Leave a `// TODO(2.6-s5): enqueue catalog.recover.stage2 job here on floor breach` comment for future wiring.

7. **Curated baseline deduplication.** For each validated item:
   - Normalize its `canonical_name` via the same function used in `declareForHousehold()` (2.6-s1): `trim().normalize('NFC')` then `replace(/[\s\-']+/g, '')` then `toLowerCase()`.
   - Query `curated_baseline_items WHERE recipes_normalized_canonical_name(canonical_name) = <normalized>` (or do an in-memory lookup against all active baseline names loaded once at the start).
   - **Match:** reuse curated baseline's `allergen_flags`, `dietary_flags`, `cultural_tags`, `cuisine_tags` (authoritative). Log `catalog.stage1.flag_disagreement` if any LLM-emitted flag differs (include `item_index`, NOT `canonical_name`). Keep LLM's `canonical_name` for display.
   - **No match:** use LLM-emitted tags as-is.

8. **Allergy guardrail filter.** Same pattern as `CuratedBaselineMaterializationService.runBatch()` in 2.6-s2:
   - Rules loaded once in step 2.
   - Call `evaluate([baselineToPlanItem(item, householdId)], rules)` — pure engine function, no DB round-trip.
   - `'cleared'` → keep. `'blocked'` → silently skip. `'uncertain'` → skip + log `catalog.stage1.guardrail_uncertain` with `item_index`.
   - `baselineToPlanItem()` is already implemented in `curated-baseline.service.ts` — do NOT duplicate it. Import and reuse it (or extract it to a shared helper in `apps/api/src/modules/catalog/catalog-guardrail-helper.ts` if both services need it).

9. **Persist survivors.** Call `RecipesRepository.seedFromCatalogBaseline(householdId, survivors)` — **this method already exists from 2.6-s2**. It inserts `recipes` (`source='catalog_seeded'`, `confidence_score=60`) + `household_recipe_usage` (`catalog_provenance='inferred'`). The only difference for Stage 1: LLM items get `confidence_score=50` (not 60 from baseline). Pass a custom `confidenceScore=50` parameter or add a separate `seedFromLLMItems()` method if `seedFromCatalogBaseline()` hardcodes 60. **Do NOT call `declareForHousehold()` — it sets provenance='declared' and confidence=80 (wrong for Stage 1)**.

10. **Log completion.** Log `catalog.stage1.completed` with `{ household_id, candidate_count: items.length, validated_count, guardrail_blocked_count, persisted_count, request_id }`.

11. **Set `stage1_completed_at`.** `await householdsRepo.setStage1CompletedAt(householdId)` — this is the signal 2.6-s4 polls. Set it regardless of post-guardrail count (zero survivors is a valid degraded state; don't retry forever).

## Dev Notes

### Why this slice exists (context from 2.6-s2)

Stage 0 (2.6-s2) materializes a "broad safe" curated baseline at household creation — ~50 generic, culture-agnostic items. Stage 1 (this slice) replaces the global default with a household-specific set of ~50 items calibrated to the family's M1-M4 signals. Stage 2 (2.6-s5) is a recovery path that fires only if Stage 1 produces < 35 survivors post-guardrail. The three-stage stack ensures every household has at least some catalog coverage entering M5.

**No UI change in this slice.** 2.6-s4 wires the M5 chip card to the catalog. Stage 1 only needs to ensure `households.stage1_completed_at` is set and survivors are in `recipes`+`household_recipe_usage` before 2.6-s4's 5s polling window expires.

`RecipesRepository.seedFromCatalogBaseline()` (2.6-s2) inserts `household_recipe_usage` with `confidence_score=60`.

**Choose option 1** (add optional param) — simpler, avoids duplication. Both the 2.6-s2 service and this service call the same method; 2.6-s2 calls with default (60), Stage 1 calls with `50`.

### Layer 2 integration — precise location in `PlansService`

The `materializeBeforeCommit()` private method is at approximately line 529. The `recipe_id !== undefined` branch is at approximately line 549-553. That is the insertion point.

**Key constraint:** `findById()` is a new DB call per plan item that has a `recipe_id`. For plans where all items already have full recipes (the common case), this adds N round-trips. To limit cost:
- Only call `findById()` when the item's `recipe_id` is present AND slot is `'main'`.
- If `findById()` returns `null` or `source !== 'catalog_seeded'`, skip the Layer 2 check immediately.
- The majority of plan items will have `source='agent_generated'` or `'imported'` (from existing 3-31 materialization), so the branch will short-circuit quickly.

If the performance cost is a concern, an alternative is to have the agent tool include a `is_catalog_seeded: true` flag in the plan item — but this requires a contract change. Stick with the DB check for now; optimize only if profiling shows it matters.

### LLM model choice for Stage 1

Use `gpt-4o` (not `gpt-4o-mini`). Rationale:
- Stage 1 must generate culturally-diverse, allergen-disciplined output for Somali / Yemeni / Tibetan / Caribbean cohorts.
- `gpt-4o-mini` has lower cultural knowledge depth and tends to produce Anglo-biased outputs for under-represented cuisines.
- The one-call-per-onboarding cost (~1 input + output = ~$0.02 per household) is acceptable vs. the M5 quality risk.

The `response_format: { type: 'json_object' }` pattern is already used in `recipe-agent.ts` at line 214. Follow the exact same pattern (no zodResponseFormat, just `json_object` + manual JSON.parse + Zod safeParse).

### Curated baseline deduplication — in-memory vs DB lookup

Two approaches:
1. **DB lookup per item:** `SELECT id FROM curated_baseline_items WHERE recipes_normalized_canonical_name(canonical_name) = normalize(item_name)`. One DB call per item = up to 50 calls.
2. **In-memory:** Load all active `curated_baseline_items` once at service start (same `findAllActive()` call from 2.6-s2), build a `Map<normalizedName, CuratedBaselineItemRow>`, look up each LLM item in the map.

**Use option 2 (in-memory).** The baseline table has ~50 rows. Load it once at the start of `seedForHousehold()`, build the lookup map, and reuse it for all 50 LLM items. This is the same pattern 2.6-s2 uses for the guardrail rules batch.

### Anti-patterns to reject

- **Do NOT** call `declareForHousehold()` for Stage 1 LLM items — wrong provenance and confidence score.
- **Do NOT** call `RecipeAgent.discover()` during Stage 1 seeding — Tavily is NOT part of Stage 1. Stage 1 is LLM-only (name+tags). Layer 2 (Tavily fetch) happens lazily at plan-commit time (AC8).
- **Do NOT** await the `catalogSeedQueue.add()` call in the onboarding turn — fire-and-forget only.
- **Do NOT** set `stage1_completed_at` if the LLM times out or response is invalid — leave it NULL so 2.6-s4 timeout triggers the cold-start fallback.
- **Do NOT** add a cron or scheduler for Stage 1 — it is triggered by M2 completion only.
- **Do NOT** import `CURATED_BASELINE` seed data array at runtime — read from DB via `CuratedBaselineRepository.findAllActive()`.
- **Do NOT** log `canonical_name` in error/warn events — even LLM-generated lunch names can be culturally identifying once combined with household allergen data.
- **Do NOT** modify `2.6-s2`'s `CuratedBaselineMaterializationService` behaviour to accommodate Stage 1 — it is done and tested; extend only its shared helper.

### Edge cases from brief rev 3

| Edge case | Handling |
|---|---|
| LLM emits item matching curated baseline with different allergen_flags | Curated baseline tags are authoritative; overwrite LLM flags; log `catalog.stage1.flag_disagreement` with item_index |
| LLM response schema-invalid or partial | Treat as Stage 1 failure; do NOT set `stage1_completed_at`; TODO comment for Stage 2 enqueue |
| Post-validation count < 10 | Log `catalog.stage1.floor_breach`; persist whatever survived; still set `stage1_completed_at` |
| Concurrent M3/M4 turn modifies household state mid-job | Stage 1 reads snapshot ONCE at job start and does not re-read; stale output accepted; Stage 2 recovery handles guardrail mismatches if they emerge at M5 |
| `catalog_seeded` recipe Layer 2 fails at plan-commit | Set `discover_failed_at`; throw; planner retries with alternate recipe; plan never commits with `ingredients=[]` |
| Non-catalog recipe at commit (source != `catalog_seeded`) | `findById()` returns quickly; Layer 2 branch skipped; existing behavior preserved |
| Stage 1 runs twice for same household (job retry) | Idempotency check on `stage1_completed_at` short-circuits; `ON CONFLICT DO NOTHING` handles any partial first-run rows |
