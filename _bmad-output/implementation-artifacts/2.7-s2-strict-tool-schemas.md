## Story

As a **HiveKitchen developer**,
I want to **route onboarding's 11 tool schemas through the same strict-JSON-Schema hardening the planner uses (`toStrictJsonSchemaParameters` / `makeNullable`), with null-stripping before each handler's Zod parse**,
so that **malformed tool args become structurally impossible, eliminating the error-recovery round-trips the agent currently pays (up to `MAX_TOOL_ITERATIONS=6`) and closing the exact failure class that broke every `plan.compose` until commit `bea6d4b`**.

---

## Acceptance Criteria

**AC1 — Tool serialization goes through the strict adapter.**
- `OnboardingAgent.toOpenAITools()` (`apps/api/src/agents/onboarding.agent.ts:99`) routes each tool's JSON Schema through `toStrictJsonSchemaParameters` / `makeNullable` / `addStrictConstraints` from `apps/api/src/agents/providers/openai.adapter.ts:97-178` — the same path the planner depends on.
- Tools are emitted with `strict: true` (or the adapter's equivalent), `additionalProperties: false`, and all properties listed in `required` per OpenAI strict-mode rules.

**AC2 — Optional/nullable fields are null-safe end to end.**
- Every optional/nullable Zod field on an onboarding tool serializes as `anyOf:[<schema>, {"type":"null"}]` (per memory `strict-tool-schema-nullable-rule`).
- Tool-call args are **null-stripped** before the handler's `Schema.parse(input)` so Zod does not reject the model-supplied nulls.
- A new test asserts both halves: the serialized schema contains the `anyOf:[…,null]` form for each optional field, AND a payload with explicit nulls parses cleanly after stripping.

**AC3 — Vocabulary validation stays at the handler boundary.**
- Allergen / dietary / cuisine / cultural tag validity remains a loose string in the JSON Schema (NOT a strict enum). `VocabularyService` continues to validate at the handler so the model receives a recoverable error message rather than a hard schema rejection. (This is deliberate per `packages/contracts/src/onboarding-tools.ts:27-30`.)

**AC4 — Recoverable error round-trips drop.**
- A previously-bounced malformed-arg fixture (one that today produces an `{error}` tool-result and a re-call) now succeeds on the first call.
- No increase in tool-loop iterations from spurious arg errors.

**AC5 — Refinements that don't serialize are still guarded.**
- `rule.set`'s `.refine` (custom_label xor non-custom) and `household.upsert`'s mutually-exclusive `declared_allergens` vs `declared_allergens_add` are NOT expressible in JSON Schema. Verify the handler-side throws still guard these after the strict transform (add/keep tests).

**AC6 — No behavior regression.**
- `apps/api/src/agents/onboarding.agent.test.ts` + `apps/api/src/agents/tools/onboarding.tools.test.ts` green; no change to tool count or intent.
- The `2.7-s1` golden eval stays green (structured outcomes unchanged).
- Root typecheck clean.

## Dev Notes

### Why this slice exists

This is the highest-risk *gap* in onboarding and a direct port of proven planner code. Onboarding currently calls `tool_choice:'auto'` with loose JSON Schema (`onboarding.agent.ts:236`); malformed args are caught only at the handler and bounced back to the model as an `{error}` tool-result, costing an extra round-trip each time. The planner already hardened this (Epic 3.5) using `openai.adapter.ts`. The nullable rule is non-negotiable: under strict mode OpenAI forces ALL properties `required`, so optional fields MUST be `anyOf:[schema,null]` and the nulls MUST be stripped before Zod — otherwise the model emits values that break parsing (this broke every `plan.compose` until `bea6d4b`).

### Patterns to follow

- **`apps/api/src/agents/providers/openai.adapter.ts:97-178`** — `toStrictJsonSchemaParameters`, `addStrictConstraints`, `makeNullable`. Reuse verbatim; do not reimplement.
- **The planner's pre-parse null-strip** — find where the planner strips nulls before its Zod parse and mirror it for the onboarding tool loop.
- Memory `strict-tool-schema-nullable-rule` — the canonical statement of this rule and how it was diagnosed (via the planner trace; onboarding gets its own trace in `s3`).

### Anti-patterns to avoid

- **Do not** put vocabulary (allergen/dietary/cuisine tags) into the JSON Schema as enums — that turns a recoverable, self-correcting error into a hard schema rejection. Keep vocab validation at the handler (AC3).
- **Do not** drop the handler-side `Schema.parse` — strict mode reduces but does not replace handler re-validation, and the `.refine` guards (AC5) live only at the handler.
- **Do not** change tool count, names, or intent — this slice is behavior-preserving; the `s1` eval must stay green.

### Edge cases captured in the brief (must be handled)

| Edge case | AC | Handling |
|---|---|---|
| Optional fields emitted without nullable form → invalid values | AC2 | `anyOf:[…,null]` + null-strip before Zod |
| Open-vocab fields (`food_preference.declare`, free-text labels) | AC3 | Stay loose strings, not strict enums |
| `.refine` constraints don't serialize to JSON Schema | AC5 | Handler-side throws retained + tested |
