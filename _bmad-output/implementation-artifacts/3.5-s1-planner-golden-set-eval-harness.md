## Story

As a **HiveKitchen engineer about to re-architect the allergen-critical plan-compose path**,
I want **a deterministic, CI-runnable golden-set eval harness that runs the planner against recorded household scenarios and asserts the composed plan is allergen-safe, fully covered, non-consecutive-Main, schema-valid, and within a cost/turn budget**,
so that **every later Epic 3.5 slice (forced structured output, handle-index, loop collapse) can be proven not to regress safety or behavior before it merges — replacing the reactive `planner-prompt-rollback.md` §10.7 production tripwire with a pre-merge gate**.

## Acceptance Criteria

1. **Deterministic harness, no live LLM, no network.** A new eval harness runs `DomainOrchestrator.planWeek(...)` against fixtures using a **fake `LLMProvider`** that returns pre-baked responses. No call reaches OpenAI/Anthropic, Redis, Supabase, or Tavily over the network. Aligns with the project-context testing rule: *"Agent Layer — unit-test orchestration logic with stubbed OpenAI responses. Test decisions … not LLM output verbatim."* Runs under the existing Vitest runner; a single entry (`runPlannerEval()` or the `*.eval.test.ts` suite) executes the full set.

2. **≥8 ratified household fixtures + 1 schema-invalid-stub fixture (9 total).** The cohort set (ratified by Menon 2026-06-24, do NOT trim) is exactly:
   1. Anglo single-child (baseline happy path)
   2. Multi-child with a declared FALCPA allergen — peanut **allergen-fork** (shared Main, one child's variation `removals:["peanut paste"]` + substitute)
   3. Halal + vegetarian intersection (stacked cultural constraints)
   4. Partial-week / day-scope (`plannedDays` set; mutually exclusive with `dayScope`)
   5. Cold candidate slate (forces the `recipe.search`/`discover` fallback path)
   6. Sovereignty `alternating` (rotate-tradition-by-day)
   7. High-activity Extra proposal (FR119 override on a named day)
   8. Banned-recipe present (a `recipes.banned` entry must NOT appear in output)
   9. **Schema-invalid stub** — the fake provider returns a malformed `plan.compose` tree on the FIRST turn, then a valid tree on the second, to pin the CURRENT self-correction behavior (so s2's removal of that branch is provably outcome-neutral).

3. **Assertion A — allergen-safe (the non-negotiable).** For every (child, day, slot) in the composed output, the **effective ingredient set** = `recipe.ingredients − variation.removals + variation.add_ons` contains NO allergen declared for that child. The child's effective allergen set = household-wide rules ∪ that child's own `declared_allergens` (matches `plan-generation.job.ts` `declaredAllergensByChildId` semantics and story 3-39's `buildCommitGuardrailInputs` effective-set walk). Fixtures carry a `recipeIngredients: Record<recipeName, string[]>` map so the assertion can compute effective sets without a DB.

4. **Assertion B — slot coverage.** Every **active** slot (per each child's `bag_composition`: Main always on; Extra per-child opt-in) has exactly one filled slot row with ≥1 child variation. Inactive slots produce NO row. Snack is server-assigned (not emitted by the planner) and is OUT of scope for this assertion.

5. **Assertion C — no-consecutive-Main.** No two adjacent composed days share the same Main (same `main_assignment_sequence`). A 2-day plan uses 2 distinct Mains; a 3+-day plan may reuse a Main but never on adjacent days. (Currently prompt-only/best-effort — PLANNER_PROMPT v2.6.0, no validator; this assertion is the first mechanical check of it.)

6. **Assertion D — schema-valid.** The planner's returned object parses `PlanComposeTreeOutputSchema` (from `@hivekitchen/contracts`) with no errors.

7. **Assertion E — cost/turn budget.** Per fixture, the harness records (a) total tool-call count, (b) `plan.compose` call count, (c) prompt + completion token totals (from the fake provider's `usage`), and asserts each is `<=` a per-fixture recorded ceiling. The recorded baseline numbers are committed in the fixture (this is the number s2/s3/s5 will later DROP — the eval measures the win, not just guards regressions).

8. **Characterization parity — zero planner behavior change.** The harness runs against the CURRENT `DomainOrchestrator.planWeek` / `PLANNER_PROMPT` / `plan.compose` code unmodified. Production files (`orchestrator.ts`, `planner.prompt.ts`, `plan.tools.ts`, `plan-generation.job.ts`) are NOT edited for behavior. If a minimal test seam is unavoidable (e.g., exporting an existing pure helper), it must be additive, non-behavioral, and called out in the Dev Agent Record. **Do NOT introduce a `PlannerContext` type** — fixtures use the existing `PlanWeekOptions` shape; the typed context object is s4's job.

9. **Prompt/model version pinned by content-hash.** Each eval run records a content hash of `PLANNER_PROMPT.text` + `PLANNER_PROMPT.version` + the resolved model tier string, alongside the run. The `// vX.Y.Z` changelog in `planner.prompt.ts` is annotated (comment only) as descriptive, not the safety mechanism.

10. **CI-runnable + green.** The suite is picked up by `pnpm test` / the API package's Vitest config, passes `pnpm typecheck` with zero new errors, and is green on all 9 fixtures. No new runtime/external dependency is added (Vitest + Zod are already in the repo).

## Dev Notes

### What this story IS and IS NOT
- **IS:** a test-only harness under `apps/api/src/agents/eval/`. Pure addition.
- **IS NOT:** any change to planner runtime behavior, prompt content, the tree contracts, or `plan.compose` logic. If you find yourself editing `orchestrator.ts`'s control flow, STOP — that is s2/s5, not s1.

### How `planWeek` runs (so you stub the right seam)
- `DomainOrchestrator.planWeek(opts: PlanWeekOptions)` builds messages `[system: PLANNER_PROMPT.text, user: contextLines.join('\n')]`, then loops up to `MAX_PLAN_ITERATIONS` (8) calling `this.completeWithMessages(messages, tools, {tier:'flagship', temperature:0.2, maxTokens:4096}, PLANNER_PROMPT.toolsAllowed)`. [Source: `apps/api/src/agents/orchestrator.ts:372–735`]
- `completeWithMessages` delegates to `provider.completeWithMessages(...)`. **Stub at the provider** — return an `LLMResponse` whose `toolCalls=[{ id, name:'plan.compose', arguments: <tree> }]`, `finishReason:'tool_calls'`, `content:''`, `usage:{promptTokens,completionTokens,...}`. [Source: `apps/api/src/agents/providers/llm-provider.interface.ts`]
- When the model returns `plan.compose`, the orchestrator runs `TOOL_MANIFEST.get('plan.compose').fn(args)` → resolves recipe names via `recipeService.findIdByName` → `planService.composeTree(parsed)` → validates output with `PlanComposeTreeOutputSchema`. [Source: `apps/api/src/agents/tools/plan.tools.ts:18–86`]
- The planner's allowed tools are ONLY `recipe.search`, `recipe.fetch`, `recipe.discover`, `plan.compose` [Source: `apps/api/src/agents/prompts/planner.prompt.ts:281–290`]. So your `OrchestratorServices` doubles only need `recipe` + `plan` to be functional for the happy path; the cold-slate fixture (#5) additionally exercises `recipe.search`/`discover` — stub those tool results in the fake provider's response queue plus the `recipe` service double.

### Allergen assertion must match production semantics (AC3)
- Effective set per (child, day, slot) = recipe ingredients `−` `variation.removals` `+` `variation.add_ons`. This mirrors story 3-39's `PlansService.buildCommitGuardrailInputs` and the commit-time guardrail — do NOT assert on surface slot ingredients only, or the allergen-fork fixture will false-pass. [Source: brief §1 evidence 1; sprint-status `3-s39` entry; `apps/api/src/modules/allergy-guardrail/allergy-rules.engine.ts`]
- Child's effective allergen set = household-wide rules/allergens ∪ child's own `declared_allergens` — exactly the `declaredAllergensByChildId` build in `plan-generation.job.ts:457–466`.
- Reuse the engine's matching semantics (synonyms, FALCPA canonical keys); do not invent a new matcher. [Source: `allergy-rules.engine.ts`; memory `allergen-storage-model`]

### Reuse, don't reinvent
- KitchenMap / ChildSignalOutput / candidate-slate fixture builders already exist in `orchestrator.test.ts`, `orchestrator.planweek.test.ts`, and `plan.tools.test.ts` — copy their shapes so fixtures stay contract-aligned. [Source: `apps/api/src/agents/orchestrator.planweek.test.ts`]
- `PlanComposeTreeOutputSchema` / `PlanComposeTreeInputSchema` come from `@hivekitchen/contracts` via `@hivekitchen/types` — never hand-write the tree type. [project-context: "No hand-written types that duplicate a contract"]
- Tree shape reference (main_assignments + days[].slots[].variations; slot_kind main|extra; snack server-assigned) is documented verbatim in `PLANNER_PROMPT` [Source: `planner.prompt.ts:51–229`].

### Testing standards (project-context)

- Editing planner control flow / prompt content to make a fixture pass (that inverts the point — fixtures characterize current behavior).
- Introducing `PlannerContext` or extracting renderers (that is s4).
- Adding a dependency (assertion lib, snapshot lib) — Vitest's `expect` + Zod suffice.

### Completion Notes List

- **Harness reuses the existing `orchestrator.planweek.test.ts` pattern.** A `FakeLLMProvider` replays a fixture's queued `LLMResponse`s; the REAL `DomainOrchestrator.planWeek` + REAL `plan.compose` tool (input/output schema validation + name resolution) run against them. Recipe/Plan service DOUBLES make `plan.compose` runnable offline: `recipe.findIdByName` is identity (resolves a name to itself so assertions map recipe→ingredients without a DB; production resolves to a catalog UUID), `plan.composeTree` echoes the parsed input tree as an output tree with a deterministic `plan_id`.
- **Allergen assertion reuses the REAL engine** (`evaluate` from `allergy-rules.engine.ts`) so the matcher + FALCPA synonym expansion stay identical to the commit-time guardrail (story 3-39). Effective set = `ingredients − removals + add_ons`. Per-child semantics: a child's declared allergens are passed as `rule_type:'falcpa'` rules (so the engine's fail-closed baseline check passes — matching is identical regardless of `rule_type`); children with no declared allergens are skipped (vacuously safe).
- **RECONCILIATION (Task 4 / AC8) — self-correction characterization.** The story sketch suggested asserting the schema-invalid fixture produces a `planner.bad_output` audit. On inspection those are two DISTINCT orchestrator branches: (a) the **recoverable** path fires when the tool `fn` THROWS a ZodError on malformed *input* args (`orchestrator.ts:609-666`) — fed back, no audit; (b) the **fatal** `planner.bad_output` audit fires only when the tool RETURNS unparseable *output* (`orchestrator.ts:680-701`) — which throws. The realistic "model emitted malformed args, loop recovered (costing a turn)" behavior — exactly what s2's forced schema eliminates — is path (a). Fixture #9 therefore characterizes path (a): malformed first emission → real `PlanComposeTreeInputSchema` throws → fed back → valid second turn. The explicit test asserts `turns === 2` and `planComposeCalls === 2` (the extra-turn cost s2 will remove). Asserting a `bad_output` audit on the recoverable fixture would have been incorrect.
- **Negative assertion tests included** — six tests prove each assertion actually rejects the unsafe/incorrect shape it guards (a safety net that never fails is worthless). Plus a positive fork test proving the allergen assertion passes when a removal strips the allergen.
- **AC9 prompt-hash** implemented via `recordPromptHash()` (sha256 of `PLANNER_PROMPT.version` + text + tier) with a determinism test; a one-line non-behavioral pointer comment was added to `planner.prompt.ts` (the only production-file touch — additive, comment-only, per AC8).
- **No new dependencies** (Vitest + Zod already present). **No `PlannerContext` introduced** (that is s4). Determinism: no `Date.now()`/`Math.random()`; all timestamps are fixed literals.
- Vitest file isolation (default) means the harness's per-fixture `TOOL_MANIFEST` mutation does not leak to other test files; each fixture run reconstructs the orchestrator (which resets the manifest to real specs).
