## Story

As a **parent completing Moment 5 of onboarding**,
I want **the chip card to surface ~18 lunch ideas drawn from my household's personalized catalog (Stage 0 baseline + Stage 1 LLM seed), instead of a static global list**,
so that **Lumi's first impression matches my family's actual food world — Anglo households see sandwiches and pasta, Somali households see anjero and bariis, allergen-blocked items never appear, and the *"only suggests things that fit"* promise is kept from the first cold-start gesture**.

The wire format flips at the same time: chip `key` carries the `recipe_id` (UUID), chip `label` carries the canonical_name (display string). The static 18-chip catalog inside `momentToChipConfig('m5_starting_line')` and the `KEY_LABEL` map in the agent prompt are deleted in this slice.

```ts

```

Pipeline:
1. **Stage 1 wait.** Read `households.stage1_completed_at`. If non-null → proceed. If null → poll every 250ms for up to **5000ms total** until non-null. If still null at timeout, log `catalog.m5.stage1_timeout` with `{ household_id }` and proceed anyway (Stage 0 baseline rows are usable on their own; 2.6-s6 will later route to a cold-start conversational fallback). Leave a `// TODO(2.6-s6): cold-start fallback on stage1 timeout + below-threshold result` comment at the timeout branch.
2. **Catalog query.** Single SELECT:
   ```sql
   SELECT
     r.id, r.canonical_name, r.cuisine_tags, r.cultural_tags,
     hru.catalog_provenance, hru.confidence_score,
     hru.is_household_favorite, hru.is_household_banned
   FROM household_recipe_usage hru
   JOIN recipes r ON hru.recipe_id = r.id
   WHERE hru.household_id = $1
     AND hru.is_household_banned = false
   ```
   Implementation goes through `KitchenMapRepository` or a dedicated query method on `RecipesRepository` — do NOT call supabase-js from this service directly (per project conventions; all DB reads go via a repository).
3. **Sort.** Stable sort applied in TS (not SQL) so the priority weights stay readable:
   - `is_household_favorite` DESC (true first)
   - `provenancePriority(catalog_provenance)` DESC — `declared = 4`, `parent_added = 3`, `inferred = 2`, `plan_promoted = 1` (per brief AC4)
   - `confidence_score` DESC
   - `r.id` ASC (deterministic tie-breaker)
4. **Diversity cap (max 3 per cuisine).** Walk the sorted list; for each candidate, reject if ANY of its `cuisine_tags` is already at the cap of 3 in the accumulator. A recipe with two cuisine tags counts toward both. Take items until the accumulator hits 18 OR the input is exhausted.
5. **Underflow relax (max 5 per cuisine).** If the accumulator has fewer than 12 items after step 4, re-walk with the cap relaxed to 5 per cuisine. Log `catalog.m5.diversity_relaxed` with `{ household_id, after_step4: <n>, after_relax: <m> }`. Take items until 18 OR exhausted.
6. **Below-threshold log.** If the final result is fewer than 12 items, log `catalog.m5.below_threshold` with `{ household_id, final_count }`. Leave a `// TODO(2.6-s6): route to cold-start fallback when below_threshold fires` comment. Still return the partial result — never throw, never return null.
7. **Project to ChipOption[].**
   ```ts
   { key: r.id, label: r.canonical_name, provenance: hru.catalog_provenance }
   ```
   `key` is the UUID; `label` is the canonical_name verbatim.

`provenancePriority(): number` is a private pure function in the service file. No DB call.

## Dev Notes

### Why this slice exists

`2.5-s9` shipped the M5 chip card with a static 18-key catalog (`paratha-roll`, `dal-rice-thermos`, ...). The catalog was Anglo-Western-with-some-South-Asian and broke Lumi's *"only suggests things that fit"* promise for Somali / Yemeni / Tibetan / sub-regional cohorts. Slices 2.6-s1 (foundation), 2.6-s2 (Stage 0 baseline), 2.6-s3 (Stage 1 LLM seeding) built a per-household catalog in `recipes` + `household_recipe_usage`. This slice is the user-visible payoff: the M5 chip card reads from that catalog at turn-time and serves chips that match the household's M1–M4 signals.

After this slice, the brief's Epic 2.6 MVP wall is satisfied. Slices 2.6-s5 and 2.6-s6 are robustness paths (Stage 2 recovery; cold-start fallback) that can ship after.

### Mock authority

The cohort-variant mockup is **already authored** at `apps/web/src/features/onboarding-mockups/Moment5PersonalizedPage.tsx`. Two cohorts (Anglo / Somali) demonstrate the design range. The mockup is the design source of truth for:
- Per-chip `provenance` styling — leading `＋` badge for `parent_added`, no badge for `inferred` / `declared`
- The `ChoiceChip` primitive's `icon` slot is the integration point (it's already shipped in the production codebase per 2.5-s3)
- Count indicator + gate-line copy stay unchanged from 2.5-s9 (mockup confirms this)
- The chip card's parent UI (focused mode, profile card, history toggle) stays unchanged from 2.5-s9

**Out of scope from the mockup:** the `ProvenanceBreakdown` footer ("Catalog provenance (internal, not user-visible)") is a mockup-only design annotation — do NOT render it in production. The mockup's `CohortToggle` is dev-only and does not ship.

### Wire-format flip explained

Today (2.5-s9): chip = `{ key: 'paratha-roll', label: 'Paratha roll' }`. Client sends `chip_selections: ['paratha-roll', ...]`. Agent receives the slugified keys and translates via the prompt's hardcoded `KEY_LABEL` map.

After this slice: chip = `{ key: <recipe_id_uuid>, label: <canonical_name>, provenance: 'inferred' | ... }`. Client sends `chip_selections: ['<uuid>', ...]`. The agent does NOT translate keys — the chip's `label` field carries the lunch name, and the agent passes the label through verbatim to `favorite_lunch.add`.

**The translation is gone, not relocated.** The agent never sees the recipe_id in this design; it receives the chip selection key (UUID) as part of the user message and the label is delivered alongside via the chip payload. The agent's job is to fire one `favorite_lunch.add` per selected chip with the label.

**Why label-based, not id-based, at the tool boundary?** `declareForHousehold(householdId, label)` already handles the label → recipe_id resolution via the `recipes_household_normalized_name_uniq` UNIQUE conflict-recovery path (per 2.6-s1). When the label matches the Stage-1-emitted `canonical_name`, the conflict path finds the existing `recipes.id` and flips `household_recipe_usage` from `'inferred'` to `'declared'`. Adding a recipe-id-based tool input doubles the surface for marginal benefit; defer to a follow-up if the label-collision edge case shows real failures.

### Stage 1 wait — implementation detail

Polling pattern, not Postgres `LISTEN`:
```ts
const POLL_INTERVAL_MS = 250;
const POLL_TIMEOUT_MS = 5000;
const start = Date.now();
let stage1At = await this.householdsRepo.getStage1CompletedAt(householdId);
while (stage1At === null && Date.now() - start < POLL_TIMEOUT_MS) {
  await new Promise((r) => setTimeout(r, POLL_INTERVAL_MS));
  stage1At = await this.householdsRepo.getStage1CompletedAt(householdId);
}
if (stage1At === null) {
  this.logger.info(
    { module: 'catalog', action: 'catalog.m5.stage1_timeout', household_id: householdId },
    'M5 chip projection: Stage 1 timeout — falling through with current catalog',
  );
  // TODO(2.6-s6): cold-start fallback on stage1 timeout + below-threshold result
}
```

`HouseholdsRepository.getStage1CompletedAt(householdId): Promise<string | null>` already exists (added in 2.6-s3). Reuse it directly.

**Why polling, not pub/sub:** the wait is per-request, scoped to the turn handler. BullMQ + Postgres `LISTEN/NOTIFY` would add infrastructure for a 5-second blocking wait. Polling at 250ms = 20 reads max in the worst case, each a single-row indexed SELECT. Cost: trivial.

### Catalog read query placement

Two options for where the chip-row read lives:

1. **Extend `RecipesRepository`** with `findCatalogProjectionForHousehold(householdId)` returning the joined row shape. Pattern: the existing `recipes.repository.ts` has lots of per-purpose methods (`findById`, `seedFromCatalogBaseline`, etc.) — adding one more fits.
2. **Reuse `KitchenMapRepository`** which already has the same join pattern (`USAGE_JOIN_COLUMNS` was extended in 2.6-s1 to include `catalog_provenance`).

**Prefer option 1** (new `RecipesRepository` method). Kitchen Map's query is shaped for the full Kitchen Map projection (also reads cultural priors, dietary, children, etc.) — heavier than M5 needs, and tying M5 to the Kitchen Map's query cycle creates a confused dependency. A dedicated single-purpose method is cheaper and easier to test.

Implementation skeleton:
```ts
// apps/api/src/modules/recipe/recipes.repository.ts

async findCatalogProjectionForHousehold(
  householdId: string,
): Promise<Array<{
  id: string;
  canonical_name: string;
  cuisine_tags: string[];
  cultural_tags: string[];
  catalog_provenance: CatalogProvenance;
  confidence_score: number;
  is_household_favorite: boolean;
}>> {
  const { data, error } = await this.client
    .from('household_recipe_usage')
    .select(`
      catalog_provenance, confidence_score, is_household_favorite,
      recipes!inner ( id, canonical_name, cuisine_tags, cultural_tags )
    `)
    .eq('household_id', householdId)
    .eq('is_household_banned', false);
  if (error) throw error;
  return (data ?? []).map((row) => ({
    id: row.recipes.id,
    canonical_name: row.recipes.canonical_name,
    cuisine_tags: row.recipes.cuisine_tags,
    cultural_tags: row.recipes.cultural_tags,
    catalog_provenance: row.catalog_provenance,
    confidence_score: row.confidence_score,
    is_household_favorite: row.is_household_favorite,
  }));
}
```

### Sort tie-breaker rationale

`r.id ASC` is the final tie-breaker to make the sort deterministic. Without it, two rows with identical favorite/provenance/confidence would have unstable ordering across requests, producing different chip sets on retry. Deterministic order = reproducible bug reports.
