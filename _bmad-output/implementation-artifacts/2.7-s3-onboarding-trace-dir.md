## Story

As a **HiveKitchen developer**,
I want to **add a per-turn onboarding trace facility (`ONBOARDING_TRACE_DIR`) mirroring the planner's `PLAN_TRACE_DIR` / `plan-tracer.ts`, capturing the assembled prompt, dynamic blocks, tool calls, token usage, and moment-state before/after**,
so that **debugging a bad interview stops being Pino-log archaeology and the riskiest later slices (the control inversion) can be diagnosed against a captured per-turn artifact — the same tool that cracked the planner's strict-schema bug**.

---

## Acceptance Criteria

**AC1 — New tracer mirrors the planner's.**
- New `apps/api/src/agents/onboarding-tracer.ts` (or co-located with the planner tracer) following `plan-tracer.ts`'s structure and write semantics.
- Env-gated by a new `ONBOARDING_TRACE_DIR` in `apps/api/src/config/env.ts`, **off by default**.

**AC2 — Zero cost when unset.**
- When `ONBOARDING_TRACE_DIR` is unset/empty, no artifact is written and no measurable per-turn latency is added (the trace assembly is skipped, not just discarded).

**AC3 — Per-turn artifact captures the full picture.**
Each artifact (one per text turn) contains:
- The assembled system prompt AND the three dynamic blocks rendered service-side: Kitchen Map, moment-state, vocabulary (`onboarding.service.ts:1957-2100` via `renderKitchenMapBlock` / `renderMomentStateBlock` / `renderVocabularyBlock`).
- Each tool call with args + result (incl. error-results).
- Model + token usage from `OnboardingAgentUsage` (`onboarding.agent.ts:23-35`), including `cachedPromptTokens` (`cachedPromptTokensFromUsage`).
- Moment-state before and after the turn.

**AC4 — Writes are off the hot path.**
- Trace writes are async / fire-and-forget (or otherwise non-blocking) so a trace IO failure never affects the turn response. A failed write logs a warning and is swallowed.

**AC5 — Tests + no regression.**
- Test: with the var set (to a temp dir), one artifact per turn containing all AC3 fields; with it unset, no artifact and no added work.
- The `2.7-s1` golden eval stays green; existing onboarding tests green; root typecheck clean.

## Dev Notes

### Why this slice exists

There is no onboarding-specific trace today (brief §1 evidence #3). Onboarding observability is entirely Pino structured logs (`onboarding.text_turn_usage`, `onboarding.moment_state_updated`, etc.). The planner's `PLAN_TRACE_DIR` is precisely the tool that let the team diagnose the strict-schema bug fixed in `bea6d4b` (per memory `strict-tool-schema-nullable-rule`). The control inversion in `s6`/`s7` is the riskiest change in the epic; landing the trace dir first makes it diagnosable. This is a near-verbatim port of the planner tracer.

### Patterns to follow

- **`plan-tracer.ts` / `PLAN_TRACE_DIR`** — file naming, JSON artifact shape, async writes, env gating. Mirror it so the two tracers are symmetric.
- **`OnboardingAgentUsage` (`onboarding.agent.ts:23-35`)** + `cachedPromptTokensFromUsage` (`:79-87`) — the usage shape to record (includes OpenAI prompt-cache hits).
- **`renderKitchenMapBlock` / `renderMomentStateBlock` / `renderVocabularyBlock` (`onboarding.service.ts:1957-2100`)** — the three dynamic blocks; capture what's already assembled for the prompt.

### Anti-patterns to avoid

- **Do not** block the turn response on a trace write (AC4) — async/swallow-on-error.
- **Do not** do trace work when the env var is unset (AC2) — guard before assembling, not after.
- **Do not** recompute the dynamic blocks just to trace them — reuse the values already built for the prompt.
- **Do not** include PII beyond what the prompt already contains; follow the existing PII-redaction discipline in onboarding logs where applicable.

### Edge cases captured in the brief

| Edge case | AC | Handling |
|---|---|---|
| Trace var unset in prod | AC2 | No-op fast path, zero added latency |
| Trace IO failure mid-turn | AC4 | Async + swallow + warn; never affects the response |

### Project Structure Notes

- Tracer co-located with the planner tracer (or `apps/api/src/agents/onboarding-tracer.ts`).
- Env in `apps/api/src/config/env.ts:59-64` neighborhood (`ONBOARDING_AGENT_TOOLS_ENABLED` lives there).
- No migration, no contracts, no web change.

Replaced the two inline duplicate types with the agent's exported `OnboardingAgentUsage` / `OnboardingToolCallSummary`.

**Deviations (sound, documented)**
1. **JSON artifact, not the planner's `.txt`.** The planner tracer actually writes a human-readable TXT log; the story Dev Notes/Task 3 call for "JSON artifact shape" and a `.json` filename, and AC3 enumerates discrete fields. JSON is the explicitly-requested format and makes the AC3 fields directly assertable — chosen over byte-mirroring the planner's TXT.
2. **`systemPrompt` captured as base + 3 blocks separately** (not a single pre-assembled string). The full system prompt is assembled *inside* the agent (`buildToolSystemPrompt`); recording the base prompt + each block separately gives a reader the same content without duplicating the agent's concatenation logic or reaching into the agent.
3. **Extended `OnboardingToolCallSummary` with `args`/`result`.** AC3 requires per-tool args + result, but the existing summary carried only `{tool, error}`. Extending it is the minimal carrier; the four 2.7-s2 agent tests that asserted the exact `{tool, error}` shape via `toEqual` were updated to `toMatchObject` (intent unchanged — which tool, error flag).
4. **`write()` returns `Promise<void>`** (callers `void` it). Fire-and-forget in the service (AC4); the returned promise exists only so the tracer unit test can await deterministically. The service-wiring test uses `vi.waitFor` (event-driven, no sleep).
5. **Tracer reads `process.env` directly even though it's in `env.ts`.** This mirrors `createPlanTracer` exactly (symmetry was an explicit story goal) and keeps the test toggle pattern identical to `plan-tracer.test.ts`. The `env.ts` entry documents/validates the var.
