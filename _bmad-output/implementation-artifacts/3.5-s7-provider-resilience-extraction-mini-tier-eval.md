## Story

As a **HiveKitchen engineer isolating the planner's provider-resilience concerns from its domain orchestration logic**,
I want **a `providers/resilience.ts` `ResilientProvider` decorator that owns the 429-retry loop, circuit-breaker state, and provider-switching logic, while `DomainOrchestrator` delegates to it transparently**,
so that **the orchestrator's domain code is free of retry/failover plumbing, both concerns are independently tested, and a mini-tier live eval gives us a data-driven answer on whether compose can drop from flagship to mini (NFR-COST-3)**.

### AC2 — 429 retry loop + circuit-breaker accounting in `completeWithMessages`

`ResilientProvider.completeWithMessages(messages, tools, options)` implements the retry loop extracted from `orchestrator.completeWithMessages()`:

```
for (let attempt = 0; ; attempt++) {
  try {
    result = await providers[currentProviderIndex].completeWithMessages(messages, tools, options);
    this.breaker.recordSuccess();
    return result;
  } catch (err) {
    const isRateLimit = err != null && typeof err === 'object' && 'status' in err
      && (err as { status: number }).status === 429;
    if (isRateLimit && attempt < MAX_RATE_LIMIT_RETRIES) {
      // Parse x-ratelimit-reset-tokens header — two formats:
      //   "54.726s"      → seconds only → parseFloat(secMatch[1])
      //   "1m21.587s"    → minutes+seconds → parseInt(m)*60 + parseFloat(s)
      // Default when header absent: 90 s
      // waitMs = Math.ceil(resetSec * 1000) + 1000  (+1s buffer)
      // logger.warn({ attempt, waitMs, resetTokensHeader }, '...')
      // await new Promise<void>((resolve) => setTimeout(resolve, waitMs))
      // continue (breaker NOT incremented on 429)
    }
    this.breaker.recordFailure();
    throw err;
  }
}
```

**Key invariant: `breaker.recordFailure()` is NOT called on a 429 rate-limit error** — 429 indicates API throttling, not a provider outage. The circuit-breaker fires only on non-429 errors.

**`ResilientProvider.complete(prompt, tools, options)` — circuit-breaker accounting, NO retry loop:**
```ts
try {
  const result = await providers[currentProviderIndex].complete(prompt, tools, options);
  this.breaker.recordSuccess();
  return result;
} catch (err) {
  this.breaker.recordFailure();
  throw err;
}
```

### AC3 — Recovery probe race guard preserved

`handleRecoveryAttempt()` in `ResilientProvider` MUST preserve the guard verbatim:

```ts
private async handleRecoveryAttempt(): Promise<void> {
  if (this.currentProviderIndex === 0) return;   // ← RACE GUARD: must not be removed
  ...
}
```

This guard prevents a stale recovery callback (e.g., one that fires after `currentProviderIndex` was already reset by a manual action) from probing the primary unnecessarily. Even if the circuit breaker schedules the recovery timeout, if the orchestrator is already back on the primary provider, the probe is skipped.

### AC6 — `providers/resilience.test.ts` — unit tests

New file `apps/api/src/agents/providers/resilience.test.ts`. All tests use `vi.fn()` stubs — no real network calls.

**429 retry tests (at least 4 cases):**

1. **`"54.726s"` header → correct wait:** stub provider throws `{ status: 429, headers: { 'x-ratelimit-reset-tokens': '54.726s' } }` on first attempt, resolves on second. Assert: provider was called twice; wait was `Math.ceil(54.726 * 1000) + 1000 = 55726` ms (use `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync(55726)`).

2. **`"1m21.587s"` header → correct wait:** throw with `'1m21.587s'` → wait = `Math.ceil((60 + 21.587) * 1000) + 1000 = 82587` ms.

3. **No header → 90s default:** throw 429 with no `headers` on error → wait = `Math.ceil(90 * 1000) + 1000 = 91000` ms.

4. **Non-429 error → does NOT retry, propagates immediately:** throw `{ status: 500 }` → provider called once, error re-thrown, circuit-breaker `recordFailure` called (assert `onFailover` fires after threshold).

5. **Retry limit: after `MAX_RATE_LIMIT_RETRIES` retries (3) on 429, propagates:** provider throws 429 four times → retried 3 times → 4th throw propagates; `breaker.recordFailure()` called on the final throw.

**Circuit-breaker / failover tests (at least 3 cases):**

6. **5 failures → `onFailover` fires with (from, to, reason):** call `resilient.complete()` 5 times with a throwing provider → `onFailover` called once with `from='primary', to='fallback', reason=...`.

7. **Success resets failure count:** 4 failures, then success → breaker NOT tripped; `onFailover` NOT called.

8. **`getStatus()` reflects active provider and circuit state:** initial state → `active_provider='primary', circuit_open=false, providers=['primary','fallback']`. After failover → `active_provider='fallback', circuit_open=true`.

**Recovery probe race guard test (1 case):**

9. **Race guard — `handleRecoveryAttempt` no-ops when already on primary:** trigger recovery timer when `currentProviderIndex === 0` (simulate a stale timer firing after manual reset). Assert: `probe()` is NOT called on the primary provider.

**`supportsStrictTools()` delegation (1 case):**

10. **Delegates to active provider:** primary returns `supportsStrictTools() = true`; after failover to fallback (which returns `false`); `resilient.supportsStrictTools()` returns `false`.

**`completeWithMessages` circuit-breaker accounting (1 case):**

11. **429 does NOT trigger circuit-breaker recordFailure:** provider throws 429 once then succeeds; assert `onFailover` never fires (recordFailure was not called for the 429).

### Recovery probe race guard — why it matters

After `handleBreakerOpen()` fires and swaps to the secondary, the circuit breaker schedules the `recoveryMs` (900s) timer. When it fires, `handleRecoveryAttempt()` runs. But if `currentProviderIndex` has already been reset to 0 by some other code path (unlikely today but defensive), re-probing is wasteful and potentially confusing. The guard `if (this.currentProviderIndex === 0) return;` is the original defensive check — do not remove it.

### Mini-tier eval: service doubles compatibility with real model

The `makeRecipeDouble()` function in the harness uses `findIdByName: async (value) => value`. When the real gpt-4o-mini model emits a recipe name (e.g. `"Chicken Tacos"`) instead of a handle-formatted name, `findIdByName` returns `"Chicken Tacos"` as the UUID. This is fine for the eval: allergen checks look up by the returned ID in `fixture.recipeIngredients`, so the fixture's ingredients map must use the same format the model produces.

**Important caveat:** The golden fixtures' `recipeIngredients` maps are keyed by stub-response recipe names (the ones in `fixture.stubResponses`). For the LIVE eval, the real model may use different names. This means the `assertAllergenSafe` check in the live eval will find most recipe IDs NOT in `fixture.recipeIngredients` — resulting in an empty ingredient set → passes by default (no false positives). The allergen check is conservative here: it only blocks if it finds a known-allergen ingredient.

Document this caveat in the test file's header comment:
```ts
// NOTE: allergen assertions in the live eval are best-effort. The
// recipeIngredients map from each fixture is keyed by the recipe names
// used in the stub responses; the real model emits different names, so
// most ingredient lookups will return undefined → treated as empty set →
// pass. The hard safety guarantee remains the commit-time guardrail (3-39).
// This eval's primary purpose is plan-structure validity and cost-per-turn
// measurement, not ingredient-level allergen testing.
```
