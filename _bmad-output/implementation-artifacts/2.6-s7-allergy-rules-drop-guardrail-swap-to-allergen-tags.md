# Story 2.6-s7 — Drop `allergy_rules`, swap allergy guardrail to read FALCPA seeds from `allergen_tags`

**Status:** done
**Epic:** 2.6 — Personalized Onboarding Catalog
**Created:** 2026-05-24
**Author:** Drafted by Claude Code during Epic 2.6-s1 code review; surfaced by Menon

---

## Summary

The `allergy_rules` table now contains **only FALCPA system seeds** (9 rows, `household_id IS NULL`). Parent-declared allergen rules were migrated out of this table to `households.declared_allergens` / `children.declared_allergens` in story 2-s27. The identical FALCPA allergen vocabulary already exists in `allergen_tags WHERE rule_class='falcpa'` — the canonical vocabulary table created in migration `20260820000100`. `allergy_rules` is redundant and creates confusion about where the authoritative FALCPA list lives.

This story:
1. Swaps `allergy-guardrail.repository.ts` to read FALCPA seeds from `allergen_tags WHERE rule_class='falcpa' AND is_active=true`
2. Updates `FALCPA_SYNONYMS` and `FALCPA_TOP_9` in the engine to use `allergen_tags.key` format as canonical (the old keys had 4 mismatches — `peanuts`, `tree_nuts`, `milk`, `eggs` — vs `peanut`, `tree_nut`, `dairy`, `egg` in `allergen_tags`)
3. Drops `allergy_rules` via a new migration

---

## Context and Motivation

The `allergy_rules` table was created in story 3.1 (`20260610000000_create_allergy_guardrail_tables.sql`) as the combined source for:
- FALCPA reference rows (`household_id IS NULL`, `rule_type='falcpa'`)
- Parent-declared household/child rules (`household_id NOT NULL`, `rule_type='parent_declared'`)

Story 2-s27 moved parent-declared rules to encrypted columns on `households` and `children`, making `allergy_rules` a FALCPA-only table. The vocabulary table `allergen_tags` (created `20260820000100`) was introduced later and already contains the same 9 FALCPA allergens under `rule_class='falcpa'`. The two tables now duplicate the same information.

This redundancy has been raised multiple times. The ticket was deferred until Epic 2.6 stabilized the catalog schema. The catalog work (s1) is now in code review; this is the right time to close the gap.

## Key Technical Finding — Key Mismatch

The `allergy_rules` FALCPA rows use different allergen string values than `allergen_tags.key`:

| `allergy_rules.allergen` | `allergen_tags.key` | `allergen_tags.alias_keys` |
|--------------------------|---------------------|----------------------------|
| `peanuts` | `peanut` | `['groundnut','arachis']` |
| `tree_nuts` | `tree_nut` | `['treenut']` |
| `milk` | `dairy` | `['milk','lactose']` |
| `eggs` | `egg` | `['eggs']` |
| `wheat` | `wheat` | `[]` |
| `soy` | `soy` | `['soya','soybean']` |
| `fish` | `fish` | `[]` |
| `shellfish` | `shellfish` | `['crustacean','mollusc']` |
| `sesame` | `sesame` | `[]` |

The engine (`allergy-rules.engine.ts`) expands FALCPA allergen strings using `FALCPA_SYNONYMS`. The lookup key in `FALCPA_SYNONYMS` is the allergen string itself (e.g., `FALCPA_SYNONYMS['peanuts']` returns `['peanut', 'groundnut', ...]`). If we read `allergen_tags.key = 'peanut'` from the DB and pass `allergen: 'peanut'` to the engine, `FALCPA_SYNONYMS['peanut']` would return `undefined` — **the synonym expansion would silently break**, reducing guardrail coverage.

**Fix:** Update `FALCPA_SYNONYMS` keys (and `FALCPA_TOP_9`) in the engine to use the canonical `allergen_tags.key` format. Move the old string values (e.g., `peanuts`, `tree_nuts`, `milk`, `eggs`) into the synonym lists to preserve backward compatibility with any existing ingredient-string matches that rely on them.

This is a net safety improvement:
- `dairy` canonical key + `milk` in synonyms → catches both `'dairy-free spread'` and `'skim milk'` in ingredients (current `milk` key catches only `milk`-containing strings)
- `peanut` canonical key + `peanuts` in synonyms → catches both `'peanut butter'` and `'chopped peanuts'` (current `peanuts` key MISSES `'peanut butter'` — this is a latent bug fixed by this story)

`FALCPA_SYNONYMS` is only used internally within `allergy-rules.engine.ts`; it is not imported elsewhere (verified by grep). `FALCPA_TOP_9` is exported but has no external imports (verified).

### AllergyRule type compatibility

`AllergyRule.id` is typed as `string` (non-optional). The `allergen_tags` table has a `key` (text PK) but no UUID. Set `id: row.key` in the mapping (AC2). The engine never reads `id` in `evaluate()` — the field only matters for `Conflict` output which uses `allergen`, not `id`.

Alternatively, if the `AllergyRule` type is too strict and a cleaner solution is preferred, `id` can be made `id?: string` in the engine type definition — but only do this if the engine type genuinely doesn't need `id`. Do not gold-plate; the `id: row.key` approach is fine.

### RULE_COLUMNS removal

`RULE_COLUMNS = 'id, household_id, child_id, allergen, rule_type'` — this constant is only used on line 62 for the `allergy_rules` query. Once the query is replaced, this constant is unused. Remove it.

### `is_active` filter

The new query filters `is_active = true`. This is intentional: if a FALCPA allergen is administratively deactivated in `allergen_tags` (unlikely but possible), the guardrail should reflect that. The existing `allergy_rules` table had no equivalent concept — rows were either there or deleted. This is a correct improvement.

### Comment update in repository

The multi-line comment on lines 54–60 of the repository describes the old `allergy_rules` read pattern ("We still read the table for the FALCPA reference rows"). Update this comment to describe the new `allergen_tags` read. Keep it short — one sentence.

### Migration sequencing

The `allergy_rules` table has no FK dependencies from other tables (only its own FK to `households` and `children`, which are ON DELETE CASCADE dependencies). Dropping it is safe at any point after the code no longer references it.

This migration ships AFTER the 2.6-s7 code change is deployed (code is deployed, referencing `allergen_tags`; then migration drops the now-dead table). Do NOT apply the migration before the code change.
