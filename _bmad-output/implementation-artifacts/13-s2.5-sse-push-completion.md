> **Why this slice exists:** the SSE *infrastructure* is solid (Redis pub/sub, multi-instance, 20s heartbeat) but **9 of 13 contract event types have a working client handler and no server `emit`** — so plan generation is *polled* via `setInterval`. This is finishing deferred work, not new architecture. It is a **hard dependency** of 13-s3 (whisper "Undo" was deferred to here) and 13-s10 (talk-to-your-plan needs real push, not polling).

---

## Story

As a **HiveKitchen parent with the app open while Lumi works in the background**,
I want **the plan, its progress, and every data change to arrive by server push instead of a timer poll**,
so that **a second tab or device updates the moment the work finishes, the draft spinner reflects real stages, and the app feels like a calm system that already knows — not one I have to refresh**.

---

## Context — current state (file-grounded, verified 2026-07-02)

**Infra (keep, do not rebuild):**
- `apps/api/src/plugins/sse-dispatcher.plugin.ts` — `emit(householdId, event, data)` PUBLISHes `event: ${event}\ndata: ${data}\n\n` on `sse:household:{id}`; a separate subscriber client fans out to local sockets. Multi-instance-safe. **The emit frame has NO `id:` field** (`:83`) — this is why there is no resume.
- `apps/api/src/routes/v1/events/events.routes.ts` — single `GET /v1/events`, JWT via `?token`, household-scoped `register(payload.hh, reply.raw)` (`:79`), 20s `:ping` heartbeat. **Does not read `Last-Event-ID`.**
- `apps/web/src/lib/realtime/sse.ts` — the bridge. **All 13 client handlers already exist** in an exhaustive `switch` (`:160-272`) with a `never` default (`:263`). Backoff + jitter (`:51`), thread gap-recovery (`:98`). It already comments that native `EventSource` sends `Last-Event-ID` on reconnect **once the server sets `id:`** (`:292`) — the client is already resume-ready.

**What is broken / deferred (this slice fixes it):**
1. **`plan.updated` is never emitted.** `apps/api/src/jobs/plan-generation.job.ts:690-696` still logs `'plan.updated SSE emission deferred to Story 5.2'`. The client handler exists (`sse.ts:161`, invalidates `plan(week_id)` + `['brief']`).
2. **Two `setInterval` polls compensate** in `apps/web/src/features/plan/BriefCanvas.tsx` — the compose-now loop (`:83`, invalidates `brief`+`plan`, gives up after ~2 min) and the regenerating loop (`:318`, invalidates `brief`).
3. **Two `EventSource`s per tab.** The bridge (`sse.ts`, mounted once in `providers/query-provider.tsx:44-53`) AND `apps/web/src/hooks/useLumiNudgeSSE.ts` (its own `EventSource` at `:27`, mounted in `routes/(app)/layout.tsx:23`) each open a connection to `/v1/events`.
4. **No progress signal** — the draft spinner shows a fixed "~30s", not real stages.
5. **Data mutations don't push** — `memory.updated`, `memory.forget.completed`, `pantry.delta`, `child_request.received/resolved` handlers exist but nothing emits them (cross-tab/device inconsistency).
6. **No resume** — a dropped connection loses events sent during the gap (only `thread.turn` is partially protected via `from_seq`).

### AC6 — Last-Event-ID resume (Tier 3a)

- **Server (`emit`, `sse-dispatcher.plugin.ts:82-87`):** stamp a monotonic id and buffer recent events per household via a Redis Stream, then set the SSE frame `id:`:
  - `XADD sse:stream:household:{id} MAXLEN ~ 200 * type <event> data <data>` → native monotonic id; frame becomes `id: ${streamId}\nevent: ${event}\ndata: ${data}\n\n`.
  - **Keep `emit` sync/fire-and-forget** (spec §5): do `xadd`→`publish` inside `void (async () => { ... })()`. `XADD *` ids are monotonic regardless of races.
  - TTL / `MAXLEN ~ 200` so the stream self-prunes (≈1h).
- **Route (`events.routes.ts`, before `register(...)` at `:79`):** read `request.headers['last-event-id']`; if present, `XRANGE sse:stream:household:{id} (lastId +`, write each buffered frame to `reply.raw`, then go live. Native `EventSource` sends `Last-Event-ID` automatically on reconnect.
- **Client:** already ready (`sse.ts:292`) — no change beyond confirming reconnect replays. Replay of an invalidation event is harmless (idempotent refetch); `thread.turn` is deduped by id+seq already.
- **Verify:** integration test — emit N events, connect with `Last-Event-ID: <k>`, assert events `k+1..N` are replayed before the live stream. Confirm `MAXLEN` caps the buffer.

### Build order (spec §6 — honor it)
`1a (emit + delete polls) → 1b (one connection) → 2c (data emits) → 2a (progress) → 3a (replay)`. **Tier 2b (optimistic edits) is OUT of this slice** — deferred to **13-s10** (talk-to-your-plan) per spec §5/§6; it is the highest-risk change (reconciliation edge cases) and rides on the `plan.updated` reconciler this slice ships. Do not build `onMutate` optimistic writes here.

### The client is further along than the server
All 13 `InvalidationEvent` handlers exist (`sse.ts:160-272`) and the bridge is already resume-ready (`:292`). This slice is **mostly backend emit-wiring + one frontend consolidation (1b) + one contract add (2a)**. Resist rewriting the client switch or the bridge backoff/gap-recovery — they are correct.

### `emit` contract discipline
`emit(householdId, event, data)` takes the **event name** (`'message'` for `InvalidationEvent`, `'lumi.nudge'` for the named nudge) and a **stringified** payload. `InvalidationEvent` members ride the default `message` event; only `lumi.nudge` is a named event. Do not change this — the client's `message` listener + named `lumi.nudge` listener depend on it.

### 1b must not regress 13-s3
The whisper channel (13-s3) is live and reviewed. Its surfacing gate was patched to `presenceState === 'atRest'` (not `!== 'summoned'`) during review. The store API is `setNudge(turn)`, `appendTurn(turn)`, `whisper()`, `dismissNudge()` (atomic), with `presenceState`, `surface`, `proactiveNudges` selectors (`apps/web/src/stores/lumi.store.ts`). Copy the *exact* logic from `useLumiNudgeSSE.ts:29-53` into the bridge listener.

### Ordering / race safety (spec §5)
- Land AC1 emit before AC2 poll-deletion (same slice, ordered).
- `emit` stays fire-and-forget even with the replay buffer — `void (async () => { const id = await xadd(); await publish(frameWithId); })()`.
- Replay duplicating a live event is harmless: invalidation refetches are idempotent; `thread.turn` dedups by id+seq.
- Multi-instance ordering: the Redis Stream per household gives a single global order; pub/sub stays the live transport.
