## Acceptance Criteria

### AC1 — DB: loosen `cultural_priors.key` CHECK constraint (foundation for cuisine.declare)

The current `cultural_priors.key` CHECK constraint (`CHECK (key IN ('halal','kosher','hindu_vegetarian','south_asian','east_african','caribbean'))`) admits only 6 values. `cuisine.declare` needs to write cuisine keys like `'south_indian'`, `'levantine'`, `'italian'` — none of which are in the CHECK set. This is the retrofit migration flagged in `supabase/migrations/20260820000100_create_vocabulary_tables.sql:155` ("Existing CHECK constraints on cultural_priors retrofit to FKs in a follow-up migration").

**AC1.1 — New migration** `supabase/migrations/20260906000000_cultural_priors_drop_key_check.sql`:

```sql

-- cuisine_tags) at write time. The CHECK was redundant with vocabulary
-- validation and blocked cuisine.declare from sharing this table per the
-- Epic 2.5 sprint-change-proposal Section 4.A.
```

### AC2 — New `FoodPreferencesRepository` with encrypted `declare`

The `food_preferences` table (migration `20260903000200_create_food_preferences_table.sql`) already exists with `item` ciphertext + `item_hash` + unique on `(household_id, COALESCE(child_id, sentinel_uuid), item_hash)`. Build the writer.

**AC2.1 — New file** `apps/api/src/modules/food-preferences/food-preferences.repository.ts`:

```typescript
import { Buffer } from 'node:buffer';
import type { SupabaseClient } from '@supabase/supabase-js';
import { isUniqueViolation } from '../../common/errors.js';
import { encryptField, normalizedHash } from '../../lib/envelope-encryption.js';
import { getOrCreateHouseholdDek } from '../../lib/household-key.js';

export class FoodPreferencesRepository {
  constructor(
    private readonly client: SupabaseClient,
    private readonly kek: Buffer | null,
  ) {}

  /**
   * Declare a food preference. `item` is encrypted under the household DEK;
   * `item_hash` is SHA-256(lower(trim(plaintext))) for idempotency.
   *
   * Idempotency: re-emit with the same item + scope is a no-op (returns the
   * existing row's id with was_existing=true). The 23505 fallback handles
   * functional-index conflicts the same way DietaryPreferencesRepository
   * does (2.5-s6 AC2). Updates `valence`/`enforcement`/`source` on conflict
   * — if a parent re-declares the same item with stronger valence ("Layla
   * REFUSES broccoli, I said dislikes earlier"), the row reflects the
   * latest declaration.
   */
  async declare(
    householdId: string,
    childId: string | null,
    item: string,
    valence: 'loves' | 'likes' | 'neutral' | 'dislikes' | 'refuses',
    enforcement: string,
    source: string,
  ): Promise<{ food_preference_id: string; was_existing: boolean }> {
    const dek = await getOrCreateHouseholdDek(this.client, this.kek, householdId);
    const ciphertext = encryptField(item, dek);
    const item_hash = normalizedHash(item);

    // Primary path — onConflict on the functional unique index. If Supabase
    // refuses the functional-index onConflict (42P10), fall through to the
    // insert + 23505-catch + UPDATE fallback (mirrors 2.5-s6 dietary repo).
    const { data, error } = await this.client
      .from('food_preferences')
      .upsert(
        {
          household_id: householdId,
          child_id: childId,
          item: ciphertext,
          item_hash,
          valence,
          enforcement,
          source,
          updated_at: new Date().toISOString(),
        },
        { onConflict: 'household_id,child_id,item_hash', ignoreDuplicates: false },
      )
      .select('id, created_at, updated_at')
      .maybeSingle();

    if (error !== null && error !== undefined) {
      // Postgres 42P10 = no unique constraint matches ON CONFLICT (functional-
      // index incompatibility). Switch to the fallback path.
      const code = (error as { code?: string }).code;
      if (code === '42P10') {
        return this.declareViaInsertFallback(
          householdId, childId, ciphertext, item_hash, valence, enforcement, source,
        );
      }
      throw new Error(`food_preferences.declare: ${error.message}`);
    }
    if (data === null) {
      throw new Error('food_preferences.declare: no row returned');
    }
    const row = data as { id: string; created_at: string; updated_at: string };
    const was_existing = Math.abs(
      new Date(row.updated_at).getTime() - new Date(row.created_at).getTime(),
    ) > 1000;

    return { food_preference_id: row.id, was_existing };
  }

  private async declareViaInsertFallback(
    householdId: string,
    childId: string | null,
    ciphertext: string,
    item_hash: string,
    valence: string,
    enforcement: string,
    source: string,
  ): Promise<{ food_preference_id: string; was_existing: boolean }> {
    try {
      const { data, error } = await this.client
        .from('food_preferences')
        .insert({
          household_id: householdId,
          child_id: childId,
          item: ciphertext,
          item_hash,
          valence,
          enforcement,
          source,
        })
        .select('id')
        .single();
      if (error) throw error;
      return { food_preference_id: data.id, was_existing: false };
    } catch (err: unknown) {
      if (isUniqueViolation(err)) {
        // Resolve sentinel for NULL child_id (matches the functional unique
        // index in migration 20260903000200).
        const sentinelUuid = '00000000-0000-0000-0000-000000000000';
        const { data: existing, error: selectErr } = await this.client
          .from('food_preferences')
          .select('id')
          .eq('household_id', householdId)
          .eq('child_id', childId ?? sentinelUuid)
          .eq('item_hash', item_hash)
          .maybeSingle();
        if (selectErr) throw selectErr;
        if (existing === null) {
          throw new Error(
            'food_preferences.declare: 23505 raised but no existing row found on follow-up SELECT',
          );
        }
        // Update the existing row's mutable fields. Re-declare with a new
        // valence/enforcement reflects parent's latest intent.
        const { error: updateErr } = await this.client
          .from('food_preferences')
          .update({ valence, enforcement, source, updated_at: new Date().toISOString() })
          .eq('id', (existing as { id: string }).id);
        if (updateErr) throw updateErr;
        return { food_preference_id: (existing as { id: string }).id, was_existing: true };
      }
      throw err;
    }
  }
}
```

### AC3 — New `HouseholdRulesRepository` with encrypted `custom_label`

The `household_rules` table (migration `20260903000500_create_household_rules_table.sql`) has TWO unique paths: non-custom rules unique on `(household_id, rule_type)`, custom rules unique on `(household_id, custom_label_hash)`. Idempotency branches on `rule_type`.

**AC3.1 — New file** `apps/api/src/modules/household-rules/household-rules.repository.ts`:

```typescript
import { Buffer } from 'node:buffer';
import type { SupabaseClient } from '@supabase/supabase-js';
import { isUniqueViolation } from '../../common/errors.js';
import { encryptField, normalizedHash } from '../../lib/envelope-encryption.js';
import { getOrCreateHouseholdDek } from '../../lib/household-key.js';

export type RuleType =
  | 'no_pork'
  | 'no_alcohol'
  | 'no_beef'
  | 'no_overnight_leftovers'
  | 'no_microwave_at_school'
  | 'custom';

export class HouseholdRulesRepository {
  constructor(
    private readonly client: SupabaseClient,
    private readonly kek: Buffer | null,
  ) {}

  /**
   * Declare a household-wide rule. Idempotency branches on rule_type:
   *   - non-custom: unique on (household_id, rule_type) — re-emit is no-op
   *   - custom: unique on (household_id, custom_label_hash) — encrypts label,
   *     hash idempotency on normalized form
   *
   * For custom rules, the `custom_label` MUST be passed (the tool factory
   * enforces this via RuleSetInputSchema.refine). For non-custom rules,
   * custom_label MUST be null.
   *
   * Returns `was_existing=true` only when an existing row was already in
   * place; in that case `enforcement`/`source` are also UPDATEd so a
   * parent edit re-declaration takes effect.
   */
  async declare(
    householdId: string,
    ruleType: RuleType,
    customLabel: string | null,
    enforcement: string,
    source: string,
  ): Promise<{ household_rule_id: string; was_existing: boolean }> {
    let customLabelCipher: string | null = null;
    let customLabelHash: string | null = null;
    if (ruleType === 'custom') {
      if (customLabel === null || customLabel.length === 0) {
        throw new Error('household_rules.declare: custom rules require a custom_label');
      }
      const dek = await getOrCreateHouseholdDek(this.client, this.kek, householdId);
      customLabelCipher = encryptField(customLabel, dek);
      customLabelHash = normalizedHash(customLabel);
    } else if (customLabel !== null) {
      throw new Error(
        `household_rules.declare: non-custom rule_type '${ruleType}' must not carry a custom_label`,
      );
    }

    // Two upsert paths — one per unique index. Both branches return the row id.
    const baseRow = {
      household_id: householdId,
      rule_type: ruleType,
      custom_label: customLabelCipher,
      custom_label_hash: customLabelHash,
      enforcement,
      source,
      updated_at: new Date().toISOString(),
    };

    if (ruleType !== 'custom') {
      // Unique (household_id, rule_type) WHERE rule_type <> 'custom'
      const { data, error } = await this.client
        .from('household_rules')
        .upsert(baseRow, {
          onConflict: 'household_id,rule_type',
          ignoreDuplicates: false,
        })
        .select('id, created_at, updated_at')
        .maybeSingle();
      if (error !== null && error !== undefined) {
        const code = (error as { code?: string }).code;
        if (code === '42P10') {
          // Partial-index onConflict can be refused; fall back.
          return this.declareViaInsertFallback(baseRow, 'rule_type');
        }
        throw new Error(`household_rules.declare: ${error.message}`);
      }
      if (data === null) {
        throw new Error('household_rules.declare: no row returned (non-custom)');
      }
      const row = data as { id: string; created_at: string; updated_at: string };
      return {
        household_rule_id: row.id,
        was_existing:
          Math.abs(new Date(row.updated_at).getTime() - new Date(row.created_at).getTime()) >
          1000,
      };
    }

    // custom — Unique (household_id, custom_label_hash) WHERE rule_type='custom'
    const { data, error } = await this.client
      .from('household_rules')
      .upsert(baseRow, {
        onConflict: 'household_id,custom_label_hash',
        ignoreDuplicates: false,
      })
      .select('id, created_at, updated_at')
      .maybeSingle();
    if (error !== null && error !== undefined) {
      const code = (error as { code?: string }).code;
      if (code === '42P10') {
        return this.declareViaInsertFallback(baseRow, 'custom_label_hash');
      }
      throw new Error(`household_rules.declare: ${error.message}`);
    }
    if (data === null) {
      throw new Error('household_rules.declare: no row returned (custom)');
    }
    const row = data as { id: string; created_at: string; updated_at: string };
    return {
      household_rule_id: row.id,
      was_existing:
        Math.abs(new Date(row.updated_at).getTime() - new Date(row.created_at).getTime()) > 1000,
    };
  }

  private async declareViaInsertFallback(
    baseRow: Record<string, unknown>,
    conflictKey: 'rule_type' | 'custom_label_hash',
  ): Promise<{ household_rule_id: string; was_existing: boolean }> {
    try {
      const { data, error } = await this.client
        .from('household_rules')
        .insert(baseRow)
        .select('id')
        .single();
      if (error) throw error;
      return { household_rule_id: data.id, was_existing: false };
    } catch (err: unknown) {
      if (isUniqueViolation(err)) {
        const query = this.client
          .from('household_rules')
          .select('id')
          .eq('household_id', baseRow.household_id as string)
          .eq(conflictKey, baseRow[conflictKey] as string);
        const { data: existing, error: selectErr } = await query.maybeSingle();
        if (selectErr) throw selectErr;
        if (existing === null) {
          throw new Error(
            'household_rules.declare: 23505 raised but no existing row found on follow-up SELECT',
          );
        }
        const { error: updateErr } = await this.client
          .from('household_rules')
          .update({
            enforcement: baseRow.enforcement,
            source: baseRow.source,
            updated_at: new Date().toISOString(),
          })
          .eq('id', (existing as { id: string }).id);
        if (updateErr) throw updateErr;
        return { household_rule_id: (existing as { id: string }).id, was_existing: true };
      }
      throw err;
    }
  }
}
```

```typescript
  ctx: OnboardingToolContext,
  deps: OnboardingToolDeps,  // remove underscore

    inputSchema: FoodPreferenceDeclareInputSchema,
```

**AC9.1 — Directive parser:**

```typescript
// Slice 2.5-s7 — elevation chip prompt directive. Optional second directive
// the agent may emit on M3 turns. Format:
//   [CHIP_PROMPT:elevation:<tag_key>:<tag_label>]
// tag_key + tag_label are forwarded into the action chip rendering so the
// parent sees "Got it — '<tag_label>'. Should I treat that as a hard rule
// or more like a preference?" The chip keys are fixed: always-respect /
// prefer / just-context.
const CHIP_PROMPT_ELEVATION_RE = /\[CHIP_PROMPT:elevation:([a-z0-9_]+):([^\]]+)\]\s*$/;

interface ElevationPrompt {
  tag_key: string;
  tag_label: string;
}

function parseElevationPrompt(text: string): {
  cleaned: string;
  prompt: ElevationPrompt | null;
} {
  const match = text.match(CHIP_PROMPT_ELEVATION_RE);
  if (match === null) return { cleaned: text, prompt: null };
  return {
    cleaned: text.replace(CHIP_PROMPT_ELEVATION_RE, '').trimEnd(),
    prompt: { tag_key: match[1]!, tag_label: match[2]!.trim() },
  };
}
```

The directive must be stripped from the user-visible prose (same as `[NEXT_MOMENT:]`). Strip both directives in either order — chain the two regexes.

## Dev Notes

### Encryption patterns

`food_preferences` and `household_rules` both follow the same envelope-encryption pattern HouseholdsRepository / ChildAllergensRepository use:

1. Resolve DEK via `getOrCreateHouseholdDek(this.client, this.kek, householdId)`
2. Encrypt the sensitive plaintext with `encryptField(plaintext, dek)`
3. Compute idempotency hash with `normalizedHash(plaintext)` — SHA-256(lower(trim(...)))
4. Upsert with the appropriate functional-index conflict target

The `kek` (Key Encryption Key) comes from `fastify.env.ENVELOPE_ENCRYPTION_MASTER_KEY` and is already in scope as `kek` in `onboarding.routes.ts` (built around line 43 of that file by 2.5-s6's wiring).

### 42P10 functional-index workaround (already proven in 2.5-s6)

Both `food_preferences` and `household_rules` (custom path) have unique indexes on functional expressions (`COALESCE(child_id, sentinel_uuid)` and partial indexes `WHERE rule_type <> 'custom'`). Supabase `.upsert()` may refuse the `onConflict` parameter on these — when it returns Postgres `42P10`, fall back to:

1. INSERT
2. If 23505 (unique violation), SELECT the existing row by the same predicates
3. UPDATE the mutable fields on the existing row
4. Return `{ id, was_existing: true }`

Use `isUniqueViolation(err)` from `apps/api/src/common/errors.js` to detect 23505. The pattern is established — copy from `DietaryPreferencesRepository.declareViaInsertFallback`.

### Cross-household child guard (already proven in 2.5-s6)

`food_preference.declare` accepts `child_id` from the agent. The agent can supply a stale or wrong UUID — protect against cross-household writes by calling `deps.childrenService.getChild({ householdId, childId })` before the repo write. `getChild` throws `NotFoundError` when the `(householdId, childId)` pair isn't in `children`. Mirror the M2 review-patch from 2.5-s6's `allergen.declare`.

For `food_preference.declare` with both `child_id` and `child_name` null, this guard is skipped (household-scoped writes don't need a child guard).

### Elevation directive (`[CHIP_PROMPT:elevation:...]`) — design intent

The directive is an opt-in mechanism for the agent. The agent does NOT have to emit it for every strong-enforcement signal; for very obvious cases ("strictly Halal — non-negotiable") it MAY directly emit `dietary.declare(tag='halal', enforcement='non_negotiable')` and skip the confirmation. The CHIP_PROMPT is for ambiguous cases ("strictly Halal" → ask whether that means non_negotiable or strong) and for cases where the agent wants explicit parent ratification on a hard elevation.

The chosen enforcement (`non_negotiable` / `strong` / `just_for_context`) on the chip-confirmation TURN is then the enforcement the agent passes to the subsequent tool call. There is NO additional service-side enforcement transition logic — the agent owns this routing, the service just passes through.

This minimises new state-machine surface. The `cultural_priors.state` transitions (suggested → opt_in_confirmed) remain a separate ratification path handled at 2.5-s10's summary moment.

### Chip-tap handler — no new logic needed for the broad-hint scenario

`OnboardingText.tsx`'s chip-tap handler already covers:
- `mode: 'hint'` → no onClick (HintChip is non-interactive)
- `mode: 'action'` → single-select (sets `chipSelections=[opt.key]`)
- `mode: 'choice'` → multi-select with M2 mutual-exclusion branch (added in 2.5-s6 for the `'none'` chip)

For M3:
- `mode: 'hint'` with `skip_label` → broad-hint scenario: hints render, parent free-types, SkipChip is first-class
- `mode: 'action'` (elevation override) → existing single-select branch handles the 3 elevation chips

No new chip-tap branch is needed in this slice. The M3-specific behaviour is entirely server-side (chip_config emission) + the new taste card.

### M3 status line below the input bar

In M2 (2.5-s6), the status line carried required-mode hint copy and selection-count copy. M3 is OPTIONAL — the M2 status-line pattern does NOT apply. The default chip selection count copy already in place (from 2.5-s3/s5) is correct for M3 elevation chips ("1 selection will be sent with your message"). No new M3 status-line branch is needed.

### Why the M3 taste card is intentionally lean in this slice

The Moment3Page mock shows a rich "Your kitchen's taste" card with cultural badges (with enforcement borders), cuisine pills, and dietary chips. Building that in this slice would require either:

- Heuristic regex extraction from the chat transcript (the pattern 2.5-s6 retired in favour of structured state), or
- Reading from the Kitchen Map on every turn response (extra round-trip, unbounded latency cost on the chat-critical path), or
- Echoing tool-call results from the service into the turn response (extra contract surface, schema churn)

The right surface for live, data-bound Kitchen Profile rendering is **2.5-s11**, when the read endpoint is wired against `KitchenMapSchema`. This slice's lean card acknowledges M3 progress without re-introducing fragile heuristics or premature data plumbing.

### Pre-existing 5 `child.upsert` test failures (unchanged)

The 5 failing `createChildUpsertToolSpec` tests have a pre-existing `resolveAllergen` API drift (tracked since 2.5-s5; documented in every Epic 2.5 slice). Do NOT fix or modify these tests in this slice — leave them as-is.

### Pre-existing typecheck errors (unchanged)

The 16 typecheck errors in `plans/`, `voice/`, `households/`, `day-overrides/`, `brief-state.composer.test.ts` are unrelated to onboarding. Do NOT introduce new errors and do NOT fix the existing ones.
