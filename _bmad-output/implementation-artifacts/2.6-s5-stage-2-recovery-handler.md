Status: done

**Brief:** [_bmad-output/planning-artifacts/epic-2.6-brief.md](../planning-artifacts/epic-2.6-brief.md) (rev 3, Section 4 → 2.6-s5)

**NO WALL** — this is a robustness slice; M5 already works without it.

---

## Story

As a **household onboarding through Moment 5**,
I want **the system to automatically recover when Stage 1 produces too few safe catalog items (floor breach) or when the allergen guardrail blocks more than half of Stage 1's output (mass-block)**,
so that **high-allergen households, underrepresented-cuisine households, and households where Stage 1 LLM fails entirely arrive at M5 with a usable chip set rather than routing straight to the cold-start fallback**.

Stage 2 is **recovery-only**. It fires ONLY on named trigger events emitted by Stage 1 completion. It has **no scheduler, no cron, no idle trigger**.

## Acceptance Criteria

**AC1 — New BullMQ queue `catalog.recover.stage2`.**
- Queue name: `catalog.recover.stage2` (string constant exported from `apps/api/src/jobs/catalog-recovery.job.ts`).
- Job data shape: `{ household_id: string; request_id: string; triggered_by: 'floor_breach' | 'mass_block' | 'stage1_failure'; emitted_count?: number; blocked_count?: number }`.
- `emitted_count` and `blocked_count` are only present for `mass_block` triggers (for ops visibility).
- Job plugin registered as a Fastify plugin following the same pattern as `catalogSeedJobPlugin` (`apps/api/src/jobs/catalog-seed.job.ts`).

**AC2 — `CatalogRecoveryService.recoverForHousehold(householdId, triggeredBy, opts?)` authored.**
New service at `apps/api/src/modules/catalog/catalog-recovery.service.ts`.

```ts
async recoverForHousehold(
  householdId: string,
  triggeredBy: 'floor_breach' | 'mass_block' | 'stage1_failure',
  opts?: { emitted_count?: number; blocked_count?: number },
): Promise<void>
```

NEVER throws. Catches everything; logs; returns void. Pipeline:

1. **Concurrent Stage 1 guard.** Read `households.stage1_completed_at`. If NULL (Stage 1 in-flight), log `catalog.stage2.deferred_stage1_in_flight` and return (the job's `attempts: 2` / 30s backoff handles the retry — see AC1 job opts). The one-retry max is enforced via the BullMQ attempts setting, not in-service loops.
2. **Skip-if-recovered check.** Query `RecipesRepository.countCatalogSeededForHousehold(householdId)`. If `count >= 35`, log `catalog.stage2.skip_already_recovered` with `{ count }` and return — no recovery needed.
3. **Load cuisine context.** Call `kitchenMapService.get(householdId)` to get the current KitchenMap. Extract `cuisineTags` as the union of `map.cultural.active.map(p => p.key)` (same derivation `CatalogSeedService.buildSnapshot` uses). If cuisine tags are empty, use `[]` — `CuratedBaselineMaterializationService.rematerialize` handles the empty-tags skip internally.
4. **Re-materialize curated baseline.** Call `curatedBaselineMaterializationService.rematerialize(householdId, cuisineTags)`. This re-seeds baseline rows for the household's cuisine buckets; ON CONFLICT DO NOTHING means `declared` rows and already-seeded rows are preserved. Uses the existing `CuratedBaselineMaterializationService` from 2.6-s2 — do NOT duplicate its logic.
5. **Post-recovery count.** Call `RecipesRepository.countCatalogSeededForHousehold(householdId)` again.
6. **Terminal-zero detection.** If post-recovery count is 0, log `catalog.stage2.terminal_zero` with `{ household_id, triggered_by }`. This is the signal for ops and for 2.6-s6 cold-start routing. Do NOT throw — still return normally.
7. **Completion log.** Log `catalog.stage2.completed` with `{ household_id, triggered_by, pre_recovery_count, post_recovery_count }`.

### Why Stage 2 exists

Stage 0 guarantees at least the broad-safe global baseline (broad-safe seed, no nut/shellfish/pork items). Stage 1 generates ~50 personalized ideas via LLM but can fail or produce a mass-blocked result for high-allergen households. Stage 2 runs ONLY when those failures produce a catalog below the 35-row floor. Its job: re-materialize curated baseline rows for the household's cuisine buckets to add culturally-appropriate items to a depleted catalog. This is NOT a background enrichment pass — it runs once per Stage 1 completion event on households that need it.

### STAGE 2 DISCIPLINE (read before implementing)

```
// STAGE 2 IS RECOVERY-ONLY. NO SCHEDULER. NO CRON.
```

The brief (Section 4, 2.6-s5) and Epic 2.5 retro Action #4 both require this invariant. The BullMQ job opts for Stage 2 MUST NOT include `repeat`, `cron`, or any scheduled trigger. Code review will `grep` for these. The service has no `schedule`, `setInterval`, or `setTimeout` recurring call.

### Key thresholds (locked in brief rev 3)

| Threshold | Value | Where evaluated |
|---|---|---|
| Floor breach | total post-guardrail `catalog_seeded` rows for household < **35** | In `CatalogSeedService` after persisting; Stage 2 also re-checks in `CatalogRecoveryService` |
| Mass-block | guardrail-blocked items > **50%** of LLM emission count | In `CatalogSeedService` after guardrail loop; denominator = `candidateCount` (LLM output count) |
| Stage 1 floor (existing constant) | validated items < 10 | Pre-existing constant in `catalog-seed.service.ts`; separate from the floor-breach trigger |
| Skip-if-recovered | total `catalog_seeded` rows >= **35** | In `CatalogRecoveryService` before running rematerialize |
| BullMQ retry | 1 retry max for Stage 2 jobs | Via `attempts: 2` in job opts |

### Using `CuratedBaselineMaterializationService.rematerialize` for recovery

Stage 2's recovery path is **exactly** `CuratedBaselineMaterializationService.rematerialize(householdId, cuisineTags)` (already built in 2.6-s2). Do NOT re-implement it. Key properties that make it safe to call here:
- It is additive only: ON CONFLICT DO NOTHING means declared/already-seeded rows are preserved.
- It runs the allergen guardrail before persisting — recovery items also pass through safety checking.
- It NEVER throws (catches internally; logs errors).
- It handles `cuisineTags.length === 0` with a skip-and-log.

The `CatalogRecoveryService` constructs and calls this service directly — it does not call `CuratedBaselineRepository.rematerialize` (the repo method doesn't exist; the logic is in the service layer).

### How to get cuisine tags in Stage 2

`kitchenMapService.get(householdId)` returns the KitchenMap. Cuisine tags for Stage 2 recovery:
```ts
const map = await this.kitchenMapService.get(householdId);
const cuisineTags = map.cultural.active.map((p) => p.key);
```
This matches `CatalogSeedService.buildSnapshot`'s derivation. If the parent hasn't completed M3 yet (`cultural.active` is empty), `cuisineTags` will be `[]`; `rematerialize` handles this with a no-op log. Stage 0 baseline is still available as a fallback floor.

### `enqueueRecovery` — fire-and-forget implementation

```ts
private enqueueRecovery(
  householdId: string,
  requestId: string,
  triggeredBy: 'floor_breach' | 'mass_block' | 'stage1_failure',
  opts?: { emitted_count?: number; blocked_count?: number },
): void {
  if (!this.recoveryQueue) {
    this.logger.warn(
      { module: 'catalog', action: 'catalog.stage2.recovery_skipped_no_queue', household_id: householdId },
      'Stage 2 recovery skipped — recoveryQueue not wired',
    );
    return;
  }
  const jobData: CatalogRecoveryJobData = {
    household_id: householdId,
    request_id: requestId,
    triggered_by: triggeredBy,
    ...opts,
  };
  // Fire-and-forget — do not await. The worker handles failures independently.
  void this.recoveryQueue.add(CATALOG_RECOVERY_QUEUE, jobData, CATALOG_RECOVERY_JOB_OPTS).catch((err) => {
    this.logger.error(
      { module: 'catalog', action: 'catalog.stage2.enqueue_failed', household_id: householdId, triggered_by: triggeredBy, err },
      'Stage 2 recovery enqueue failed',
    );
  });
}
```

### Floor breach check placement in `seedForHousehold`

The floor breach check replaces the existing TODO comment at the bottom of Step 8 (`if (persisted < STAGE1_FLOOR) { ... }`). However, the floor breach threshold for triggering Stage 2 is **35** (total household count), not `STAGE1_FLOOR` (10, which is just a local floor-breach log threshold). The implementation:

```ts
  this.enqueueRecovery(householdId, requestId, 'floor_breach');

```

Add `const STAGE2_FLOOR = 35;` as a module-level constant in `catalog-seed.service.ts`. Keep the existing `STAGE1_FLOOR = 10` constant (it controls a different local log).

### Mass-block detection placement

After the guardrail loop (after `guardrailBlocked` is finalized, before Step 7 persist):

```ts
// Mass-block check: > 50% of LLM-emitted items blocked → trigger Stage 2.
const massBlockRatio = candidateCount > 0 ? guardrailBlocked / candidateCount : 0;
if (massBlockRatio > 0.5) {
  this.logger.warn(
    { module: 'catalog', action: 'catalog.stage1.mass_block_detected', household_id: householdId,
      request_id: requestId, emitted_count: candidateCount, blocked_count: guardrailBlocked, ratio: massBlockRatio },
    'stage 1 mass-block detected — Stage 2 recovery enqueued',
  );
  this.enqueueRecovery(householdId, requestId, 'mass_block', {
    emitted_count: candidateCount, blocked_count: guardrailBlocked,
  });
}
// Then proceed to Step 7 persist...
```

Note: mass-block and floor-breach can BOTH trigger in the same Stage 1 run. Both `enqueueRecovery` calls are safe — BullMQ deduplication via `jobId` is NOT used (two separate trigger reasons should produce two jobs, but the Stage 2 service's skip-if-recovered guard prevents double work). To avoid two Stage 2 runs for the same household, add a job ID: `jobId: \`stage2:${householdId}\`` in `CATALOG_RECOVERY_JOB_OPTS` with `removeOnComplete: true` and `conflictPolicy: 'replace'`. This ensures only one Stage 2 job runs per household at a time.

Actually re-read: since both mass_block and floor_breach can fire simultaneously, use a `jobId: \`${CATALOG_RECOVERY_QUEUE}:${householdId}\`` to deduplicate at BullMQ level. The second `queue.add` with the same jobId replaces the first if not yet started.

### BullMQ job opts for Stage 2

```ts
export const CATALOG_RECOVERY_JOB_OPTS = {
  attempts: 2,
  backoff: { type: 'fixed' as const, delay: 30_000 }, // 30s, matches brief "re-queued for 30s later (one retry max)"
```

| Both mass-block and floor-breach fire simultaneously | AC5 | Two `enqueueRecovery` calls with same `jobId` → BullMQ dedup via `jobId: \`catalog.recover.stage2:${householdId}\`` — only one Stage 2 job runs. |
| Skip-if-recovered (Stage 2 job arrives but count already >= 35) | AC2 step 2 | Log `catalog.stage2.skip_already_recovered`, return. Count may have risen due to concurrent Stage 0 re-materialization or manual seeding. |
| `kitchenMapService.get` throws (household not found mid-onboarding) | AC2 / AC8 | Outer try/catch catches; logs generic failure; returns void. No rematerialize call, no crash. |
| `countCatalogSeededForHousehold` throws | AC2 | Outer try/catch catches; logs `catalog.stage2.failed`; returns void. |

### Deferred work from brief rev 3

The brief names these as explicitly out-of-scope for this slice (surface in `deferred-work.md` at code review):

### Completion Notes List

- **Architecture: reused 2.6-s2 service.** Stage 2 recovery does NOT re-implement the curated-baseline re-materialization logic — it composes `CuratedBaselineMaterializationService.rematerialize` (built in 2.6-s2). This kept `CatalogRecoveryService` to ~150 lines and ensures Stage 0 and Stage 2 take the exact same guardrail / ON-CONFLICT-DO-NOTHING / fail-closed paths.
- **Plugin registration order.** `catalogRecoveryJobPlugin` is registered BEFORE `catalogSeedJobPlugin` in `app.ts` so the recovery queue is reachable at the moment `catalogSeedPlugin` calls `fastify.bullmq.getQueue(CATALOG_RECOVERY_QUEUE)`. BullMQ's `getQueue` is idempotent (lazy + cached), so functional order is independent — but explicit ordering makes the dependency graph readable. Comment in `app.ts` documents this.
- **JobId dedup for concurrent triggers.** Both mass-block AND floor-breach can fire on the same Stage 1 run. To avoid two Stage 2 jobs racing on the same household, `enqueueRecovery` passes `jobId: \`catalog.recover.stage2:${householdId}\`` in `CATALOG_RECOVERY_JOB_OPTS`. BullMQ's `add()` with an existing jobId is a no-op for queued (not yet running) jobs.
- **Floor-breach trigger moved AFTER setStage1CompletedAt.** Per brief AC2 step 1, Stage 2 must NOT run while Stage 1 is in-flight. Moving the floor-breach check after `setStage1CompletedAt` guarantees the Stage 2 worker sees a non-null `stage1_completed_at` on first run (no deferred_stage1_in_flight retry loop in the happy path). The existing `STAGE1_FLOOR=10` warn log is preserved as a diagnostic but its TODO comment is removed.
- **Mass-block trigger fires BEFORE persist.** Per brief AC5, the mass-block enqueue runs immediately after the guardrail loop so Stage 2 is queued even if persist later fails. Calling order: guardrail loop → mass-block check (enqueue if ratio > 0.5) → persist → setStage1CompletedAt → floor-breach check.
- **Floor-breach check wrapped in nested try/catch.** If `countCatalogSeededForHousehold` throws after a successful Stage 1, we log `catalog.stage2.floor_breach_check_failed` and continue — Stage 1's happy path has already succeeded; M5 will route through whatever catalog exists. This intentionally avoids re-throwing into the outer catch-all (which would log `catalog.stage1.failed` and confuse ops about whether Stage 1 itself succeeded).
- **NEVER-throws discipline preserved.** Both services use outer try/catch wrapping the entire pipeline. The `enqueueRecovery` helper uses `void queue.add(...).catch(...)` so a Redis blip never propagates into Stage 1's hot path. `CatalogRecoveryService.recoverForHousehold` similarly catches everything and logs `catalog.stage2.failed`.
- **No scheduler / no cron — verified.** `CATALOG_RECOVERY_JOB_OPTS` contains only `attempts: 2`, `backoff: { type: 'fixed', delay: 30_000 }`, `removeOnComplete`, `removeOnFail`. No `repeat` key. The 30s backoff exists ONLY to serve the brief's "one retry max for the stage1-in-flight race" mechanism. AC6 grep target: `grep -r 'catalog.recover.stage2' apps/api/src/jobs/ | grep -i 'repeat\|cron\|schedule'` → zero results.
- **Tests: mass-block needs guardrail-blocked names, not allergen_flags.** Initial test draft used `allergen_flags: ['peanut']` but the engine evaluates only `ingredients` (= canonical_name). Corrected to use `canonical_name: 'pasta dish N'` which matches the wheat synonym 'pasta' in `FALCPA_SYNONYMS.wheat` and gets blocked.
- **Pre-existing failures verified.** `git stash` + `vitest run catalog-seed.service.test.ts` on clean main reproduces the 1/12 happy-path failure → confirms it's pre-existing, not introduced by this slice. Documented in 2.6-s3 and 2.6-s4 Dev Agent Records (same root cause: Zod array parse fails on items missing `applicable_slots`, dropping the whole response before per-item validation).
