## 2. What went well

**The contract-preservation discipline held for 9 straight slices.** Every JSONB-to-rows cutover (s3, s4, s5, s6) and the one true cutover (s7) kept its repository's public contract byte-identical, so downstream readers — planner, guardrail, Kitchen Map, all of `apps/web` — needed zero edits. This was proven each time (`contracts:check` run, `git status apps/web packages` checked empty), not assumed. This is the single biggest reason a 9-slice schema migration shipped with an empty frontend diff.

**Spec-vs-reality corrections were caught before they became implementation bugs.** 15-s5 rejected the spec's literal `extra_library_id` FK because pins/bans were never actually linked to `extra_library`. 15-s9 corrected the spec's `'strict'` enforcement value, which doesn't exist in the shipped enum — the real threshold is `non_negotiable`. 15-s7 corrected which of the three slot columns actually reaches `apps/web` before deciding where to draw the contract boundary. Each correction was disclosed in the story, not silently patched around.

**The `s3`/`s4` reconciliation-section habit from Epic 14's Action Item 2 carried over and paid off again** — most stories opened with a dated section checking spec claims against the live codebase before writing code.

**15-s9's code review needed zero decisions** — the only slice this epic where the 3-layer adversarial pass found nothing requiring a judgment call, just patches. That's a real signal the story was well-scoped and well-authored going in.

**The atomic cutover (s7) validated the "do the risky one last, once everything else is stable" sequencing from the spec's own §8 ordering** — it shipped with the smallest deviation count of the four database-shape-changing slices and needed only one repository file plus the migration touched.

## 3. What was hard / recurring patterns

**Same defect class caused a review-blind spot twice, and the second instance is still live.** 15-s5's code review found two literal NUL bytes hidden in `backfill-child-extra-rules.ts`'s template literal — `git` reported the file as binary and hid the entire diff from review; fixed by replacing with spaces. 15-s8's review found the **same defect class** in `child-preferences.repository.ts`, flagged it as an "unrelated observation," and explicitly did not fix it because it was out of that story's file list.

**I checked this file just now — it is still corrupted.** `file` reports it as `data` (binary): a dedup-key template literal used 2 literal NUL characters as delimiters between `child_id`, `recipe_id`, and `slot_kind`. This means `git diff`/`git show` on this file has been silently blind since whenever it was introduced, through 15-s6, s7, s8, and s9's reviews, none of which had it in scope. This is the same failure mode that already cost a review pass once this epic; it is currently unowned and undetected by any gate. **Fixed as part of this retro** — see §6.

**No Postgres test harness remains the epic's standing, unclosed gap.** 15-s5, 15-s6, and 15-s7 all disclosed the same limitation: SQL function/trigger bodies (the `SECURITY DEFINER` RPCs, the polymorphic-reference triggers, the RESTRICT-on-delete guards) are reviewed but never executed by any test, because no pg-mem/testcontainers/PGlite harness exists in this repo. By s7 this gap covers the epic's single most safety-critical piece of new logic — the `pg_trigger_depth() > 1` cascade-bypass that keeps dev-reset and account-deletion from breaking under the new RESTRICT triggers — and it is asserted only by string-presence checks over migration text, not execution.

**Deferred debt grew fast against last epic's explicit ruling.** Epic 14's retro action item 1 was "every story's ACs must name ≥1 existing deferred item to absorb... net deferred delta ≤ 0 for the next epic." Epic 15 added roughly 32 new deferred-work.md entries across its 9 code reviews and dev-story sessions, and closed exactly 1 (15-s3's per-kind `subject_ref` schema). Net delta is roughly **+31**, the opposite of what was committed to.

**~~Nine unpushed, ordered migrations are now stacked.~~ — SUPERSEDED, see correction below.** Every slice from s3 onward disclosed a `USER-SIDE GATE` — supabase push, then a backfill script, then (only after backfill succeeds) a drop migration — and every single one of those gates is still marked pending in the sprint-status log. All 9 of epic 15's migrations (`20261035000000` through `20261037000000`) sit unapplied against the live database. Three of them are irreversible column drops (`school_policy_notes`, `extra_rules`, `preferred_family_language_terms`) that depend on their sibling backfill script having run first, in order. This is the largest deploy-ordering risk the project is currently carrying — a single out-of-order `supabase db push` or a skipped backfill script would desync the parity gates every slice built specifically to catch.
