## Story

As a parent who has completed all five onboarding moments,
I want to see a summary moment where Lumi reads back what was captured and I can confirm my kitchen before finalizing,
so that I can seal my kitchen profile (transitioning `is_onboarded=true`) and start receiving personalized weekly plans.

### AC1 — Contracts: `TextOnboardingTurnResponseSchema` extended

File: `packages/contracts/src/onboarding.ts`

Add two optional fields to `TextOnboardingTurnResponseSchema`:
```typescript
required_set_complete: z.boolean().nullable().optional(),
missing_required_set: z.array(z.string()).optional(),
```

Add matching fields to `SubmitTextTurnResult` (internal service interface in `onboarding.service.ts`):
```typescript
required_set_complete: boolean | null;
missing_required_set: string[];
```

`missing_required_set` is an array of moment-key strings identifying which required moments are not yet satisfied. Valid values: `'m1_table'`, `'m2_safe'`, `'m5_starting_line'`. Derived from the four required-set booleans:
- `!m1_household_name || !m1_child_declared` → push `'m1_table'`
- `!m2_allergen_response` → push `'m2_safe'`
- `!m5_complete` → push `'m5_starting_line'`

When `momentRepository` is absent or throws, both fields default to `null` / `[]`.

### AC3 — M5 override-path fix: `m5_complete` sticky + override detection

File: `apps/api/src/modules/onboarding/onboarding.service.ts`

**Problem:** When a parent uses `override_fewer` (taps early exit at ≥4 items), the agent embeds `[NEXT_MOMENT:summary]` without reaching 10 items. The current `m5_complete` computation (`counts.favorite_lunch_count >= 10`) is `false`, so `required_set_complete` stays `false` and finalize is blocked — contradicting the user's explicit opt-out.

**Fix:** Replace the current `m5_complete` computation inside `submitTextTurn`'s required-set block:

```typescript
// Override path: parent explicitly advanced out of m5_starting_line with 4+ items
// (tapped override_fewer chip). Treat as complete even if count < 10.
const m5OverridePath =
  previousMoment === 'm5_starting_line' &&
  nextCurrentMoment !== 'm5_starting_line' &&
  counts.favorite_lunch_count >= 4;

// Sticky: once m5_complete is true (natural 10-item path OR override), preserve
// across subsequent turns in summary/finalized moments so the gate stays open.
const m5_complete =
  counts.favorite_lunch_count >= 10 ||
  m5OverridePath ||
  (preTurnMomentState?.required_set_status.m5_complete === true);

const requiredSetStatus: RequiredSetStatus = {
  m1_household_name: counts.household_name_set,
  m1_child_declared: counts.child_count > 0,
  m2_allergen_response,
  m5_favorite_count: counts.favorite_lunch_count,
  m5_complete,
};
```

This replaces the existing `m5_complete: counts.favorite_lunch_count >= 10` line.

### AC4 — `finalizeTextOnboarding` required-set gate

File: `apps/api/src/modules/onboarding/onboarding.service.ts` — `finalizeTextOnboarding` method

Add a required-set check BEFORE the `isSummaryConfirmed` LLM call. Insert after the "turns.length === 0" check (currently around line 912) and before the `isSummaryConfirmed` call:

```typescript
// 2.5-s10 — Required-set gate: the moment must be 'summary' and the
// required-set must be complete before the thread can be closed.
// This is the server-authoritative EPIC MVP WALL enforcement.
let finalizeState: MomentState | null = null;
if (this.momentRepository !== undefined) {
  try {
    finalizeState = await this.momentRepository.getState(input.householdId);
  } catch (err) {
    this.logger.warn(
      { err, module: 'onboarding', action: 'onboarding.finalize_moment_state_read_failed',
        household_id: input.householdId },
      'moment state read failed during finalize — proceeding with null state',
    );
  }
  if (finalizeState === null || finalizeState.current_moment !== 'summary') {
    throw new ConflictError(
      'onboarding summary not reached — complete all five moments before finalizing',
    );
  }
  const rss = finalizeState.required_set_status;
  const reqComplete =
    rss.m1_household_name &&
    rss.m1_child_declared &&
    rss.m2_allergen_response &&
    rss.m5_complete;
  if (!reqComplete) {
    throw new ConflictError(
      'required fields incomplete — finish all required onboarding moments before finalizing',
    );
  }
}
```

The `momentRepository` check makes this gate best-effort: if the repository is missing (legacy/test path), the finalize proceeds with the existing `isSummaryConfirmed` guard alone. In production, `momentRepository` is always wired.

**Order of checks in `finalizeTextOnboarding` after this change:**

3. Idempotency: existing summary turn check (existing)
4. Empty-thread guard (existing)
5. **NEW: moment-state required-set gate (AC4 above)**
6. `isSummaryConfirmed` LLM call (existing — keep as safety net)
7. `extractSummary` (existing)
8. Append summary turn (existing)
9. Cultural inference (existing)
10. Seed memory (existing)
11. Close thread (existing)

### AC5 — `finalizeTextOnboarding` writes `finalized` to `momentRepository`

File: `apps/api/src/modules/onboarding/onboarding.service.ts` — `finalizeTextOnboarding` method

After `await this.threads.closeThread(thread.id)` (step 7 in the method), add:

```typescript
// 2.5-s10 — Mark the moment state as finalized. Best-effort: a failure here
// does not block the successful finalize response — the thread is already
// closed (the authoritative is_onboarded signal) and the moment state is a
// secondary projection.
if (this.momentRepository !== undefined && finalizeState !== null) {
  try {
    await this.momentRepository.upsertState(input.householdId, {
      current_moment: 'finalized',
      required_set_status: finalizeState.required_set_status,
    });
  } catch (err) {
    this.logger.warn(
      { err, module: 'onboarding', action: 'onboarding.finalize_moment_state_write_failed',
        household_id: input.householdId },
      'moment state finalized write failed — thread is closed, is_onboarded still true',
    );
  }
}
```

`finalizeState` is the variable set in AC4 (in scope because AC4 is in the same method). Guard with `finalizeState !== null` because without a prior state the write is a no-op.

### `m5_complete` Sticky Logic — Why It's Needed

The `m5_complete` field in `RequiredSetStatus` is recomputed from scratch every turn:
```typescript
m5_complete: counts.favorite_lunch_count >= 10,
```

When a parent uses `override_fewer` (4+ items, advances to summary with <10 items):
- Turn at which agent advances: `previous='m5_starting_line'`, `next='summary'`, `count=6` → `m5_complete = false`
- Next turn (in summary): `current='summary'`, `count=6` → `m5_complete = false` still

So `required_set_complete = false` even after override → `finalizeTextOnboarding` rejects → parent can never finalize.

The fix detects the override path on the advancing turn AND persists `m5_complete = true` via `upsertState`. Subsequent turns read `preTurnMomentState.required_set_status.m5_complete === true` and preserve it.

### "Back to Moment N" Client-Side Navigation

When the parent taps "Back to Moment N" in the gap callout, `setCurrentMomentKey(momentKey)` is called client-side. This:
1. Updates the header to show `Moment N of 5 · <name>` (reverts the summary header)
2. Re-renders the input bar (the `currentMomentKey !== 'summary'` branch)
3. Does NOT fire any API call

The agent is still in `summary` moment in the DB. When the parent sends their next message, the agent will:
- See `current_moment: summary` in the system block
- Receive the parent's message about the missing data
- Fire the appropriate tool to fix it (e.g., `child.upsert` for missing bag composition)
- Eventually re-advance to `summary` or acknowledge the correction

This is intentionally simple — the DB-side state is self-healing via the agent's state-awareness.

### Rollback of `requiredSetComplete` in error path

In `submitTurn`, when the POST fails:
```typescript
// Rollback optimistic render
setTurns((prev) => prev.filter((t) => t.id !== optimisticUserTurn.id));
setDraft(draftSnapshot);
setChipSelections(chipSelectionsSnapshot);
// Also roll back required-set state if this turn was the one that set it
// (not strictly necessary since required_set_complete only advances forward,
// but keeps state consistent with the failed turn).
```

Simple approach: don't roll back `requiredSetComplete`/`missingRequiredSet` on error. These are server-derived signals; the state before the failed turn was accurate and the values shouldn't regress. On the next successful turn, the server will return updated values. This avoids complexity.
