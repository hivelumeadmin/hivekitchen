## Story

As a **HiveKitchen engineer closing the open-ended ReAct planner loop**,
I want **`planWeek` to be a linear `assemble → ensureCandidateCoverage → compose` pipeline where the LLM makes exactly one call (forced `plan.compose`) and recipe acquisition is a deterministic pre-flight**,
so that **turn count is bounded at 1 on the happy path, the self-correction machinery and iteration ceiling become dead code that can be deleted, and the planner's cost and reliability improve without changing any user-visible behavior**.

## Acceptance Criteria

### AC1 — New `apps/api/src/agents/planner/coverage.ts` module (deterministic pre-flight)

New file `apps/api/src/agents/planner/coverage.ts`. No `index.ts` barrel file in the directory.

```
export const MIN_MAIN_CANDIDATES = 2;   // minimum for no-consecutive-Main rule

export interface CoverageDeps {
  recipeService: RecipeService;
  recipeAgent: RecipeAgent | null;
  redis: Redis;
  auditService: AuditService;
  requestId: string;
  householdId: string;
  logger: FastifyBaseLogger;
}

export async function ensureCandidateCoverage(
  ctx: PlannerContext,
  deps: CoverageDeps,
): Promise<PlannerContext>
```

**Coverage check** (all conditions must hold for a no-op return):
- Main: `(ctx.recipeCandidates?.main.length ?? 0) >= MIN_MAIN_CANDIDATES`
- Extra: `(ctx.recipeCandidates?.extra.length ?? 0) >= 1` OR no bag composition requires an extra slot (extra is optional — a bag with no extra slot doesn't need a candidate). "Requires extra" = `ctx.extraRules !== undefined && ctx.extraRules.length > 0` (any extra rules exist → extras are in scope for at least one child).

When coverage is **sufficient**: return `ctx` unchanged. No service calls, no logging.

When coverage is **insufficient**:
1. **Derive a search query** from `ctx`:
   - If `ctx.culturalContext?.templateKey` is set, prefix the query with the template key (e.g., `"halal"`, `"vegetarian"`).
   - Fallback query: `"family-friendly lunch main dish"`.
   - If extras also need augmentation, append `" and extra side dish"`.
2. **Call `deps.recipeService.search(query, deps.householdId)`** to get recipe IDs. Fetch full candidate objects for any IDs not already in the slate. Augment `ctx.recipeCandidates.main` (and `extra` if needed) with the new candidates. Re-check coverage.
3. **If still insufficient after search and `deps.recipeAgent !== null`**: call `deps.recipeAgent.generate(query, deps.requestId)` (or the equivalent discover interface) to generate new recipes. Append any returned candidates to the slate. Log the discover invocation at `info` level.
4. After augmenting (or exhausting acquisition), return the updated `PlannerContext` with the new `recipeCandidates`. If coverage is still not met after both attempts, log a `warn` and return best-available (compose is still called — the guardrail catches anything unsafe).

**No TOOL_MANIFEST invocation.** Recipe acquisition is direct service calls, not LLM tool calls. This is what makes the tool-call count before compose = 0 on warm slates.

The function is **pure-ish** (no side effects other than service reads): it does not write to the database, does not mutate the input `ctx`, and returns a new `PlannerContext` object when augmented.

### AC2 — `planWeek` becomes a linear pipeline

The `planWeek` method body is restructured as follows. The narrative pipeline:

```
1. Destructure opts (householdId, weekOf, requestId, ...)
2. const ctx = assemblePlannerContext(opts);                 // s4
3. Build base tools array with per-run recipe.discover spec  // unchanged from today
4. await ensureCandidateCoverage(ctx, deps) → augmentedCtx  // NEW (s5)
5. renderPlannerRecipeCandidatesBlock(augmentedCtx) → { block, handleMap }
6. If recipeCandidates in augmentedCtx: create handle-aware plan.compose spec using handleMap
   planComposeTool = handle-aware spec OR base manifest spec
7. Build contextLines using augmentedCtx (kitchenMapBlock, childSignalsBlock, etc.)
8. const messages = [system, user]
9. Single forced-compose LLM call:
   const response = await this.completeWithMessages(
     messages, [planComposeTool],
     { tier: 'flagship', temperature: 0.2, maxTokens: 4096,
       metadata: { agent_type: 'planner', prompt_version: PLANNER_PROMPT.version },
       forcedToolName: 'plan.compose' },
     ['plan.compose'],
   );
10. Extract the single tool call; throw if none (provider that doesn't support strict tools)
11. Execute plan.compose: const result = await planComposeTool.fn(tc.arguments);
12. return result as PlanComposeTreeOutput;
```

Steps 1, 3, 6, 7, 8 are structurally the same as today — only the order of 4/5/6 changes (augmentation → render → handle-aware spec) and steps 9–12 replace the entire `for` loop.

**Step 9 detail:** The call passes `[planComposeTool]` as the sole tool and `forcedToolName: 'plan.compose'`. With OpenAI strict tools, the model MUST return exactly one `plan.compose` tool call. The `completeWithMessages` wrapper already enforces `allowedTools`, so any unexpected tool name throws `ForbiddenToolCallError` as today.

**Step 10 detail:** After the call, check `response.toolCalls.length`. If 0 (non-forced provider returned early), throw:
```
throw new Error(
  'planWeek: model did not call plan.compose (non-forced provider or empty response)',
);
```

**Step 11 detail:** Execute the single tool call exactly as in today's forced-compose fallback path. The `plan.compose` tool validates and returns the `PlanComposeTreeOutput` directly (s2 already removed the safeParse+audit redundancy). Infrastructure errors (ZodError from plan.tools.ts strict parse) propagate — no catch.

| Recipe acquisition is model-driven (model calls `recipe.search`) | Recipe acquisition is deterministic pre-flight (code calls service directly) |
| `MAX_PLAN_ITERATIONS = 8` constant exists | Deleted |
| Stopped-without-compose forced-compose fallback (s2) | Removed — compose is ALWAYS forced; there's no fallback anymore |

### The `ensureCandidateCoverage` module placement

`apps/api/src/agents/planner/coverage.ts` sits alongside `apps/api/src/agents/planner/context/` (the s4 output). No barrel file in either directory. The file imports only from:
- `'./context/assemble.js'` — `PlannerContext` type
- Service/infra modules (RecipeService, RecipeAgent, Redis, AuditService, FastifyBaseLogger)
- No import from `orchestrator.ts` — acyclic graph maintained

### Why `MIN_MAIN_CANDIDATES = 2`

The no-consecutive-Main rule (v2.6.0, enforced post-compose by the prompt and validated by s1 eval) requires at least 2 distinct Main options across a week's plan. With exactly 1 candidate the model is forced to repeat it every day, making the constraint trivially unmeelable. 2 allows M1/M2 alternation across a 5-day week. The planner typically selects from 3+ mains in practice (the loader `loadRecipeCandidatesForHousehold` returns up to ~10 mains from the catalog); `MIN_MAIN_CANDIDATES = 2` is the safe minimum, not the expected normal.

### Order of operations in the restructured `planWeek`

The current code runs:
1. Render `recipeCandidatesBlock` + build `handleMap`
2. Create handle-aware compose spec using `handleMap`
3. Build contextLines
4. For loop...

After s5, the order MUST be:
1. `assemblePlannerContext(opts)` → `ctx`
2. Build base tools (recipe.discover per-run override)
3. **`ensureCandidateCoverage(ctx, ...)` → `augmentedCtx`** ← NEW, comes first
4. `renderPlannerRecipeCandidatesBlock(augmentedCtx)` → `{ block, handleMap }` ← uses augmented ctx
5. Create handle-aware compose spec using updated `handleMap` ← uses updated handleMap
6. Build `planComposeTool`
7. Build contextLines using `augmentedCtx` (all render calls use `augmentedCtx`)
8. Build `messages`
9. Single forced-compose call
10. Return

The critical ordering invariant: **render must happen AFTER coverage augmentation**, because the candidate block needs to include any newly-acquired recipes so the model can reference them by handle.

### How to derive the recipe search query in `ensureCandidateCoverage`

The model used to decide what to search for. Now we derive it:

```ts
function deriveSearchQuery(ctx: PlannerContext): string {
  const parts: string[] = [];
  if (ctx.culturalContext?.templateKey) {
    // e.g., 'halal', 'vegetarian', 'gluten-free-friendly'
    parts.push(ctx.culturalContext.templateKey.replace(/_/g, ' '));
  }
  parts.push('family lunch main dish');
  return parts.join(' ');
}
```

This is a simple heuristic. The goal is "get some relevant recipes into the slate so compose can proceed," not "find the perfect recipes" — the model does the selection. The guardrail catches any safety failures regardless of how the candidates were acquired.

If both mains AND extras need augmentation, derive a single query that covers both (e.g., `"halal family lunch main dish and side"`) to avoid two separate search calls.

### Handling the forced-compose response

After the single `completeWithMessages` call:

```ts
const tc = response.toolCalls[0];
if (tc === undefined) {
  throw new Error('planWeek: model did not call plan.compose (non-forced provider or empty response)');
}
// tc.name MUST be 'plan.compose' due to allowedTools enforcement in completeWithMessages
const result = await planComposeTool.fn(tc.arguments);
// plan.tools.ts PlanComposeTreeOutputSchema.parse() validates and returns PlanComposeTreeOutput
// or throws ZodError. No try/catch here — let infra errors propagate.

  { requestId, householdId, weekOf, planId: (result as PlanComposeTreeOutput).plan_id },
  'planWeek: plan composed',
);
return result as PlanComposeTreeOutput;
```

The `allowedTools: ['plan.compose']` filter in `completeWithMessages` already throws `ForbiddenToolCallError` if the model somehow returned a different tool name. So `tc.name === 'plan.compose'` is guaranteed if `tc` exists.

### Updating the FakeLLMProvider in the eval harness

The `FakeLLMProvider` in `planner-eval.harness.ts` currently responds to each iteration of the for loop. After s5, `planWeek` makes one call with `options.forcedToolName === 'plan.compose'`. The fake provider must:

1. Detect `options.forcedToolName === 'plan.compose'` (or detect it's the only tool in the tools list).
2. Return a response shaped as:
   ```ts
   {
     content: null,
     toolCalls: [{ id: 'forced-compose-1', name: 'plan.compose', arguments: <fixture-plan-tree> }],
     finishReason: 'tool_calls',
     usage: { promptTokens: 100, completionTokens: 500, cachedPromptTokens: 0 },
   }
   ```
   Where `<fixture-plan-tree>` is the fixture's expected `PlanComposeTreeInput` (what the model would have emitted).
3. Throw/return an error response if called more than once per fixture run (regression guard).

The 1 bad-handle fixture (negative test) should use an `arguments` object that contains an unknown handle — the `plan.compose` tool's `fn()` will throw a "Recipe not found" / "handle not in map" error, which should propagate from `planWeek`.

### Eval budget assertion

The s1 eval has a budget assertion for tool-call count and tokens. After s5, the expected tool-call count for warm-slate fixtures is **1** (the single plan.compose call). Update the assertion:

- Old (s2 era): `toolCalls.length <= N` (allowed for multi-turn loop)
- New (s5): `toolCalls.length === 1` AND `toolCalls[0].name === 'plan.compose'`

This is a stricter assertion and acts as a regression guard: if any future change accidentally re-introduces pre-compose tool calls, the eval will fail.

### Regen callback path (plan-generation.job)

`plan-generation.job.ts` calls `orchestrator.planWeek(opts)` for both the initial plan and the guardrail-retry regen callback. The job assembles the `PlanWeekOptions` (including `recipeCandidates`) ONCE and passes the same object to both invocations. After s5:

- Initial call: `ensureCandidateCoverage` runs, slate may be augmented, compose runs.
- Regen call (on guardrail block): same opts, `ensureCandidateCoverage` runs again — since the slate was already sufficient for the initial call, the regen call will also find it sufficient (same slate, same data) and return immediately. **No behavioral change** for the regen path.

The `rejectionContext` in opts is set for the regen call to tell the model to avoid blocked ingredients. This is injected into `contextLines` as today — no change needed.
