## Story

As a parent completing the Moment 4 ("What goes in the bag") step of onboarding,
I want Lumi to present action chips for the 4 canonical bag composition patterns plus a free-text input for per-child variation,
so that Lumi can record each child's `bag_composition_pattern` and use it to structure weekly lunch plans.

## Acceptance Criteria

1. **AC1 — Chip config wired for m4_bag**: `momentToChipConfig('m4_bag')` in `onboarding.service.ts` returns a `ChipConfig` with `mode: 'action'` and exactly 4 chips whose `key` values match `BagCompositionPatternSchema` enum values (`main_only`, `main_plus_snack`, `main_plus_extra`, `main_plus_snack_plus_extra`). No `skip_label` (M4 is a required-response gate).

2. **AC2 — Service write path for bag_composition_pattern**: `UpsertByNameBody` in `children.service.ts` gains optional `bag_composition_pattern?: BagCompositionPattern` field. `ChildrenService.upsertByName()` passes it to the repository when present.

3. **AC3 — Repository write**: `ChildrenRepository` writes `bag_composition_pattern` to the `children.bag_composition_pattern` column when the field is provided in the upsert call. Uses the established `UPDATE ... SET bag_composition_pattern = $1 WHERE id = $2 AND household_id = $3` pattern (cross-household safety guard). Null value is accepted (PATCH semantics: omit to preserve).

4. **AC4 — Tool wiring**: `createChildUpsertToolSpec` (in `packages/contracts/src/onboarding-tools.ts` factory and/or `apps/api/src/agents/tools/`) extracts `bag_composition_pattern` from `ChildUpsertInputSchema` (already present from 2.5-s1) and passes it to `ChildrenService.upsertByName()`. Tool spec already accepts it via `ChildUpsertInputSchema.bag_composition_pattern`; this AC wires the downstream path.

5. **AC5 — Agent prompt M4 chip-key alignment**: Verify (and patch if needed) that the M4 section in `apps/api/src/agents/prompts/onboarding.prompt.ts` uses the exact chip keys that match `BagCompositionPatternSchema` (`main_only`, `main_plus_snack`, `main_plus_extra`, `main_plus_snack_plus_extra`). The prompt must also specify that when a parent submits a single chip, the agent calls `child.upsert` for every child with the same `bag_composition_pattern`. For freetype prose describing per-child variation, the agent calls `child.upsert` per child with the inferred pattern.

6. **AC6 — OnboardingText.tsx M4 state tracking**: `OnboardingText.tsx` tracks M4 capture state (pattern: `m4BagCapture: M4BagCaptureState`). State type: `{ state: 'none' } | { state: 'capturing' } | { state: 'captured'; mode: 'household'; pattern: string } | { state: 'captured'; mode: 'per-child'; children: Array<{ name: string; pattern: string }> }`. State transitions from `'none'` → `'capturing'` when `currentMoment === 'm4_bag'` is detected in an agent turn. State advances to `'captured'` when `NEXT_MOMENT:m5_starting_line` directive is received. Note: exact captured data comes from the Kitchen Map live read (2.5-s11); the `OnboardingText.tsx` profile card for M4 can use the same lean "Still listening…" → "Captured" approach used in M3 (showing the moment is done, not the full structured data).

7. **AC7 — M4 profile card rendered in OnboardingText.tsx right panel**: When `m4BagCapture.state !== 'none'`, the M4 profile card renders in the right-column Kitchen Profile using `IcoLunchBag` (SVG already in `Moment4Page.tsx` — copy the inline SVG), title "What goes in the bag". `state: 'capturing'` → "Still listening…" (inactive card style). `state: 'captured'` → active card style with "Saved — Lumi knows how lunch travels" or similar minimal confirmation text. Full structured display deferred to 2.5-s11.

8. **AC8 — Typecheck + test sweep**: `pnpm typecheck` passes. At minimum 6 unit tests:
   - `momentToChipConfig('m4_bag')` returns correct chip keys and labels
   - `upsertByName` passes `bag_composition_pattern` to repository
   - Repository writes correct UPDATE SQL with `bag_composition_pattern`
   - `createChildUpsertToolSpec` surfaces `bag_composition_pattern` to service
   - `OnboardingText.tsx` M4 card renders in `'capturing'` state
   - `OnboardingText.tsx` M4 card renders in `'captured'` state

### Chip Key Reconciliation (Mockup vs Contract)

The `Moment4Page.tsx` mockup uses 5 display patterns with arbitrary keys (`main-2-sides`, etc.) that do NOT match the contract. The production implementation MUST use `BagCompositionPatternSchema`'s 4 enum values:

| Contract key | Suggested display label |
|---|---|
| `main_only` | "Main only" |
| `main_plus_snack` | "Main + snack" |
| `main_plus_extra` | "Main + sides" |
| `main_plus_snack_plus_extra` | "Full bag" |

The mockup's "Thermos + snack" maps to `main_plus_snack`. "Bento-style" and "Sandwich + fruit" are presentation variants that map to `main_plus_extra` or `main_plus_snack_plus_extra` depending on context — the agent infers from prose if the parent describes these.

### DB Column Verification

The `children.bag_composition_pattern` column was supposed to be added in 2.5-s1. Before T3, verify by checking `supabase/migrations/` for the migration that adds it. If the column is missing, create a new migration in T3.3 — do not modify an existing merged migration.

### Dual bag_composition vs bag_composition_pattern

Two coexisting fields in `children`:
- `bag_composition: { main: true, snack: boolean, extra: boolean }` — the **planner-facing** boolean struct. Written by `ChildrenRepository.updateBagComposition()`. Updated from `PATCH /v1/children/:id/bag-composition` (settings). Do NOT touch this in 2.5-s8.
- `bag_composition_pattern: BagCompositionPattern | null` — the **parent-stated mental model** written in Moment 4 via `child.upsert`. This is what 2.5-s8 wires.

Both fields exist independently in `KitchenMapChildSchema` — the planner uses `bag_composition` (struct); the profile display uses `bag_composition_pattern` (label). 2.5-s11 will project live data from both fields.

### Tool Call Flow (M4)

```
Parent taps "Main + snack" chip
  → Client submits: { chip_selections: ['main_plus_snack'], text: '' }
  → POST /v1/onboarding/text/turn
  → OnboardingService.submitTextTurn
  → Agent executes with chip context
  → Agent calls: child.upsert({ child_id: 'layla-id', bag_composition_pattern: 'main_plus_snack' })
  → Agent calls: child.upsert({ child_id: 'adam-id', bag_composition_pattern: 'main_plus_snack' })
  → createChildUpsertToolSpec → ChildrenService.upsertByName → ChildrenRepository.updateProfile
  → Agent emits: "Got it — same for both. [NEXT_MOMENT:m5_starting_line]"
```

For prose: "Layla bento, Adam thermos":
```
  → Agent infers Layla → main_plus_extra, Adam → main_plus_snack
  → Two child.upsert calls with different patterns
```
