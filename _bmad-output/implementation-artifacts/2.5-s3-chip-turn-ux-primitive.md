## Story

As **the onboarding conversation system**,
I want **a chip turn UX primitive — production chip components, an extended API contract that accepts bundled `{ chip_selections, text }` payloads, and a rendering slot in `OnboardingText` that shows chips inline below Lumi's message when the agent's response includes a chip config** —
so that **the five moment slices (2.5-s5 through 2.5-s10) can each wire their specific chip group into the onboarding conversation without rebuilding the chip infrastructure**, and so that the backend can receive structured chip selections from the client as a first-class turn format.

### AC2 — Extended `TextOnboardingTurnRequestSchema`

`packages/contracts/src/onboarding.ts` is updated so that `POST /v1/onboarding/text/turn` accepts two distinct turn shapes:

```ts
// Text-only turn (existing — unchanged)
export const TextTurnBodySchema = z.object({
  message: z.string().trim().min(1).max(4000),
});

// Chip turn — at least one selection OR non-empty text
export const ChipTurnBodySchema = z.object({
  chip_selections: z.array(z.string().min(1).max(64)).min(1).max(20),
  text: z.string().trim().max(4000).optional(),
});

// Union — the route handler discriminates on which keys are present
export const TextOnboardingTurnRequestSchema = z.union([
  TextTurnBodySchema,
  ChipTurnBodySchema,
]);
```

Both schemas and the union are exported from `@hivekitchen/contracts`. Add corresponding types via `z.infer<>`:

```ts
export type TextTurnBody = z.infer<typeof TextTurnBodySchema>;
export type ChipTurnBody = z.infer<typeof ChipTurnBodySchema>;
export type TextOnboardingTurnRequest = z.infer<typeof TextOnboardingTurnRequestSchema>;
```

**Backward compatibility note:** The existing `{ message }` shape still parses correctly. No change to the response schema in this slice.

### AC3 — Extended `TextOnboardingTurnResponseSchema` — chip config

The response schema gains an optional `chip_config` field (null when the agent returns no chips, non-null when the agent's response includes structured chip suggestions):

```ts
export const ChipConfigSchema = z.object({
  mode: z.enum(['hint', 'action', 'choice']),
  options: z.array(z.object({ key: z.string(), label: z.string() })).optional(),
  hints: z.array(z.string()).optional(),
  skip_label: z.string().optional(),
});

export const TextOnboardingTurnResponseSchema = z.object({
  thread_id: z.string().uuid(),
  turn_id: z.string().uuid(),
  lumi_turn_id: z.string().uuid(),
  lumi_response: z.string(),
  is_complete: z.boolean(),
  chip_config: ChipConfigSchema.nullable().optional(),   // ← NEW, optional
});
```

In this slice, the backend always returns `chip_config: null` (the agent doesn't emit chip configs until 2.5-s4). The field is added now so `OnboardingText.tsx` can be wired to read it without a follow-up contract change.

Add `ChipConfig`, `ChipConfigSchema` to the contracts barrel.

### AC4 — Backend route: accept chip turns and serialize to agent-readable message

`apps/api/src/modules/onboarding/onboarding.routes.ts` handler for `POST /v1/onboarding/text/turn`:

1. Parse the request body using `TextOnboardingTurnRequestSchema` (Zod union — Fastify/ZTP handles the validation).
2. Discriminate the payload shape:
   - If `'message' in body` → text turn: `agentMessage = body.message` (unchanged)
   - If `'chip_selections' in body` → chip turn: serialize to natural language:
     ```
     `[Chips selected: ${body.chip_selections.join(', ')}]${body.text ? ` ${body.text}` : ''}`
     ```
   The serialized string is passed to `onboardingService.textTurn(threadId, agentMessage)` — the service signature is **unchanged**.
3. Return `{ ..., chip_config: null }` in the response (AC3). The `chip_config` field is always null until 2.5-s4.

**Do NOT change `OnboardingService` or the agent in this slice.** The service/agent receive the serialized string, not the raw chip payload.

**Fastify schema validation:** The route's `schema.body` must be updated to accept both shapes. With `fastify-type-provider-zod`, pass `TextOnboardingTurnRequestSchema` as the body schema. Do not hand-roll Ajv.

### AC5 — `OnboardingText.tsx` chip rendering slot

`apps/web/src/features/onboarding/OnboardingText.tsx` gains chip awareness:

1. **State**: Add `chipConfig` to component state — initialized from the latest `lumi_response`'s `chip_config` field. Type: `ChipConfig | null`.

2. **Rendering** — in the focused view (not history view), after Lumi's question prose and before the input bar, render the chip group when `chipConfig` is non-null:
   ```
   [Lumi's waveform orb]
   [Lumi's question text — large serif]
   
   [Chip group — if chipConfig is non-null]
     hint mode:  HintChip × N (non-selectable, illustrative; see Moment1Page)
     action mode: ChoiceChip mode="single" × N
     choice mode: ChoiceChip mode="multi" × N
   [SkipChip — only if chipConfig.skip_label is set]
   [FreetypeInput — always shown when chipConfig is non-null, below chips]
   
   [Input bar / pill form — same as today]
   ```

3. **Input bar layout** — follow `Moment1Page.tsx` pattern (NOT `ChipPrimitivePage` StickyBottomBar):
   - The pill-shaped form at the bottom stays as-is.
   - The FreetypeInput (from chip config) does NOT replace the textarea — the textarea remains.
   - The `chip_selections` state is tracked separately from `draft` (textarea text).
   - `hasResponse = chip_selections.length > 0 || draft.trim().length > 0`
   - Send is disabled when `hasResponse` is false (same as existing logic).
   - When `chip_selections.length > 0`, show a micro-confirmation below the input bar:
     `"N selections will be sent with your message"` (foliage color, italic, centered — copy the Moment1Page pattern exactly).

4. **Submit handler**: When `chipConfig` is non-null, POST `{ chip_selections, text: draft }` (chip turn body). When `chipConfig` is null, POST `{ message: draft }` (text turn body — unchanged).

5. **On successful response**: parse `chip_config` from the response; update `chipConfig` state. Clear `chip_selections` on every successful submission.

6. **When agent returns `chip_config: null`** (always, in this slice): `chipConfig` is set to null → chips do not render → pure text input (existing behavior unchanged).

**The focused view renders chips INLINE** (not in a StickyBottomBar). The mockup authority for the input bar layout is `Moment1Page.tsx` line 308–358.

### Contract union discrimination — no "kind" field needed

The `TextOnboardingTurnRequestSchema` is a `z.union` (not `z.discriminatedUnion` — no shared discriminant key). Zod tries each branch in order. The route handler discriminates manually:

```ts
// In the route handler after body is parsed:
const agentMessage =
  'chip_selections' in body
    ? `[Chips selected: ${body.chip_selections.join(', ')}]${body.text ? ` ${body.text}` : ''}`
    : body.message;
```

This serialization format is intentionally simple — the agent in 2.5-s4 will be prompted to understand `[Chips selected: ...]` prefixes. Do NOT try to do anything fancier here.

### `OnboardingText.tsx` — chip config state management

The `chipConfig` state starts as `null` (no chips on initial render). After each successful Lumi response that includes a `chip_config`, update it. After each successful Lumi response where `chip_config` is absent or null, clear it:

```ts
const [chipConfig, setChipConfig] = useState<ChipConfig | null>(null);
const [chipSelections, setChipSelections] = useState<string[]>([]);

// In the success branch of handleSubmit:
const parsed = TextOnboardingTurnResponseSchema.parse(raw);
setChipConfig(parsed.chip_config ?? null);
setChipSelections([]);  // always clear on turn completion
```

In this slice, `parsed.chip_config` is always `null` (backend hardcodes it). That's fine — the existing text-only behavior is unchanged.

### FreetypeInput in OnboardingText — do NOT render it as a second textarea

When `chipConfig` is non-null, the UI shows:
- Chips above the pill-form textarea (inline, in the content scroll area)
- The existing pill-form textarea at the bottom

The `FreetypeInput` component from the chip components IS essentially a styled `<input>` / `<textarea>`. Do NOT render it as a separate input ABOVE the pill-form. The chip group renders above the pill-form; the user types additional context directly in the existing pill textarea below. The chip selections are tracked separately from `draft`.

This keeps the layout clean: chips are structured suggestions (above), freetype is the existing text area (below). The mockup hint placeholder text changes based on `chipConfig`:
- No chips: `"Type your answer..."` (existing)
- Chips present: `"Add a note…"` or `"Or type your own…"` (a shorter, lighter placeholder that signals chips are the primary input)


`handleSkip` in this slice can be a no-op stub since the real skip behavior (advancing the agent to the next moment) lives in 2.5-s4's prompt.
